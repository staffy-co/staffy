## Intent

**Problem:** Между «каталог разрешённых действий» (3-1) и «авторизацией Operation» (3-5) отсутствует подготовительный контур (FR-28, AC-блоки 1-12): нет proposal-границы — типизированной строгой валидации входа действия против TypedInputSchema выбранной Action Definition с ограниченным repair-pass (AD-7: строгая валидация допускает одну попытку исправления, повторная невалидность — терминальный отказ; лишнее поле сегодня некому отвергнуть и нечему не передаваться — Connector write-tool вообще не определён); нет Policy-проверки подготовки живыми источниками — Tenant/Employee/Domain Pack/Conversation Mode/Response Owner/role-authority/Scoped Controls/Entitlement/stage/gates/capability evidence существуют по отдельности (identity 1-2, cases 2-4/2-5, control 3-2 EffectiveFor, entitlement AdmissionState 1-11/1-14, employee ReadinessView+GateDictionary 1-4/1-14, connector CapState 1-8/1-9), но никто их не собирает в один вывод «разрешить подготовку preview либо точная блокировка», и текст proposal не объявлен не-входом Policy; нет материального snapshot свежих read-only данных Owning System (external IDs, versions, observed times, evidence — AD-3) — stale/conflicting/unknown значениям некогда блокировать готовность и нечем явно становиться разрешённой неопределённостью; нет Action Preview как append-only версии со стабильным ID, digest и полным материальным показом (action type, target, точные поля, последствия, цена/сумма, reversibility, cancel/compensation semantics, terminal evidence, разграничение staffy/human-only); нет отдельного перечисления эффектов с порядком/зависимостями/failure semantics и структурного запрета открытого набора; нет human-only маркировки unsafe/бесreconciliation-path возможностей и обязательного человеческого owner + recovery instruction при one-shot процедуре; нет dry-run/validation evidence с честным «dry-run ≠ выполненное действие»; нет stale-вывода при изменении Fact/Observation/owner epoch/control generation/Release Manifest/policy/capability evidence (старая версия читаема для аудита, авторизации не подлежит); нет редактирования-новой-версии с diff материальных изменений; нет Timeline-различения proposal/previewed; нет a11y-поверхности preview с readback и основным действием «переход к авторизации», а не скрытым dispatch. Честное состояние контура: AI Runtime не существует (AG-4 — автор proposal человек с правами кейса; типизированная граница останется для будущего Runtime: контракт proposal — машиночитаемая форма, машина не получает write-tool и не создаёт Authorized Action в принципе — Authorized Action строит только 3-5 после Confirmation); реальных коннекторов с query/command-capabilities нет (AG-4 — бинарный каталог 3-1 честно пуст; вертикаль закрывается fixture-определениями/fixture-ридером тестового контура); Connector write-request в срезе физически невозможен (мутационные адаптеры — исключительная территория dispatch composition root 3-6, в 3-4 их не существует); Operation/Action Receipt — story 3-5/3-6 (таблиц нет, слова Timeline не выводятся); Confirmation связывается только с показанным набором — 3-5 (здесь пинится дисциплина: preview-effects конечны из definition, редактирование = новая версия). Первый срез рождает подготовительный контур: proposal с repair-pass, живая Policy подготовки, материальный snapshot с честной неопределённостью, append-only Preview с версиями/digest/эффектами/human-only, stale-вывод, dry-run evidence, Timeline-слова, страница Preview с a11y.

## I/O & Edge-Case Matrix

## Implementation Notes

- Repair-pass — СТРУКТУРНАЯ граница: attempt_no CHECK ∈ {1,2} + UNIQUE (proposal_key, attempt_no) в БД — третья попытка невозможна на уровне миграции, не дисциплиной; «ограниченный» = repair не добавляет полей: DisallowUnknownFields, effects вне typed_input, тот же ключ попыток; verdict rejected терминален навсегда (новый ключ = новый proposal, но определение/автор/кейс те же — счётчик историй попыток показан на странице честно).
