## Intent

**Problem:** 2-4 выдал контуру единственного response-owner и записывающую поверхность, но сама природа диалога не управляется: Conversation Mode не существует как класс — карточка показывает текст-плейсхолдер «Запрос ещё не классифицирован» (2-1), лестницы приоритетов нет, смена режима не фиксируется, продажные ответы ничем не останавливаются (FR-14: «коммерческие Actions и убеждение недоступны в запрещающем режиме» — нечему запрещать). Модель не может «понизить» приоритетный режим — верно по отсутствию модели, но и детерминированной Policy-механики нет: предложения intent/mode не принимает, не валидирует и не сохраняет (AC-4/5). Возврат в `sales` существует как риск будущих автономных поверхностей без гейта (AC-7). Per-Work-Item контекст режима отсутствует: разные WI одного диалога не имеют собственных режимов, строгий активный режим не применяется к несовместимым действиям (AC-8). Оператор не видит режим/причину/источник сигнала/запрещённые действия (AC-9). AI-раскрытие не существует: Staffy-владелец (назначается с 2-4) может «отвечать» без записи о том, что он цифровой сотрудник; текст/канал/время/lineage/delivery-статус раскрытия не сохраняются (FR-15, AC-1); состояния generated/sent/playback/customer-confirmed не различаются (AC-2); исходящий партнёрский контакт без основания (источник/цель/consent) нечему блокировать (AC-3); оспаривание основания не переводит диалог в `privacy_no_contact` (FR-15). Идемпотентность policy-событий и защита от двойных переходов не определены (AC-10). Доступность смены режима (badge текстом, повторное чтение раскрытия, без неожиданного focus) не реализована (AC-11).

**Approach:** Первый срез строит механику режимов и раскрытия целиком на append-only-дисциплине (прецедент 2-2/2-3/2-4: история не редактируется, «текущее» — производная чтения), без изменений ingest-логики 2-1 (кроме ровно одного INSERT initial-терма — прецедент initial-термина владения 2-4) и без реальной доставки/медиа (AG-4). AI Runtime в контуре нет — честная граница среза: предложения intent/mode приходят явными командами (операторская фиксация сигнала с привязкой к turn-событию; синтетический proposer-порт для будущих автономных поверхностей), а детерминированная Policy валидирует их по лестнице приоритетов. (1) **Словарь и лестница:** `safety > claim > cancellation > privacy_no_contact > human_requested > unclassified > sales` (rank строгости; всё кроме `sales` — несбытовой путь); initial-терм при admission — `unclassified` (канон-текст 2-1 «не классифицирован»; неизвестный/неоднозначный случай — безопасный несбытовой путь, AC-5). (2) **Термы режимов:** append-only `mode_terms` со scope `conversation|work_item`: mode, mode_version монотонная (UNIQUE tenant+conversation+version — CAS-прецедент epoch 2-4), origin `ingest_initial|proposal|exit_override`, reason ≤200, signal_source `turn_event|operator|policy_rule`, turn_ref на событие кейса, actor, prior_mode, rule_version (словарь `mode-policy-v1`). Производные: активный режим диалога — максимальная версия терма scope=conversation; контекст WI — последний терм scope=work_item; **эффективный режим WI = строгий из двух** (AC-8: conversation применяет наиболее строгий к несовместимым действиям). (3) **Детерминированная Policy (mode-policy-v1):** GuardProposeMode — предложение РАНЬШЕ активного (понизить) → честный отказ `mode_not_downgradable` (модель не может понизить — AC-4); равный активному → отказ `mode_active` (повтор сигнала — не переход); выше → терм version+1; неизвестный mode → 400; неоднозначные сигналы → строгий (лестница максимума); выход из приоритетного режима — NEVER автоматичен: только `exit_override` с полномочием и причиной (AC-7 «не возвращается только по отсутствию повторения»); явное правило v1: нейтральные действия при запретном режиме разрешены (безопасная работа по независимому WI — только по этому объявленному правилу, AC-8). Полномочия exit: `safety` — только надзор (`configuration`); остальные — текущий владелец с `review` либо `configuration` (AC-9: override не ослабляет platform safety). (4) **Гейт продажных действий:** существующая команда `send_client_reply` (2-4) расширяется required-полем `reply_class` `sales|neutral|protected_request` (класс размечает продюсер — машина контент не классифицирует, честная граница): `sales` → эффективный режим WI обязан быть `sales` (иначе машинночитаемый отказ: active_mode, reason, signal_source, rule_version, permitted_path=exit) + действующее AI-раскрытие для канала; `protected_request` → действующее AI-раскрытие (AC-1: раскрытие до продажи и запроса защищённых данных); `neutral` — без раскрытия. (5) **AI-раскрытие:** append-only `disclosure_records` (conversation, channel, точный текст ≤2000, lineage релиза по прецеденту reply 2-4, parent_ref для повторного раскрытия после перебивания) + append-only `disclosure_delivery_events` (kind `generated|sent|playback_acknowledged|playback_estimated|customer_confirmed|interrupted` — состояния не смешиваются, AC-2); действующее раскрытие = производная: последняя запись (conversation, channel) с последним событием ∈ {sent, playback_acknowledged, playback_estimated, customer_confirmed}; `interrupted` гасит (перебивание до завершения — Staffy кратко повторяет, AC-2: повторная запись с parent_ref); события доставки записывает команда (живые playback/barge-in сигналы — AG-4, честно отложено; `playback_acknowledged/estimated` не считаются доказательством услышал/понял — гейт требует только «отправлено»). (6) **Основания исходящего контакта:** доменная механика fail-closed GuardOutboundBasis (partner source word + purpose + consent word — синтетические слова, продюсеров в контуре нет: исходящие коннекторы AG-4); без основания первый исходящий контакт блокируется (AC-3); оспаривание основания клиентом — сигнал turn_event → предложение `privacy_no_contact` → Policy поднимает (FR-15); voicemail/третье-лицо формулировки — вместе с реальными исходящими (за границей). (7) **Поверхность:** Status Badge (активный mode + AI-role владельца из owner_kind 2-4 + причина) текстом не цветом; панель Conversation Mode (лестница, активный, история термов, запрещённые действия, формы предложения/выхода/per-WI-контекста); раскрытия в таймлайне карточки и панель раскрытий (текст, канал, delivery-статус, повторное чтение); смены режима в таймлайне; формы PRG/focus-flash/≥44×44px/320px (прецедент 2-2/2-3/2-4); динамическая смена режима объявляется aria-live без неожиданного перемещения focus (AC-11). (8) **Идемпотентность:** все 4 новые команды через `command_records` (прецедент 2-2/2-3/2-4: replay исхода, отказ не отравляет ключ, тот же ключ с иным материалом → конфликт); повтор turn/policy event не создаёт второй переход (AC-10); конкурентные термы — advisory-лок кейса, ровно одна версия, проигравший — честный 409 с текущим режимом.

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 2-3/2-4): демо-путь — входящее обращение (2-1) в одной транзакции создаёт Case/Conversation/WI + initial-терм режима `unclassified` v1 → карточка: badge «не классифицирован», продажи невозможны → оператор фиксирует сигнал классификации (propose `sales`, turn_ref) → Policy: выше → терм v2, продажные действия открыты → оператор отправляет продажный ответ (`reply_class=sales`) → отказ гейта: действующего AI-раскрытия для канала нет (AC-1) → record_disclosure (текст «цифровой сотрудник», канал, lineage) + delivery `sent` → продажный ответ проходит → синтетический proposer предлагает `safety` (turn-сигнал) → Policy: строго выше → терм v3, badge safety + причина + источник → продажный ответ → машинночитаемый отказ (режим запрещает; permitted_path=exit) → предложение понизить в `sales` → отказ `mode_not_downgradable` (AC-4/7) → turn без сигнала → терма нет (автовозврата нет) → явный выход надзором (configuration, причина) → терм v4 `sales` → пер-Work-Item: WI-1 контекст `cancellation` (терм) → эффективный WI-1 = cancellation → продажный ответ WI-1 отказан, WI-2 (без терма, conversation sales) — разрешён (явное правило v1) → перебивание раскрытия: delivery `interrupted` → действующее погашено → продажный ответ снова требует раскрытия → повторное раскрытие (parent_ref) + `sent` → проходит → replay команды идемпотентен, тот же ключ с другим материалом — конфликт (AC-10) → гонка двух предложений → одна версия + 409 → оспаривание основания: сигнал turn_event → `privacy_no_contact` v2 → продажи остановлены (FR-15) → RLS: чужой Tenant 404 → вся цепь 320px/focus/badge текстом. AI Runtime (авто-извлечение сигналов/intent), реальная доставка/playback/TTS, barge-in сигнал, исходящие коннекторы и voicemail-правила, богатые policy-правила по Domain Pack/фактам и воспроизводимость Policy Outcome — 2-6/AG-4 честно; real-time push и Work Control Card — 2-14.

## Boundaries & Constraints

**Always:** Append-only: `mode_terms`, `disclosure_records`, `disclosure_delivery_events` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, грантов UPDATE/DELETE нет; активный режим / контекст WI / действующее раскрытие — производные чтения (максимальная версия терма scope=conversation; последний терм scope=work_item; последнее delivery-событие записи), не хранимые state-колонки. CAS-версии: каждая переходная команда несёт expected_mode_version ≥ 1; переход — INSERT терма под UNIQUE (tenant, conversation_id, mode_version) + advisory-лок кейса (сортированный lock-план, прецедент 2-3/2-4); конфликт — честный 409 с текущим режимом (mode, reason, signal_source, version); конкурентные гонки детерминированы интеграционными тестами (ровно один терм, проигравший — безопасное перечитывание). Идемпотентность — единый механизм 2-2/2-3/2-4: `cases.command_records` (UNIQUE tenant+actor+command+key, request-hash со всем материалом команды, replay исхода до стражей), словарь команд расширяется `propose_mode|exit_mode|record_disclosure|record_disclosure_event`; гейт продажных ответов расширяет существующую `send_client_reply` (новой команды нет; expected_epoch/владелец/гейт 2-4 не меняются, reply_class — required после гейта владения тем же порядком «гейт раньше CAS»). Initial-терм `unclassified` v1 пишет та же транзакция ingest, что создаёт Case/Conversation (лестница адмиссии, словари отказов и логика 2-1 не меняются ни строкой; тесты 2-1 не правятся; +1 INSERT — прецедент initial-термина владения 2-4). Лестница приоритетов и словарь режимов — фиксированный словарь домена (`safety|claim|cancellation|privacy_no_contact|human_requested|unclassified|sales`; несбытовой = всё кроме `sales`); Policy mode-policy-v1 — детерминированные правила домена, версионированы словарём, терм хранит rule_version; понижение режима командой предложения НЕВОЗМОЖНО как класс (GuardProposeMode отказывает), единственный путь понижения — `exit_mode` с полномочием (authority `supervisor` для `safety`; владелец с `review` или `configuration` для остальных) и причиной ≤200; автоматического выхода по отсутствию сигнала не существует (AC-7). Эффективный режим WI = строгий (max rank) из активного режима диалога и контекста WI; продажные ответы (`reply_class=sales`) — только при эффективном `sales`; нейтральные — по явному правилу mode-policy-v1 (безопасная работа при запретном режиме); `protected_request` — действующее раскрытие (AC-1). Раскрытие: запись несёт conversation, channel (словарь каналов 2-1), точный текст ≤2000, lineage релиза (employee, decision_no, profile_version — снимок прецедента reply 2-4), actor, время, parent_ref для повторного; delivery-события — словарь `generated|sent|playback_acknowledged|playback_estimated|customer_confirmed|interrupted`, состояния не смешиваются, последнее событие записи — её текущий статус; действующее раскрытие (conversation, channel) — последняя запись со статусом ∈ {sent, playback_acknowledged, playback_estimated, customer_confirmed}; `interrupted`/`generated` не действуют; playback-статусы доказательством услышал/понял не считаются (гейту нужен только факт отправки — AC-2); срок действия не выдумывается (без TTL-полей — действительность определяется записью и её последним событием, не часами). Основания исходящего контакта: GuardOutboundBasis — доменная функция над синтетическими словами (partner source word, purpose word, consent word), fail-closed: без полного набора исходящий первый контакт блокируется (AC-3); продюсеров слов в контуре нет (AG-4), положительная ветка доказывается юнит-тестом на синтетике (прецедент evidence-гейта 2-4). Outbox: `case.mode_changed` v1 (снимок терма: version, mode, scope, reason, signal_source, actor) и `case.disclosure_recorded` v1 — той же транзакцией, что терм/запись; доставка — существующий `DrainOutbox` (не меняется). Полномочия на сервере до SQL: propose/record/event — участники с `review`; exit — по лестнице authority выше; гейт reply_class — только текущий владелец (наследуется гейтом 2-4, владелец-Staffy: продавливание продажных классов будущими автономными поверхностями через те же гейты); не-участник Tenant — 404 без раскрытия существования; межтенантная изоляция — RLS во всех новых таблицах. Privacy: новые таблицы — класс `case-operations` (чтение `review`/`audit`, команды — `review`; текст раскрытия ≤2000 следует классу операционных записей кейса, как контент reply 2-2/2-4); TestPerimeterIntegrity синхронно заявляет все новые таблицы; в exceptions/телеметрию/outbox-конверты — только идентификаторы, словарные состояния и времена, без текста раскрытия и без PII. Транспорт: операторские формы PRG + машинный JSON-контракт, OpenAPI синхронно (пути 4 команд + расширение send_client_reply required reply_class + ModeView/DisclosureView + форму отказа режима: active_mode, reason, signal_source, rule_version, permitted_path), контракт-тест ассертит словари и required-дисциплину. UI: активный режим, AI-role владельца (owner_kind), причина/источник сигнала, запрещённые действия и delivery-статус раскрытия — текстом (не цветом); unclassified и sales — разные подписи; раскрытие можно повторно прочитать (текст записи); динамическая смена режима — aria-live без неожиданного перемещения focus; ошибки связаны с полями; flash-focus после действия/конфликта; цели ≥44×44 px; 320 px без горизонтального скролла. Регресс 2-1/2-2/2-3/2-4 обязан оставаться зелёным (build/vet/unit/интеграция обеих TZ/journeys/контракт/diff); файлы тестов прошлых срезов не правятся (кроме механических расширений фикстур journeys, если неизбежно — с честной записью в Change Log).

**Never:** Не менять колонки/ограничения миграций 00001–00004 (снятие CHECK epoch/surface — уже сделано 2-4; текущие режимы — в термах 00005, «текущее» — производная). Не позволять понижение режима предложением (GuardProposeMode отказывает всегда; выход — только exit_mode с полномочием; никакие «системные» понижения и таймеры). Не снимать `safety` владельцем-оператором (только configuration-надзор; platform safety не ослабляется override — AC-9). Не возвращать `sales` автоматически (отсутствие повторения сигнала — не выход; exit-терм обязан существовать с причиной и полномочием). Не пропускать продажный/защищённый ответ без действующего раскрытия (гейт серверный; скрытие кнопки — не проверка). Не считать `playback_acknowledged/estimated` доказательством того, что клиент услышал/понял (гейту достаточно sent; требования confirmed — будущая policy). Не смешивать delivery-состояния (одно событие — один kind; статус записи — производная последнего события; UPDATE/DELETE событий не существует). Не выдумывать срок действия раскрытия и дедлайны режимов (никаких TTL-полей; действительность — производная записи и событий). Не классифицировать контент ответов машиной (reply_class размечает продюсер: оператор в форме, будущие автономные поверхности — своими гейтами; словарь fixed). Не записывать текст раскрытия в exceptions/логи/outbox-конверты (текст живёт только в записи). Не заявлять реальную доставку/playback/TTS-аудио (delivery-события пишет команда; живые сигналы — AG-4; аудио-версия раскрытия — исходящие диалоги). Не строить автоматическое извлечение сигналов/intent из клиентских реплик (AI Runtime нет; сигнал фиксируется командой с turn_ref; авто-извлечение — будущая AI-story с собственными gate). Не строить в этом срезе: реальные policy-правила по Domain Pack/фактам и Policy Outcome с воспроизводимостью по входным версиям (2-6), генерацию ответов Staffy (2-6+), исходящие коннекторы/первый исходящий партнёрский контакт как поверхность и voicemail/третье-лицо формулировки (AG-4), barge-in автоматический (AG-4), real-time push карточки, Work Control Card (2-14), heartbeat-периодический опрос DeliveryStatus. Не блокировать входящие события состоянием режима (ingest и правила продолжения не трогаются; таймлайн живёт по 2-1/2-3). Не трогать гейты и семантику владения 2-4 (reply_class добавляется ПОСЛЕ гейта владения тем же порядком; владелец/epoch/surface/drain не меняются; stale-семантика drain сохраняется).

## I/O & Edge-Case Matrix

- Given новое обращение на допущенном маршруте, when ingest исполняется, then в одной транзакции создаются Case/Conversation/WI/payload/outbox/initial-термин владения как в 2-4 И initial-терм режима (scope=conversation, version 1, mode `unclassified`, origin `ingest_initial`); карточка показывает badge «не классифицирован» текстом; продажные ответы невозможны (эффективный режим несбытовой) (AC-5).
- Given валидное предложение режима (словарь, rank выше активного, expected_version совпадает, reason, signal_source, turn_ref при turn_event), when propose_mode исполняется, then append-only терм version+1 с prior_mode/rule_version/actor; той же транзакцией outbox `case.mode_changed`; badge/панель/таймлайн обновлены; replay команды — исходный исход (AC-4).
- Given предложение режима rank НИЖЕ или РАВНО активному диалога, when propose_mode исполняется, then честный отказ (`mode_not_downgradable`/`mode_active`) с текущим mode/reason/signal_source/version; записи нет; никакой surface (UI/API/будущая автономия) не может понизить (AC-4/7).
- Given два предложения одновременно с одной исходной версией, when обе команды исполняются, then ровно один терм version+1; проигравший — честный 409 с текущим режимом, безопасное перечитывание; replay любой — исходный исход (AC-10).
- Given активный запретный режим и клиентский turn без прежнего сигнала, when предложения нет, then терма нет: система не возвращается в `sales` по отсутствию повторения; выход — только явный exit_mode (AC-7).
- Given явный выход уполномоченным (configuration для `safety`; владелец с review либо configuration для остальных) с причиной, when exit_mode исполняется, then терм понижения с origin `exit_override`, authority, reason; продажи открываются, если эффективный режим WI стал `sales`; рядовой оператор на `safety` — честный отказ полномочия (AC-9).
- Given WI-1 имеет собственный терм контекста `cancellation` (scope=work_item), а режим диалога `sales`, when формируется ответ WI-1/WI-2, then эффективный WI-1 = cancellation (строгий), продажный ответ WI-1 — отказ режима; WI-2 (без терма) — эффективный sales, продажный разрешён по явному правилу mode-policy-v1 (AC-8).
- Given оператор-владелец отправляет ответ reply_class=sales при эффективном `sales`, when send_client_reply исполняется (после гейта владения 2-4), then гейт раскрытия: без действующей записи (conversation, channel) со статусом ∈ {sent, playback_*} — машинночитаемый отказ с permitted_path=record_disclosure; с действующей — prepared-запись как в 2-4 (AC-1).
- Given reply_class=protected_request, when send_client_reply исполняется, then требуется действующее раскрытие (AC-1); класс защищённого запроса размечен продюсером — машина контент не разбирает.
- Given record_disclosure (conversation, channel, текст ≤2000, lineage, parent_ref для повторного), when команда исполняется, then append-only запись + delivery-событие `generated`; затем record_disclosure_event `sent` → раскрытие действует для канала; текст виден в панели и таймлайне, доступен для повторного чтения (AC-1/11).
- Given delivery-событие `interrupted` (перебывание до завершения раскрытия, фиксирует команда — живой сигнал AG-4), when гейт раскрытия читает производную, then последняя запись погашена (последнее событие — interrupted); продажный ответ — отказ; повторное раскрытие (parent_ref) + `sent` — действует (AC-2).
- Given запись раскрытия со статусом playback_acknowledged либо playback_estimated, when гейт оценивает, then статус НЕ считается доказательством, что клиент услышал/понял; гейту достаточно «отправлено»; требования customer-confirmed будущей policy — словарь есть, продюсера нет (AC-2).
- Given исходящий первый контакт проверяется GuardOutboundBasis, when слова оснований (источник заявки, purpose, consent) неполны/отсутствуют, then fail-closed блокировка контакта (AC-3); полное синтетическое слово — юнит-доказательство положительной ветки (продюсеры — AG-4, в контуре недостижим).
- Given клиент оспаривает основание контакта (реплика — сигнал), when оператор фиксирует propose_mode `privacy_no_contact` с turn_ref, then Policy поднимает режим, продажные ответы останавливаются немедленно (AC-6/FR-15); текст отказа не маркетинговый (словарь).
- Given смена режима к приоритетному, when RR — человек, then панель показывает mode, причину, источник сигнала, rule_version и запрещённые следующие действия; смена видна в таймлайне; aria-live объявляет без перемещения focus (AC-6/9/11).
- Given повторный turn/policy event с тем же идемпотентным ключом и тем же материалом, when команда приходит повторно, then второй переход не создаётся (replay исхода); тот же ключ с иным материалом — конфликт ключа (AC-10).
- Given пользователь другого Tenant, when запрашивает режим/раскрытия/формы, then RLS и серверная авторизация: 404 без раскрытия Tenant (AC — регресс 2-1).
- Given карточка с клавиатуры/screen reader/увеличенным текстом/320 px, when оператор работает, then режим, AI-role, причина, delivery-статус и текст раскрытия доступны текстом; unclassified и sales различимы; повторное чтение раскрытия доступно; динамическая смена режима — без неожиданного перемещения focus (AC-11).

## Implementation Notes

- Идемпотентность — единый механизм 2-2/2-3/2-4: command_records до стражей, request-hash включает весь материал (вкл. expected_mode_version — урок m-r2-1 2-4: разный материал под тем же ключом = честный ErrCommandKeyConflict, не replay); advisory-лок кейса — сортированный lock-план.
- Ingest: ровно один дополнительный INSERT (initial-терм unclassified) в существующей транзакции приёма; лестница/словари/порядок ступеней 2-1 не меняются; initial-термин владения 2-4 не трогается; тесты 2-1/2-4 остаются зелёными без правок.
- Порядок гейтов send_client_reply: гейт владения 2-4 (владелец/epoch/surface/health/governing) → гейт режима (reply_class против эффективного режима WI) → гейт раскрытия (sales/protected: действующая запись канала) → CAS/запись; не-владелец сначала узнаёт владельца (прецедент «гейт раньше CAS» 2-4); stale-семантика drain 2-4 сохраняется (reply_class пишется в prepared-запись — будущий drain наследует).
- Модель не может понизить: GuardProposeMode отказывает rank ≤ активному (и равный — `mode_active`); выход — только exit_mode; authority-лестница: safety — configuration (supervisor); остальные — текущий владелец с review либо configuration; platform safety оператором не ослабляется (AC-9).
- Delivery-события пишет команда `record_disclosure_event` (оператор/будущий адаптер): живых playback/barge-in сигналов в контуре нет — честная граница AG-4; «interrupted» фиксируется командой после наблюдения (демо/будущий media edge); TTS-аудио — исходящие диалоги.
- reply_class размечает продюсер (форма required без дефолта — урок фикстур 2-3; машина контент не классифицирует — честная граница; будущие автономные поверхности проходят те же гейты).
- GuardOutboundBasis — доменная функция над синтетическими словами оснований (partner source/purpose/consent): fail-closed; положительная ветка — юнит-синтетика (прецедент GuardExternalSurface 2-4); продюсеры слов — AG-4.
- Outbox: 2 новых типа событий v1 (`case.mode_changed`, `case.disclosure_recorded`), канонический JSON + dedup key по прецеденту 2-1; доставка — DrainOutbox без изменений.
- Фикстура journeys: мир 2-4 + сигнал классификации + раскрытие + safety-подъём + exit + per-WI + interrupted/re-disclosure (паттерн cases_fixture/cases_ownership_fixture).
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...` (UTC + TZ=Europe/Moscow), `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`; регресс 2-1/2-2/2-3/2-4 зелёный обязательно.
