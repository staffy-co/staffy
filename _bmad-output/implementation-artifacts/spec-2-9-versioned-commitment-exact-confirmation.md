## Intent

**Problem:** Commitment не существует как объект системы: нет ни таблицы, ни команды, ни словаря — «стабильный идентификатор и неизменяемая версия» (AC-1) нечем исполнить, а «черновик не считается подтверждаемым обязательством» (AC-1) нечему нести. Материальные условия не имеют типизированной структуры: «scope, позиции или услуга, цена либо диапазон, существенные неизвестные, payee, гарантийная роль, следующий шаг и последствия» (AC-2) живут нигде — показывать клиенту нечего, подтверждать нечего. Confirmation не существует: связка «точная версия Commitment, material snapshot и конечный action set» (AC-5) не обеспечена, content binding «keyed versioned HMAC» (AC-6) для материальных условий не построен (прецедент identifier keys 2-3 — для идентификаторов, не контента). Freshness-гейт заморожен 2-7: «версия становится доступной для Confirmation → система проверяет freshness и точные версии Observations» (AC-3) — не enforcement. Состояние Work Item `confirmed/ready_for_action` (AC-10) в лестнице 2-2 отсутствует — после «успешного подтверждения» WI не получает машинного шага. Отказ/изменение (AC-11) не сохраняются. Поверхности Commitment Review (AC-12) нет. Проверяемые последствия FR-25 (связь с конкретными scope/ценой/участниками/временем; однозначность подтверждения; новая версия при существенном изменении) не работают на сервере: контур материальных предложений не имеет скелета.

**Approach:** Первый срез — детерминированный серверный скелет версии → предъявления → точного подтверждения (прецедент 2-5…2-8: AI Runtime в контуре НЕТ; продюсер размечает, машина гейтит; срез — modality text/web). Пять частей: (1) словари Domain Pack v0 + типизированные материальные условия: статусы версии {draft, offered}; обязательные термины {scope, service_items, price, payee, warranty_role, next_step, consequences} + action_set (словарь слов действий, 1..4) + valid_until + consumption_limit (1..10); цена — amount либо range в центах; material_unknowns — список слов терминов: неизвестный ОБЯЗАТЕЛЬНЫЙ термин делает offered-версию непредъявляемой к подтверждению (readiness — read-time деривация, AC-2 честность «неизвестный обязательный факт блокирует готовность»); (2) append-only `cases.commitments`: стабильный commitment_id + монотонный version_no (новая версия = новая строка; текущая = max; прежние не mutatingся — AC-8 «создаётся новая версия»), каждая версия несёт полные условия, action_set, связи-пины (Work Item, Response Owner + epoch, lineage release-решения — employee/decision_no/profile_version, прецедент lineageWord 2-4; текущий Policy Outcome 2-6; пины наблюдений observation_no для observation-backed терминов) и content-токен; команда create_commitment (оператор review, гейт скоупа ДО материальных стражей — прецедент M1 2-5/2-7/2-8) создаёт draft либо offered: offered с не-unknown ценой требует текущего ok+fresh наблюдения price WI с байтовым равенством канонических значений и отсутствием конфликта с подтверждённым фактом 2-2 ( badge ≠ differs — AC-3), пин observation_no; (3) предъявление = связанный client_reply: +2 nullable колонки (commitment_id, commitment_version — пара оба-или-ни один), только reply_class=sales (коммерческий материал проходит замороженную лестницу 2-4→2-5→2-6→2-8 байт-в-байт); версия подтверждаема только после существования предъявляющего reply этой точной версии (AC-6 «показанную версию»; связка через строку — прецедент policy_outcome_id 2-6 / objection_id 2-8); (4) команда confirm_commitment (оператор review; продюсер размечает ясное согласие клиента): evidence — принятый text-turn кейса + дословные span-выдержки слов подтверждения (побайтовое вхождение в payload — прецедент 2-8, выдуманное согласие невозможно); гейты по порядку: скоуп → участники → не-терминальный WI → версия существует и offered → readiness (обязательные термины не unknown, valid_until не прошла, версия текущая) → предъявление существует → evidence-валидность → freshness-гейт: текущее наблюдение price = пиннутая версия (observation_no), ok, fresh, байтовое равенство, без конфликта с фактом → authority-гейт (rule table v1): identity-уровень субъекта = verified (DeriveAssuranceState 2-3) И при цене > 0 — действующая authority-запись (mandate_note); отказ честный со словами step-up-лестницы 2-3 → append-only `cases.confirmations`: actor/subject (kind+ref), method=explicit_text, channel, timestamp, expiry (снимок valid_until), consumption state (0/limit), evidence reference, material_snapshot (канонические байты условий), action_set-снимок, content binding = HMAC-SHA256(per-tenant commitment key v1, канонические байты материального снимка) — ключ в `cases.commitment_hmac_keys` (32 байта, INSERT-only, ensure-паттерн identifier_hmac_keys 2-3; сырые хеши телефонов/VIN/адресов/короткого текста не появляются как класс, AC-6) → транзит Work Item in_work|waiting → confirmed (единственный шаг среза, AC-10; никакой внешней мутации, mutation-адаптеров в коде нет); повторная иная команда того же субъекта+версии → честный 409 duplicate; (5) отказ/изменение: команда record_commitment_decline (outcome {declined, change_requested}, evidence turn+spans) — append-only `cases.commitment_declines` без ухудшения скрытых условий (ничего не мутирует, AC-11); новая версия предложения = create_commitment с тем же commitment_id (version_no+1); прежняя Confirmation перестаёт действовать автоматически — DeriveConfirmationValidity (read-time): {valid, expired (valid_until прошла), superseded (есть версия новее), owner_stale (epoch кейса ≠ пин), release_stale (lineage ≠ пин), revoked/consumed — зарезервированные слова без продюсера в срезе (прецедент reserved 2-6: отменяющая команда — будущие срезы, потребление — Action Gateway Epic 3)}; «недействующая не восстанавливается повторной доставкой старого события» — replay возвращает исходную запись (command-ключ 2-1), действительность — только чтение текущего материала. Поверхность: страница Commitment Review + панель на карточке WI (версии/статусы/подтверждения/отказы/токен-присутствие), PRG-формы create/confirm/decline, a11y: текст, 320 px, confirm — единственное основное действие и не выбрано заранее (не autofocus), «изменилось» объявляется текстом с переводом фокуса к краткому описанию (AC-12).

**Решение владельца:** ожидает CHECKPOINT 1. Предъявление — нетехническим пересказом в ответе сессии (прецедент 2-6/2-7/2-8); работа Dev-фазы начинается только после явного одобрения владельца.

## Boundaries & Constraints

**Always:** append-only `cases.commitments` / `cases.confirmations` / `cases.commitment_declines` / `cases.commitment_hmac_keys` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; version_no — монотонный счётчик (commitment_id) под advisory-локами кейса+WI (прецедент policy_outcomes 2-6 / objections 2-8); идемпотентность: тот же command-ключ с тем же материалом → replay исходной записи (command_records 2-1, +3 слова словаря команд); тот же ключ с иным материалом → ErrCommandKeyConflict 409; статусы/исходы/методы/слова действий — словари CHECK; условия — канонические JSON-байты ≤4096 (детерминированная сериализация домена), цена — центы int64 (>0), диапазон min<max; action_set 1..4 слова словаря, consumption_limit 1..10, valid_until — будущее; material_unknowns — только слова обязательных терминов; spans evidence — ≤8, каждая ≤200 символов, каждая — побайтовая подстрока payload turn-источника (ReadPayload 2-1, прецедент 2-8), DB CHECK на длину массива — домен+app; content binding: HMAC-SHA256, key bytea CHECK octet_length=32, домен-сепарация «commitment:v1:» + commitment_id + version_no + material bytes (прецедент IdentifierToken), ключ v1, ротация честно отложена (прецедент identifier keys), токен char(64) hex; material_snapshot/action_set/пины — в строке, outbox-события (commitment_version_created, commitment_confirmed, commitment_declined) — метаданные (id, версия, статус, исход) БЕЗ материальных условий и без выдержек (прецедент «кандидат не покидает строку» 2-6/2-7/2-8); гейты команд: скоуп review ДО материальных стражей (403 словами скоупа, прецедент M1), не-участник → 404 ×пути, чужой tenant → RLS 404; turn-источник — принятый (accepted) event кейса, modality=text (голос → честный 400 словарём — AC-7 голосовой контур следующих срезов); терминальный WI → 400 work-rule (граница 2-2); переход WI → confirmed: только из in_work ИЛИ waiting (GuardTransition 2-2, лестница расширяется аддитивно: +слово confirmed +переходы in_work→confirmed, waiting→confirmed, confirmed→{resolved, cancelled} — существующие переходы и тесты не меняются, байт-в-байт); презентация: client_replies.commitment_id+commitment_version — nullable пара (CHECK оба NULL или оба NOT NULL), только sales-строки (иначе 400 словарём), версия обязана существовать и быть offered на момент отправки (draft/несуществующая → 400); подтверждение требует существования предъявляющего reply точной версии (связь через строку, без временнОго упорядочивания — честная граница среза: порядок обеспечивает существование строки, продюсер размечает верно); confirm: subject — (kind, ref) участник, UNIQUE (tenant, commitment_id, version_no, subject_kind, subject_ref) — второй субъект допустим отдельной строкой, повтор того же субъекта с иным ключом → 409 duplicate; authority-гейт: DeriveAssuranceState 2-3 (identity verified + при цене>0 — authority mandate_note действующая), отказ несёт слова step-up-лестницы (прецедент 2-3); freshness-гейт на confirm: текущее наблюдение price WI — observation_no == пину версии, статус ok, fresh (age ≤ freshness_seconds матрицы 2-7), значение байтово равно термину цены версии, конфликт с подтверждённым фактом 2-2 ≠ differs (AC-3 «stale или conflicting требует нового чтения либо решения человека» — перечитывание операторское 2-7, новая версия команды); DeriveConfirmationValidity — read-time, состояния нигде не мутируются (прецедент производных 2-6/2-7/2-8); панель/страница: a11y — aria-live=polite, 320 px без горизонтального скролла, статусы не отличимы только цветом, confirm-кнопка без autofocus/preselect, объявление изменения версии текстом + фокус к описанию (AC-12).

**Never:** не исполнять внешние действия и не строить Action Gateway/Operation/receipt (AC-10, FR-27/28 — Epic 3: в срезе WI получает ТОЛЬКО состояние confirmed; mutation-адаптеров и connector-вызовов в коде среза нет как класс — прямого вызова Connector нечем обойти); не строить голосовое подтверждение/readback/barge-in-repair (AC-7 — modality среза text; голосовой evidence честно 400 словарём); не строить авто-детекцию материальных изменений наблюдений и авто-версионирование (AC-8 «система формирует обновление» — в срезе новая версия операторской командой; материальная безопасность — freshness-гейт confirm fail-closed: изменилось/устарело → 400, новая версия обязательна); не строить ротацию/уничтожение HMAC-ключей (key v1; retention-политика — deferred, прецедент identifier keys 2-3); не строить каталог Allowed Actions (FR-27 — Epic 3: action-словарь v1 — фиксированные слова Domain Pack v0, исполнения нет); не строить клиентскую web-поверхность/protected continuation (AC-4 «клиент получает в текущем канале… повторно открыть» — канал доставки = связанный client_reply 2-4 (текст условий пишет продюсер, машина связывает точную версию), клиентский re-open — story 2-10; страница Review среза — операторская); не строить авто-связь отказа с бюджетом убеждения 2-8 (decline — lifecycle предложения, возражение — дисциплина убеждения: продюсер размечает раздельно; машины не сцепляются); не трогать гейты/лестницу/миграции 2-1…2-8 (кроме: +3 слова словаря команд, +3 outbox-типа, +2 nullable колонки client_replies (пара), +слово состояния confirmed в CHECK work_item_versions через ALTER новой миграции 00009 — прецедент расширения словаря command_records в 00008); не подтверждать из untriaged/терминальных состояний (лестница 2-2); не считать «интерес клиента» подтверждением (продюсер обязан размечать явное согласие с span-выдержками; AC-9 epic — граница 2-8 «commit/next-step машина» переходит сюда); не пинать release manifest целиком (lineage-слова employee/decision_no/profile_version — прецедент 2-4; полный digest-пин — с Operation-контуром Epic 3, deferred-work); не строить eval-набор commitment (с Release Manifest-контуром); не показывать материальные условия/выдержки в outbox/логах/исключениях.

## I/O & Edge-Case Matrix

- Given кейс с действующим WI (in_work) и оператор review, when create_commitment (offered: все обязательные термины, price amount, action_set {prepare_order}, valid_until +24ч, consumption_limit 1), then append-only строка версии №1 (version_no=1, статуса offered, пины owner/epoch+lineage+policy_outcome+observation price, content-токен), outbox-метаданные без условий; панель показывает версию (AC-1/2).
- Given create_commitment со статусом draft, then строка версии создаётся, но панель помечает «черновик — не подтверждаем»; send_client_reply со связью этой версии → 400 draft-not-presentable; confirm → 400 (AC-1 «черновик не считается подтверждаемым»).
- Given offered-версия с price в material_unknowns (неизвестный обязательный факт), when create, then строка создаётся (honest offered), readiness = не-подтверждаема: confirm → 400 mandatory-unknown словами (AC-2 «неизвестный обязательный факт блокирует готовность»).
- Given offered-версия использует цену, when create, then гейт: текущее наблюдение price WI должно быть ok+fresh+байтово равно термину цены+без конфликта с фактом 2-2; пин observation_no (AC-3).
- Given цена версии ≠ текущему наблюдению price (или наблюдение stale/failed/conflict), when create offered ИЛИ confirm, then честный 400 freshness/value-словарём — требуется новое чтение 2-7 либо новая версия (AC-3).
- Given повторная create_commitment с тем же commitment_id (новая версия после изменения условий), then version_no+1 append-only; прежние версии не мутируются; прежняя Confirmation автоматически superseded (деривация); панель объявляет «версия изменена» текстом (AC-8).
- Given offered-версия, when send_client_reply класс sales со связью (commitment_id, version), then проходит лестницу 2-4→2-5→2-6→2-8 байт-в-байт и несёт связь — предъявление зафиксировано (AC-4 машинная часть).
- Given нейтральный/защищённый reply со связью версии, when send, then 400 словарём — только sales-строки несут коммерческий материал.
- Given версия БЕЗ предъявляющего reply, when confirm, then 400 not-presented — подтверждается только показанная версия (AC-6).
- Given предъявление существует, evidence — принятый text-turn кейса с span-выдержками явного согласия (побайтово в payload), субъект с identity=verified и (цена>0) действующей authority-записью, наблюдение price = пину (ok+fresh+равенство+без конфликта), when confirm_commitment, then append-only confirmation (actor/subject/method/channel/timestamp/expiry=valid_until/consumption 0/limit, evidence ref, material_snapshot, action_set, content-токен HMAC), outbox-метаданные; WI → confirmed (единственный шаг, AC-5/6/10).
- Given span не является подстрокой payload turn-источника (выдуманное согласие), when confirm, then 400 span-not-in-source — выдуманное подтверждение невозможно (AC-6 однозначность).
- Given субъект без identity verified, when confirm, then 403/400 assurance-словарём со словами step-up-лестницы 2-3 (AC-5 «недостаточные полномочия предлагают безопасный step-up»).
- Given цена>0 и нет действующей authority-записи субъекта, when confirm, then честный отказ authority-словами (AC-5 authority соответствует риску).
- Given turn-источник голосовой/quarantined/чужой кейс, when confirm/decline, then 404 либо 400 модальностью (границы 2-1/2-8).
- Given повторная confirm-команда того же субъекта+версии с тем же command-ключом, then replay: исходная строка возвращена, новых строк/событий нет (идемпотентность 2-1).
- Given повторная confirm того же субъекта+версии с ИНЫМ ключом, then 409 duplicate — одно подтверждение субъекта на версию (fail-closed).
- Given та же команда с иным материалом, then ErrCommandKeyConflict 409 (прецедент 2-6/2-7/2-8).
- Given подтверждение существует, then changes owner epoch (новый ownership term) ИЛИ lineage-решение, then DeriveConfirmationValidity → owner_stale / release_stale: панель показывает недействующую; «отозвана/исчерпана» — зарезервированные слова без продюсера (AC-9 честность).
- Given valid_until прошла, then деривация expired — недействующая; новая Confirmation требует новой версии с новым valid_until (AC-9).
- Given клиент отклоняет (record_commitment_decline, outcome=declined, evidence turn+spans), then append-only строка отказа без мутаций; «изменение» (change_requested) → оператор создаёт версию №+1; прежнее подтверждение superseded автоматически (AC-11).
- Given WI в waiting, when confirm, then переход waiting→confirmed допустим (живые состояния); из untriaged/терминальных → 400 лестницей (граница 2-2).
- Given оператор audit-only, when create/confirm/decline, then 403 словами скоупа ДО стражей (прецедент M1); не-участник → 404 ×пути; другой Tenant → RLS 404 (регресс 2-1).

## Implementation Notes

- Rule-table v1 (Domain Pack v0): обязательные термины = {scope, service_items, price, payee, warranty_role, next_step, consequences}; observation-backed = {price} (связь с матрицей 2-7: price→catalog/price_quote/freshness 300s); authority-триггер = цена > 0 (amount либо range min > 0); слова действий v1 = {prepare_order, schedule_appointment, issue_document} — исполнение отсутствует как класс (Epic 3); метод подтверждения v1 = explicit_text.
- Material snapshot = канонические JSON-байты терминов версии (детерминированная сериализация: ключи в фиксированном порядке, центы int64, без пробелов); токен = HMAC-SHA256(key, «commitment:v1:»+commitment_id+»:»+version_no+»:»+material bytes) hex — ключ per-tenant 32 байта INSERT-only (ensure: SELECT → INSERT → SELECT, прецедент verification.go 354-374); сырые хеши материальных значений не появляются (AC-6).
- Предъявление — связка через client_replies (прецедент policy_outcome_id 2-6 / objection_id 2-8): пара колонок оба-NULL-или-оба-NOT-NULL; гейт отправки проверяет версию до записи; confirm-гейт проверяет существование предъявляющей строки точной версии. ВременнОе упорядочивание события-к-reply не строится (честная граница: порядок обеспечивает существование строки + продюсерская разметка; материальная безопасность — freshness+точная версия+subject-UNIQUE).
- Переход WI → confirmed: транзит в той же транзакции, что и confirmation-insert (материальная атомарность); reason=commitment_confirmed, ref=confirmation_id (insertWorkItemVersion — существующая механика 2-2); выходы confirmed→resolved/cancelled — существующие терминальные переходы сохраняются.
- DeriveConfirmationValidity — только чтение: expired (now > expires_at), superseded (max version_no > подтверждённая), owner_stale (текущий epoch ≠ пин), release_stale (текущая lineage ≠ пин), revoked/consumed — зарезервированные слова словаря без продюсера (отменяющая команда — будущие срезы; потребление — Action Gateway Epic 3; прецедент reserved mandatory_missing 2-6); replay старого события не восстанавливает действительность (деривация от текущего материала).
- Отказ (decline) не сцепляется с бюджетом убеждения 2-8: decline — lifecycle предложения (append-only строка, ничего не мутирует, «без ухудшения скрытых условий»); возражение/бюджет — операторская разметка 2-8 (продюсер размечает раздельно; машины независимы).
- Гейт freshness на confirm строже, чем на create: пиннутое observation_no должно оставаться ТЕКУЩИМ (перечитали — наблюдение новее — версия указывает на старое чтение → 400, требуется новая версия; fail-closed, прецедент CAS-дисциплины 2-2 stale-version).
- Контрольная ветка лестницы: все существующие переходы/тесты 2-2 остаются зелёными без правок тестов (аддитивность слова confirmed — как +1 колонка/слово прецедентов 2-6/2-8).
