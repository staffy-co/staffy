## Intent

**Problem:** Между «проверенным Action Preview» (3-4) и «исполнением» (3-6) отсутствует авторизационный контур (FR-28/FR-29, AC-блоки 1-12): нет артефакта Confirmation — человеческого согласия, связывающего ТОЧНУЮ версию preview, её digest, материальный snapshot и конечный action set, с собственными valid_until, revocation и границами потребления — «подтверждённое действие зарегистрировано ровно один раз» нечему гарантировать (AD-6: material change, expiry, revocation или exhausted consumption требуют новой Confirmation); нет повторной валидации авторизации живыми источниками (Tenant, Case, Work Item, Conversation Mode, Response Owner, owner epoch, control generation, Release Manifest, Entitlement, gates, capability evidence существуют по отдельности — 3-4 собирал их только для подготовки preview, при авторизации их некому сверить повторно, и блокировка нечем сделать не-расходующей Confirmation); нет последней read-only проверки Owning System перед созданием Authorized Action — изменившемуся материальному условию нечем требовать новую версию Preview и Confirmation; нет business-intent key — эквивалентная мутация из другого Case или повторного канала неstructuralно предотвращена, а чувствительные короткие значения (телефон/VIN) не защищены от сырого несолёного хэша (AD-10 запрещает); нет атомарной транзакции резервирования «потребление Confirmation + резервирование intent + неизменяемая Operation + начальная запись Operation Ledger + outbox record» (AD-6/AD-13) — повтор запроса, webhook или Confirmation сегодня создал бы второй бизнес-эффект (FR-29), rollback нечем оставить Confirmation непотреблённой, сетевой вызов нечем исключить из транзакции; нет различения replay (тот же ключ + тот же материал → возврат первоначальной Operation без второго потребления и без второго outbox) и conflict (тот же ключ + другой материал → отклонение с видимым исключением — FR-29 «конфликт ключа с иными данными блокируется и эскалируется»); параллельные Cases не делят единственную tenant+Owning-System reservation — проигравшему нечем вернуть существующий Operation reference; нет поверхности Operation с честным authorized/queued (не executed) и видимыми pinned action version, target, Confirmation, owner, release, idempotency reference — внешнему идентификатору и Action Receipt неоткуда НЕ выдумываться (3-6); нет зондов double-click/webhook-repeat/replay-job/parallel-cases/crash-before-after-commit/idempotency-conflict. Честное состояние контура: AI Runtime не существует (AG-4 — автор подтверждения человек; типизированная граница остаётся: вход authorize — только пины, уверенность модели не заменяет Confirmation структурно); реальных провайдеров нет (AG-4 — OwningSystemReader в production не подключён: последняя проверка материала fail-closed, авторизация в production честно невозможна, вертикаль закрывается synthetic-ридером тестового контура 3-4 reused); Connector write-путь не существует вообще (мутационные адаптеры — исключительная территория dispatch composition root 3-6; «ни один Connector не получает write» vacuously честен и пиннут счётчиком); dispatch worker/дренер outbox — 3-6 (запись operation.queued создаётся, никем не дренится — честные слова на поверхности); Action Receipt/reconciliation — 3-6/3-7; определение с ConsumptionRule=bounded числовой границы в 3-1 не несёт (слово словаря без носителя) — потребление bounded fail-closed честным словом, вертикаль потребления закрывается single_use/unlimited fixture-определениями; связка Preview↔Commitment 2-9 (действие исполняет обязательство) нигде не построена — AC-3 «новая версия Commitment/Preview» исполняется новой версией Preview + новой Confirmation (слово Commitment остаётся за будущими pack-срезами, честная граница). ## Implementation Notes

- Два ключа — ядро FR-29, они НЕ взаимозаменяемы: клиентский idempotency_key — идентичность ЗАПРОСА (контракт повторов: double-click/webhook/replay несут его снова; детерминированно НЕ выводится из материала — иначе conflict AC-8 невозможен); серверный business_intent_key — идентичность МУТАЦИИ (keyed HMAC: tenant, Owning System слово, action type, нормализованное намерение; UNIQUE reservation — эквивалентная мутация из другого Case не проходит). Ключи живут в разных пространствах (UNIQUE на operations против UNIQUE на reservations) — replay и cross-case-конфликт различимы структурно.
- «Тот же ключ + другой материал» в срезе: material_digest каноничен над ПИНАМИ запроса (preview версия + confirmation пин) — одна и та же пара пин даёт тот же digest (replay), другая версия Confirmation — другой digest (conflict). Вебхук-сценарий честен: повтор с прежним ключом после того, как пользователь пере-подтвердил новую версию, = 409 с видимым исключением — ровно AC-8.
- Потребление — append-only событие consumed ВНУТРИ транзакции ReserveOperation: consumed = счёт событий read-time; allowance-проверка повторной выборкой под advisory-замком (tenant, confirmation_id) — гонка двух авторизаций одной single_use Confirmation = вторая видит consumed=1 → exhausted честным словом, НЕ потребив; bounded fail-closed (числового носителя в 3-1 нет) — вертикаль потребления: single_use (sms fixture) и unlimited; слово зарезервировано будущим срезом.
- Step-up на confirm, НЕ на authorize: confirm — человеческий акт согласия (прецедент Approve 3-3); authorize — машинная поверхность повторов (webhook/retry/replay не могут повторить step-up — требование сломало бы идемпотентность replay). Согласие материализовано в Confirmation-строке и проверяется пином+состоянием на КАЖДОЙ авторизации; hijacked-сессия может сделать только то, на что человек уже согласился (single_use + точные пины) — граница задокументирована.
- Replay-проверка ПЕРВОЙ (до лестницы отвержений): Operation уже создана = успешная авторизация была = повтор уважает её независимо от текущего состояния Confirmation (первая авторизация уже потребила; replay не потребляет и не должен отвергаться «exhausted» — иначе double-click после успеха возвращал бы 409 вместо ссылки; порядок — часть контракта, пиннут unit-порядком и матрицей).
- DeriveOperationState ∈ {authorized} — очередь НЕ состояние, а факт наличия outbox записи (честные слова «в очереди на будущий dispatch»); executed/failed/unknown — словарь 3-6, выводы НЕ существуют (зонд: слово executed не выводится нигде — «не выдумываются» и про внешний идентификатор, и про статус).
- Operation Ledger — единственная запись authorized в срезе; AD-13 «Operation Ledger is append-only» материален грантами INSERT/SELECT; 3-6 допишет dispatch-записи тем же механизмом — схема готова (entry_no монотонный, safe-details ≤500, материал НИКОГДА).
- Outbox модуля action — собственная таблица (cross-module SQL запрещён AD-2 — cases.outbox_events чужой); payload SAFE: 3-6 worker перестроит материальный payload из неизменяемых строк Operation/preview (детерминизм из неизменяемости — прецедент BuildOutboundPayload 3-3); записи pending вечно в срезе — drain контур 3-6, страница говорит словами.
