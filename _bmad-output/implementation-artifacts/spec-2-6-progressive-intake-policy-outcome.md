## Intent

**Problem:** 2-5 выдал режимы разговора и AI-раскрытие, но «разрешённый Policy Outcome» (FR-22) не существует: предложения AI (intent, извлечённые факты, кандидат ответа, недостающие факты, следующие шаги) не принимает, не валидирует и не сохраняет никто — типизированной схемы и proposer-порта нет (AC-2). Детерминированной Policy нет: чем решается «этот коммерческий ответ разрешён, а эти вопросы — минимально необходимые» — нечему (AC-3). Продажный ответ сегодня проходит по режиму (2-5) и раскрытию (2-5) — но «Policy Outcome» как серверная истина не проверяется ничем: гейту нечего требовать (AC-1/3: AI Runtime получает разрешённый контекст и Policy возвращает допустимый ответ — контура нет). Прогрессирующий intake не существует: подтверждённые факты (2-2: DeriveFactStatus=confirmed с полным provenance) не препятствуют повторным вопросам — предлагается спросить подтверждённое, и предложение не встречает ни дедупа, ни переиспользования сохранённого значения (AC-6, FR-18: «минимальное число вопросов»). Воспроизводимость решения по входным версиям отсутствует: исход не сохраняется с якорями версий и не воспроизводится (AC-3). Fail-closed на неизвестное правило/интент срабатывать нечему — словаря интентов и правил нет (AC-3). Мульти-интентный turn: предложение не привязывается к Work Item, отдельного WI для нового намерения материал не порождает (AC-7). Оператор не видит предложение, исход, обязательные факты, переиспользованные значения и следующие шаги (панель отсутствует). Идемпотентность policy-событий и защита от гонок чтение-запись фактов не определены (AC-10 карты на 2-5 — тот же прецедент).

**Approach:** Первый срез строит механику предложений и Policy целиком на детерминированном сервере (прецедент лестницы режимов 2-5: AI Runtime в контуре НЕТ — честная граница), без изменений гейтов 2-4/2-5 (владение/режим/раскрытие стоят как стоят) и без автоматической записи фактов (запись фактов — команда 2-2, её Never «не создавать факты автоматически» неприкосновенна). (1) **Предложения (типизированная схема, proposer-порт):** append-only `ai_proposals` со словарём схем `ai-proposal-v1`: intent — ограниченная строка ≤64 (словарь интентов проверяет POLICY, не сабмит: «результат модели считается предложением, а не Policy Outcome» — неизвестный intent доходит до оценки и fail-closed'ится, а не отвергается на входе), candidate_answer ≤2000 (может быть пустым — базиса ответа нет), missing_facts [{material_key ≤64 (нормализация 2-2), reason ∈ {mandatory, readback}}], extracted_facts [{material_key, value_digest, source_event_id}] — притязания модели со source span на ПРИНЯТОЕ событие кейса (факты из них НЕ пишутся: extracted — только аудит притязаний; запись факта — операторская команда 2-2), turn_ref — принятое событие, proposer ∈ {synthetic_port, operator}, снимок входа на подаче (owner epoch 2-4, mode_version 2-5). Валидация подачи — только структура/границы/словарные слова → машинночитаемые 400 field-errors (честный край repair-pass: цикл повторов/бюджеты/таймауты — рантайм, границы среза; клиенту никогда не показывается stack trace или выдуманный результат). (2) **Policy Outcome (intake-policy-v1, детерминированная):** команда `evaluate_policy` несёт proposal_ref и якоря входных версий (expected_mode_version 2-5, expected_owner_epoch 2-4, expected_facts_digest — дайджест подтверждённого факт-набора кейса, expected_work_item_version 2-2); под advisory-локом читает предложение, факты (2-2), эффективный режим WI (2-5 производные), текущий WI (2-2) и чистая доменная функция EvaluatePolicy решает исход; append-only `policy_outcomes` с UNIQUE (tenant, work_item_id, outcome_no) — номер монотонный, действующий исход WI = последний номер, предыдущие НЕ удаляются и НЕ правятся (воспроизводимость). Словарь v1: intents {general_question, service_request, price_inquiry, booking_request, human_request} (коммерческие: service_request, price_inquiry, booking_request); классы исхода {commercial_answer, informational_answer, clarify, mode_blocked, fail_closed}; правило-таблица v1 обязательных фактов по интентам (фиксированный Domain Pack v0: general_question → [], human_request → [], service_request → [service_kind], price_inquiry → [service_kind, urgency], booking_request → [slot_preference]; богатые правила по реальным Domain Pack — 2-7+/Epic 5, честная граница). (3) **Дедуп вопросов (FR-18, AC-6):** исходное множество вопросов = правило-таблица[intent] ∪ proposal.missing(reason=mandatory); для каждого ключа: факт кейса подтверждён (DeriveFactStatus=confirmed, материал совпадает) И явной причины readback нет → вопрос УДАЛЯЕТСЯ, значение переиспользуется — reused_facts с provenance (fact_id, version_no, value_digest); статус conflicting → вопрос остаётся (конфликт — причина re-ask); unverified → остаётся (значение не подтверждено); явный readback → остаётся даже при подтверждении; удалённые повторы фиксируются suppressed_questions (аудит дедупа). Актуальность/свежесть — часов нет в срезе (2-7 Owning System/freshness): подтверждённый = актуальный, конфликт/readback — единственные причины повторного вопроса v1. (4) **Классы исхода:** intent ∉ словарю → `fail_closed` (reason unknown_intent, следующий шаг human_handoff — безопасный шаблон/передача, AC-3/4); коммерческий intent И эффективный режим WI ≠ sales → `mode_blocked` (слова режима + permitted_path=exit_mode — словарь 2-5); коммерческий, режим sales, candidate_answer пуст → `clarify` (базиса нет — только вопросы); коммерческий, режим sales, кандидат есть → `commercial_answer` (путь открыт, next_steps = ask_fact оставшихся + await_confirmation — прогрессивный ответ: краткий ответ теперь, минимальные вопросы рядом); некоммерческий → `informational_answer`. Разрешает продажный ответ ТОЛЬКО commercial_answer. (5) **Гейт продажного ответа (load-bearing):** send_client_reply reply_class=sales получает НОВЫЙ гейт ПОСЛЕ раскрытия (порядок: владение 2-4 → режим 2-5 → раскрытие 2-5 → политика 2-6 → CAS): требуется якорь Work Item (продажный путь WI-принадлежен — FR-65 мир 2-2) И действующий (последний outcome_no) исход WI = commercial_answer → иначе машинночитаемый отказ ReplyPolicyError (work_item_id, current_outcome {class, reason, rule_version, outcome_no}, permitted_path ∈ {anchor_work_item, submit_ai_proposal, evaluate_policy}); reply-запись +policy_outcome_id (nullable — до-миграционная честность, прецедент reply_class 2-5). Отказы 2-5 (режим/раскрытие) срабатывают РАНЬШЕ — их тесты не меняются; проходные продажные тесты 2-5 расширяются механически (+якорь WI + подача/оценка) с честной записью в Change Log (прецедент ReplyClass-neutral 18 вызовов 2-5→2-4). (6) **Воспроизводимость (AC-3):** каждый исход хранит input_snapshot {proposal_id, schema_version, mode_version, owner_epoch, facts_digest (карта material_key → {version_no, value_digest}), work_item_version, rule_version} и decision_digest — канонический SHA-256 над (входы + решение); та же пара (предложение, якоря) → тот же decision_digest (детерминизм: два evaluate с одинаковыми якорями и разными ключами → две записи, дайджесты равны, вторая supersede первой); факт изменился → expected_facts_digest не совпадает → честный конфликт с текущим дайджестом (перечитай и пересчитай; «гейт раньше CAS» прецедент 2-4). (7) **Идемпотентность:** обе команды через command_records (прецедент 2-2..2-5: replay исхода, отказ не отравляет ключ, request-hash со всем материалом ВКЛЮЧАЯ якоря — урок m-r2-1 2-4); advisory-лок case+conversation (прецедент 2-5). (8) **Мульти-интент (AC-7):** предложение WI-скоупно; порт подаёт отдельные предложения на каждый интент (сплит — рантайм, границы; оператор создаёт WI существующей командой 2-2); исходы WI-скоупны, текущий WI не теряется. (9) **Outbox:** case.ai_proposal_submitted v1 + case.policy_evaluated v1 (идентификаторы, словарные состояния, номера версий — без текста кандидата и PII); доставка DrainOutbox не меняется. (10) **Поверхность:** панель «Progressive Intake / Policy» карточки: предложение WI (intent, подавший, кандидат — виден оператору), действующий исход (класс, reason, rule_version, обязательные факты со статусами переиспользован-с-provenance/отсутствует, next_steps, suppressed-вопросы), история исходов (outcome_no), формы подачи/оценки PRG (flash-focus, required без молчаливых дефолтов, ≥44×44px, 320px), машинные JSON-контракты + problem-маппинг (400 схема / 409 стейл-якоря / 403 гейт) и aria-live исхода без перемещения фокуса (прецедент 2-5).

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 2-3/2-4/2-5): демо-путь — обращение (2-1: кейс/разговор/WI + initial-терм unclassified + initial-термин владения) → прелюдия 2-5: классификация sales + раскрытие + sent → 2-6: порт подаёт предложение WI-1 (intent price_inquiry, кандидат «Диагностика от …», missing [service_kind, urgency], extracted [(service_kind, span)]) — service_kind УЖЕ ПОДТВЕРЖДЁН (2-2: запись + подтверждение) → оценка (якоря) → исход v1 commercial_answer: вопрос service_kind УДАЛЁН (suppressed + reused с provenance), next_steps [ask_fact urgency, await_confirmation], reason ok_commercial, rule intake-policy-v1, input_snapshot, decision_digest → продажный ответ без якоря WI → отказ «продажный путь принадлежит Work Item» → с якорем, но без исхода → отказ policy_outcome_required (permitted_path) → с якорем + исход v1 → ПРОХОДИТ (владение → режим → раскрытие → политика) → оператор спрашивает urgency нейтральным классом (вопросы — нейтральные ответы 2-5) → факт urgency записан и подтверждён (2-2) → повторная оценка (новые якоря: facts_digest изменился) → исход v2 commercial_answer, вопросов нет, supersede v1 → продажный ответ со ссылкой на v1 → отказ «исход устарел» (слова текущего v2) → со ссылкой на v2 → проходит → порт подаёт предложение с intent «urgent_magic» (не в словаре) → оценка → исход fail_closed (unknown_intent, human_handoff) → продажный ответ → отказ (fail_closed не разрешает) → safety-сигнал (2-5) → оценка → исход mode_blocked (permitted_path=exit_mode) → воспроизводимость: повторная оценка с теми же якорями → новая запись с ТЕМ ЖЕ decision_digest (детерминизм) → дедуп-грани: conflicting-факт → вопрос остаётся; явный readback → вопрос остаётся при подтверждении → replay обеих команд идемпотентен, тот же ключ с другим материалом — конфликт → гонка: якорь фактов устарел под локом → честный стейл 409 → informational: WI-2 general_question → informational_answer, продажный ответ WI-2 отказан (не commercial) → RLS: чужой Tenant 404 → панель/формы/320px/aria-live. AI Runtime (вызовы модели, цикл repair-pass, бюджеты/таймауты), генерация текста ответа, barge-in/медиа-останов (AC-8/9), телеметрия/SLO (AC-10), modality-преференсы (AC-11 → 2-10), streaming/a11y-живых частичных ответов (AC-12 → 2-14), Owning System/свежесть (2-7), богатые Domain Pack правила P1–P6 (Epic 5) — честно за границей.

## Boundaries & Constraints

**Always:** Append-only: `ai_proposals`, `policy_outcomes` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, грантов UPDATE/DELETE нет; действующий исход WI — производная чтения (максимальный outcome_no), не хранимое состояние; исходы никогда не перезаписываются (supersede = новая строка с большим номером, предшественник читаем — воспроизводимость по входным версиям, AC-3). Монотонность: UNIQUE (tenant_id, work_item_id, outcome_no), INSERT под advisory-локами (case+conversation — прецедент 2-5; сортированный lock-план); гонки чтение-факты закрыты якорем expected_facts_digest (несовпадение под локом → честный стейл с текущим дайджестом — повторная оценка с новыми якорями; никаких молчаливых TOCTOU исходов). Идемпотентность — единый механизм 2-2..2-5: `cases.command_records` (UNIQUE tenant+actor+command+key; request-hash со всем материалом ВКЛЮЧАЯ якоря evaluate_policy — expected_mode_version/expected_owner_epoch/expected_facts_digest/expected_work_item_version; replay исхода до стражей; тот же ключ с иным материалом → ErrCommandKeyConflict), словарь команд +2: submit_ai_proposal, evaluate_policy. Гейт политики — расширение существующей send_client_reply (новой команды нет; порядок гейтов: владение 2-4 → режим 2-5 → раскрытие 2-5 → политика → CAS; гейты и семантика 2-4/2-5 не меняются, policy_outcome_id пишется в prepared-запись, stale-семантика drain 2-4 наследует). Словари фиксированы: schema ai-proposal-v1; intents {general_question, service_request, price_inquiry, booking_request, human_request}; commercial = {service_request, price_inquiry, booking_request}; классы {commercial_answer, informational_answer, clarify, mode_blocked, fail_closed}; reason-слова {ok_commercial, ok_informational, mandatory_missing, no_answer_basis, mode_blocks_commercial_path, unknown_intent}; шаги next_steps {ask_fact (с material_key), await_confirmation, human_handoff}; proposer {synthetic_port, operator}; rule_version intake-policy-v1; правило-таблица v1 (Domain Pack v0): general_question → [], human_request → [], service_request → [service_kind], price_inquiry → [service_kind, urgency], booking_request → [slot_preference] — материальные ключи проходят нормализацию 2-2 (NormalizeMaterialKey). Дедуп: переиспользование только подтверждённых точных версий (DeriveFactStatus=confirmed по кейсу, ключ совпадает); reused_facts несут fact_id, version_no, value_digest (provenance-ссылки 2-2); conflicting/unverified → вопрос остаётся; явный readback (reason в proposal) остаётся при подтверждении; suppressed_questions — аудит удалённых повторов; свежесть/TTL не выдумывается (2-7). Candidate answer ≤2000 — текст класса операционных записей кейса (прецедент reply 2-4/раскрытия 2-5); в exceptions/телеметрию/outbox-конверты — только идентификаторы, словарные состояния, версии и времена. Оценка на терминальном WI (resolved/merged 2-2) — честный отказ 400 (терминальный WI не оценивается; merged — оценивай целевой WI); evaluate_policy на чужом кейсе/разговоре — 404 без раскрытия существования (RLS). Полномочия команд: submit/evaluate — участники с review (права на входе, прецедент фикса M1 2-5: audit-only отказан честным текстом «review или configuration»; конфигурация тоже проходит); оператор и синтетический порт — одинаковые гейты (порт — будущий рантайм, те же правила). Транспорт: 2 команды — машинные JSON-контракты + PRG-формы; problem-маппинг: 400 (схема предложения/словарные слова полей) / 409 (стейл-якоря — поля текущих версий) / 403 (гейт продажного ответа: ReplyPolicyError со словами текущего исхода и permitted_path) / 404; OpenAPI синхронно: 2 пути + схемы (AIProposalRequest, PolicyOutcomeView, PolicyInputSnapshot) + расширение SendClientReplyRequest (policy_outcome_id — сервер выбирает действующий исход по якорю WI, запрос поле не несёт) + форму отказа; контракт-тест ассертит словари и required-дисциплину. UI: панель Progressive Intake/Policy текстом: класс/intent/reason/rule_version словами, обязательные факты со статусами (переиспользован — с provenance-подписью; отсутствует — вопрос), next_steps, suppressed-вопросы, история исходов outcome_no; aria-live обновления исхода без неожиданного перемещения фокуса; flash-focus после действия; цели ≥44×44 px; 320 px без горизонтального скролла; формы required без молчаливых дефолтов (урок 2-3). Privacy: новые таблицы — класс `case-operations` (чтение review/audit, команды review); TestPerimeterIntegrity синхронно заявляет обе. Регресс 2-1..2-5 обязан оставаться зелёным (build/vet/unit/интеграция обеих TZ/journeys/контракт/diff); файлы тестов прошлых срезов не правятся, КРОМЕ механических расширений: (а) проходные продажные вызовы 2-5 получают якорь WI + подачу/оценку предложения перед ответом; (б) фикстуры journeys — с честной записью в Change Log (прецедент ReplyClass).

**Never:** Не строить AI Runtime: вызовы модели, цикл repair-pass на сервере, cost/tool budgets, таймауты, авто-извлечение intent/фактов из реплик (продолжение дисциплины 2-2/2-5: предложения подаёт порт/оператор явной командой; цикл повторов при schema-invalid — обязанность подающего, сервер отвечает машинночитаемыми field-errors). Не генерировать текст ответа Staffy (кандидат — базис, продюсер текста — оператор/будущий рантайм; сервер разрешает путь и минимальность вопросов, не слова). Не классифицировать контент кандидата/вопросов машиной (гейты — словари и факт-статусы; ответ оператора размечает сам — прецедент reply_class). Не писать факты автоматически из предложений (extracted_facts — притязания с span, аудит; запись факта — только команда 2-2 с полным provenance; Never 2-2 неприкосновенна). Не выдумывать актуальность/свежесть/сроки (никаких TTL-полей и часов в решении: подтверждённый = актуальный в v1; конфликт и явный readback — единственные причины re-ask; Owning System/freshness — 2-7). Не ослаблять и не переставлять гейты 2-4/2-5 (политика — НОВЫЙ гейт ПОСЛЕ раскрытия; владение/epoch/surface/drain, режим/лестница/CAS-термы, раскрытие/delivery — не меняются ни строкой). Не разрешать продажный ответ классами informational_answer/clarify/mode_blocked/fail_closed (действующий исход обязан быть commercial_answer; informational — нейтральные ответы, clarify — вопросы, fail_closed — шаблон/handoff, mode_blocked — путь выхода 2-5). Не принимать продажный ответ без якоря WI (продажный путь WI-принадлежен; WI-less sales ответ — отказ со словами permitted_path). Не «чинить» исходы (UPDATE/DELETE policy_outcomes не существует; supersede — только новая строка; replay идемпотентен). ## I/O & Edge-Case Matrix

- Given принятое обращение (2-1) с initial-термами владения и режима, оператор классифицировал sales и записал действующее раскрытие (2-5), when порт подаёт валидное предложение WI (intent price_inquiry, кандидат, missing [service_kind, urgency], extracted [(service_kind, span)], turn_ref на принятое событие), then append-only ai_proposals со снимком входа (epoch, mode_version) + outbox case.ai_proposal_submitted; схема/границы/слова валидны (AC-2).
- Given предложение с service_kind УЖЕ подтверждён (2-2 confirmed) и явного readback нет, when evaluate_policy исполняется с совпавшими якорями, then исход v1 commercial_answer: вопрос service_kind удалён (suppressed_questions + reused_facts с fact_id/version_no/value_digest), next_steps [ask_fact urgency, await_confirmation], reason ok_commercial, rule_version, input_snapshot, decision_digest; действующий исход WI = v1 (AC-3/6, FR-18).
- Given продажный ответ (reply_class=sales) без якоря WI, when send_client_reply исполняется, then машинночитаемый отказ: продажный путь принадлежит Work Item, permitted_path=anchor_work_item; гейты 2-4/2-5 отработали раньше и не изменились (AC-1/3).
- Given продажный ответ с якорем WI без исходов, when send_client_reply исполняется, then отказ policy_outcome_required (permitted_path=submit_ai_proposal, evaluate_policy) — серверная истина «разрешённый Policy Outcome» (FR-22, AC-3).
- Given действующий исход commercial_answer, when продажный ответ с якорем WI исполняется, then проходит (владение → режим → раскрытие → политика → CAS), prepared-запись несёт policy_outcome_id (AC-1/3).
- Given факт urgency записан и подтверждён ПОСЛЕ исхода v1, when повторная оценка приходит со старым expected_facts_digest, then честный стейл-конфликт с текущим дайджестом (перечитай); с новыми якорями — исход v2 commercial_answer (вопросов нет), v1 остаётся читаемым, действующий = v2 (AC-3/6).
- Given продажный ответ ссылается на устаревший исход (действующий v2), when send_client_reply исполняется, then отказ со словами ТЕКУЩЕГО исхода (class/reason/rule_version/outcome_no) и permitted_path=evaluate_policy; replay ответа — исходный исход (AC-3/10).
- Given предложение с intent вне словаря («urgent_magic»), when evaluate_policy исполняется, then исход fail_closed (reason unknown_intent, next human_handoff); продажный ответ по нему — отказ; предложение сохранено (притязание — аудит) (AC-3/4).
- Given коммерческий intent при эффективном режиме WI ≠ sales (например safety), when оценка исполняется, then исход mode_blocked (permitted_path=exit_mode, слова режима 2-5); продажный ответ и так отказан гейтом режима РАНЬШЕ — порядок не меняется (AC-8-край среза: решение исхода, не медиа).
- Given коммерческий intent, режим sales, но candidate_answer пуст, when оценка исполняется, then исход clarify (no_answer_basis): только вопросы минимального множества (AC-5).
- Given факт в статусе conflicting ИЛИ явный readback в proposal, when дедуп исполняется, then вопрос ОСТАЁТСЯ (конфликт — причина re-ask; readback — явная необходимость); confirmed без причин — удаляется (AC-6).
- Given WI-2 (general_question) и действующий informational_answer, when продажный ответ WI-2 исполняется, then отказ (не commercial); нейтральный ответ WI-2 — разрешён правилом mode-policy-v1 2-5 (мульти-интент: исходы WI-скоупны, текущий WI не теряется, AC-7).
- Given оценка на терминальном WI (resolved/merged), when команда исполняется, then честный 400 work-rule (терминальный WI не оценивается; merged — целевой WI) (граница 2-2).
- Given повторные команды (тот же ключ, тот же материал), when replay исполняется, then исходный исход без новых записей; тот же ключ с иным материалом (якоря) — ErrCommandKeyConflict (AC-10).
- Given две оценки одновременно (гонка), when обе исполняются, then монотонные outcome_no под advisory-локом; стейл-якорь второго — честный конфликт с текущими версиями; ровно детерминированный порядок (AC-10).
- Given воспроизводимость: два evaluate с ОДИНАКОВЫМИ якорями (мир не изменился), when записи сравниваются, then decision_digest равен (детерминизм); любые изменившиеся входы меняют якорь → новый дайджест (AC-3).
- Given пользователь другого Tenant, when подаёт/оценивает/читает, then RLS + серверная авторизация: 404 без раскрытия существования (регресс 2-1).
- Given панель с клавиатуры/screen reader/320 px, when исход обновляется, then класс/reason/факты/статусы/next_steps доступны текстом; aria-live без неожиданного перемещения фокуса; формы required (a11y-срез панели, AC-12-край).
