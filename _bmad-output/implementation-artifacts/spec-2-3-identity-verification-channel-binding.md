## Intent

**Problem:** Epic 2 имеет вход 2-1/2-2 (Case + Conversation + Work Items + факты с provenance), но кейс ничего не знает о личности участника: любой позвонивший/написавший считается участником, уровней доверия нет, Case не показывает assurance level (FR-11, AC-1: «Case явно показывает текущий assurance level»; «отсутствие идентификации не превращается в подтверждённую личность» — сегодня нечего показывать и нечему не превращаться). Смена канала клиента всегда создаёт НОВЫЙ кейс: сквозное продолжение существует только в UX-дизайне, механики безопасного связывания нет (AC-8), ошибочного связывания и его отмены не существует как класса (AC-9). Совпадения идентификаторов между кейсами невидимы: нет candidate-записей, нет очереди человеческого ревью дублей, «модель не может самостоятельно объединить записи» (AC-6/7) — верно по отсутствию, но честного человеческого механизма тоже нет. Нет лестницы неудач: серии провалов проверок и рискованные повторные попытки не ограничиваются (AC-10). Доступ к проверочным поверхностям чужого Tenant — не определён (AC-11).

**Approach:** Первый срез строит механику проверки-связывания-дублей целиком на append-only-дисциплине (прецедент 2-1/2-2: история не редактируется), без единого изменения в ingest (регресс 2-1/2-2 неприкосновенен) и без FK-переносов разговоров (связывание — отдельная связь, «текущее» — производная чтения). (1) **Verification records:** операторская команда StartVerification — kind `identity|authority`, метод из словаря канала, provider-наблюдаемый код из словаря синтетического контура; домен валидирует словари, преобразует provider-код в канонический исход (`passed|failed|expired|cancelled|ambiguous` — AC-3 «provider-specific результат преобразуется в канонический verification outcome»), вычисляет assurance level по методу (`basic|verified`) и срок действия по методу; append-only строка хранит тип проверки, метод, исход, уровень, subject reference (handle сессии ≤64 + объявленное отображаемое имя ≤64), issuer (оператор), время, срок, evidence (событие кейса или нота ≤200); поля для кода/пароля/секрета НЕ СУЩЕСТВУЕТ ни в команде, ни в записи (AC-3 «не сохраняет одноразовый код, пароль, полный секрет»), код-методы требуют evidence-событие, нота не может быть чистым кодом. Assurance state — производная чтения: последний непросрошенный `passed` по kind; просроченная/отменённая запись не считается. (2) **Гейт:** единственный защищённый шаг среза — связывание каналов: требует identity ≥ `verified`; `on_behalf` требует непросроченную authority-запись со scope (AC-5: личность и полномочия проверяются раздельно, подтверждённая личность ≠ право); отказ честный, панель перечисляет допустимые методы канала (AC-2), публичный путь (WI/факты/таймлайн) не блокируется (AC-2 «недостаточный уровень блокирует только защищённый шаг»); тексты отказов генерические — не раскрывают, какой идентификатор не сошёлся (AC-4). (3) **Threshold:** ≥3 исходов `failed|ambiguous` на разговор в окне 1ч → производное состояние `step_up_required`: новые проверки и связывание блокируются, пересечение пишет operational exception `identity_step_up` (без секретов — AC-10), окно истекает само по времени (без UPDATE). (4) **Binding:** операторская команда BindChannel — целевой существующий кейс A/разговор X + связываемый разговор Y (новая сессия, уже созданная обычным ingest 2-1), method `consent_handoff` (явное согласие клиента продолжить в другом канале; purpose ≤200; evidence — событие X, где клиент согласился, или нота) или `duplicate_review` (решение ревьюера дубля); append-only `channel_bindings` связывает Y с X и кейсом A (метод, actor, purpose, on_behalf, subject handle связанной личности, session handle Y, время); активность = anti-join с append-only `binding_reversals` (отмена: UnlinkChannel — уполномоченный оператор, причина ≤200; история событий и доступов не трогается, последующие события сессии Y продолжают разговор Y по правилу продолжения 2-1 — «пересчитываются» производные вьюхи: кейс A показывает события Y пока связь активна, после отмены — не показывает, кейс B владеет Y всегда; AC-9). Клиентское подтверждение связи — детерминированный текстовый шаблон без внутренних идентификаторов (AC-8 «без раскрытия внутренних идентификаторов»), в срезе предъявляется оператору для озвучки/пересылки; реальная доставка в канал — исходящие диалоги (честно отложено). (5) **Duplicate candidates:** словарь идентификаторов фактов (`phone|email|order_number`); при записи факта с ключом из словаря (значение — JSON-строка) та же транзакция нормализует значение, вычисляет keyed-HMAC-токен (AD-10: сырые хэши телефонов/VIN запрещены; ключ тенанта в `identifier_hmac_keys`, INSERT-only, ротация отложена честно) и пишет `identifier_tokens`; совпадение токена с другим открытым кейсом → append-only `duplicate_candidates` (причина `exact_identifier`, уверенность правила `high`) + задача уполномоченному оператору: минимальные сведения — замаскированное значение (последние 2 символа нормализованного), номера кейсов, канал, причина; защищённое содержимое (payload/факты) в карточку ревью не входит (AC-6/7); решение (ResolveDuplicate: `same_client|separate`, evidence-нота ≤200) — append-only `duplicate_resolutions`, состояние кандидата = производная; `same_client` создаёт binding через method `duplicate_review` (решающий — actor) — до решения и при `separate` кейсы существуют раздельно; авто-объединения нет как класса. (6) **Поверхность:** панель assurance в карточке кейса (identity/authority уровни текстом, метод, issuer, subject, срок, состояние step_up с восстановимым focus), карточки дублей, формы проверки/связывания/отмены/решения с подтверждением переходов; доступность — прецедент 2-1/2-2: текст статусов, ошибки привязаны к полям, focus предсказуем (tabindex + DOMContentLoaded, прецедент flash-focus 2-2), цели ≥44×44 px, 320 px без горизонтального скролла.

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 2-1/2-2): демо-путь — звонок (2-1, кейс A, разговор X) → факты записаны, включая «телефон» (токен создан) → клиент звонит с нового номера → кейс B, разговор Y → оператор записывает факт «телефон» → тот же токен → кандидат дубля (точное совпадение, карточка с замаскированным номером, без защищённого содержимого) → оператор пытается связать сразу → честный отказ «личность не проверена» + панель перечисляет допустимые методы канала; работа с WI/фактами не блокируется → проверка знанием (basic) — панель показывает basic, связывание всё ещё требует verified → оператор фиксирует проверку перезвоном (provider ok → passed, срок 1ч) → панель verified → связывание Y→X/A (метод consent_handoff, клиент согласился) → таймлайн A показывает события Y в порядке received_at, кейс B помечен «linked out», оператору предъявлен текст подтверждения для клиента без внутренних идентификаторов → новое событие сессии Y приходит → attach к Y, видно в A, нового кейса нет → сценарий от имени: authority-запись (scope, срок 30 дней) отдельно от личности → связывание on_behalf требует её → сценарий неудач: две неудачи + третья → step_up_required + исключение identity_step_up, проверки и связывание блокированы, окно истекает по времени → сценарий отмены: ошибочное связывание отменено (append-only reversal), события Y остаются в истории B, вьюха A пересчиталась → решение дубля «разные клиенты» — кейсы раздельны, ревью закрыто, кандидат остаётся в истории → replay команд идемпотентен → конкурентные bind/unlink → честный 409 → RLS: чужой Tenant 404 → вся цепь на 320 px. Политика P1–P6 (2-6), реальные верификаторы (AG-4), AI-детекция дублей, реальные Customer Profiles (OQ-16) — вне среза честно.

## Boundaries & Constraints

**Always:** Append-only: `verification_records`, `channel_bindings`, `binding_reversals`, `identifier_tokens`, `identifier_hmac_keys`, `duplicate_candidates`, `duplicate_resolutions` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, грантов UPDATE/DELETE нет; активность связи и состояние кандидата — производные anti-join/наличия, не хранимые state-колонки. Идемпотентность команд — прецедент 2-2: `cases.command_records` (UNIQUE tenant+actor+command+key, request-hash, replay исхода до стражей), словарь команд расширяется `start_verification|bind_channel|unlink_channel|resolve_duplicate`. Канонический набор verification record обязателен: kind, method, outcome, assurance level, subject handle, issuer, issued_at, expires_at, evidence (kind+ref) — все записи одной формы (AC-3). Provider-код и канонический исход — словари домена; преобразование — код домена с юнит-покрытием каждого provider-кода; валидация метода по каналу разговора и kind (identity-методы для identity, mandate — для authority). Срок действия — словарь по методу (`knowledge_check` 24ч, `known_number_callback` 1ч, `known_address_reply` 1ч, `mandate_note` 30д); просроченная запись остаётся в истории, в assurance не считается. Threshold: окно 1ч, порог 3, считаются `failed|ambiguous`; пересечение пишет `identity_step_up` исключение той же транзакцией; телеметрия (исключение, DEVLOG-уроки, логи) не содержит значений идентификаторов и секретов. Гейт связывания: identity ≥ verified И (on_behalf → authority непросрочена со scope); отказ перечисляет допустимые методы канала; текст отказа генерический (какой шаг, какой уровень нужен, какие методы дают) — без значений идентификаторов и без подтверждения существования чужих записей. Binding: метод из словаря `consent_handoff|duplicate_review`; для `consent_handoff` обязательны purpose ≤200 и evidence (событие кейса A или нота ≤200); связываемый разговор Y обязан существовать и быть открытым в том же Tenant; у Y не должно быть активной связи (конкурентные попытки — детерминированные advisory-локи разговоров X и Y в сортированном порядке, прецедент lock-плана 2-2; проигравший — честный 409, материал не меняется); кейс A и разговор X открыты; события Y видны в единой вьюхе кейса A в порядке `received_at` (прецедент merge-порядка 2-2). Unlink: append-only `binding_reversals` (binding, actor, причина ≤200, время); после отмены события Y остаются в кейсе B, доступы/история не перезаписываются; повторная связь Y — новая строка binding (история связей видна). Duplicate: словарь идентификаторов `phone|email|order_number`; факты с ключом из словаря требуют значения-строки (честный отказ при не-строке — токенизация только для строк); нормализация: phone — только цифры, email/order_number — trim+lower; токен = HMAC-SHA256(ключ тенанта, kind+«:»+нормализованное), hex; ключ — 32 байта crypto/rand, INSERT-only, первый удар создаёт, ротация/уничтожение — deferred-work (AD-10 честно); поиск совпадения — только среди открытых кейсов того же Tenant, той же командой, в одной транзакции; кандидат один на пару (кейс, токен) — материальный ключ уникальности; карточка ревью показывает замаскированное значение (последние 2 символа нормализованного) + номера кейсов + канал + причину, никогда payload/факты; решение `same_client` обязано создать binding (метод duplicate_review) той же транзакцией — либо транзакция откатывается целиком. Privacy: новые таблицы — класс `case-operations` (чтение `review`/`audit`, управление командами — `review`, прецедент WI-метаданных 2-2); TestPerimeterIntegrity синхронно; не-участник Tenant — 404 без раскрытия существования. Транспорт: операторские формы PRG + машинный JSON-контракт, OpenAPI синхронно (пути команд, схемы VerificationRecord/Binding/DuplicateCandidate), контракт-тест ассертит словари. UI: панель assurance текстом (уровень/метод/срок/issuer/subject/state step_up), ошибки полей связаны с полями (label+aria), focus после шага/ошибки предсказуем (flash-focus прецедент), цели ≥44×44 px, 320 px без горизонтального скролла. Регресс 2-1/2-2 обязан оставаться зелёным (все cases-тесты, обе таймзоны, journeys 19/19): ingest не меняется ни строкой.

**Never:** Не хранить одноразовый код, пароль, секрет или «лишние идентификационные данные» — ни в записи, ни в исключении, ни в логе: команды не имеют полей для секрета (превентивно), нота не может быть чистым цифровым кодом (доменная валидация с честным отказом), код-методы требуют evidence-событие. Не превращать отсутствие идентификации в личность: assurance панель показывает «не проверено» без записи; subject handle — заявленная строка, не подтверждение. Не доверять caller id/display name как личности (FR-11: они — только заявленные handle). Не выдавать failed/ambiguous за passed; не считать просроченную/отменённую запись; не расширять assurance после записи (уровень фиксирован методом в момент записи). Не блокировать публичный путь недостаточным assurance (WI/факты/таймлайн доступны как в 2-2; полная политика — 2-6, не выдумывается). Не объединять кейсы/личности/записи автоматически (никакого merge по токену/имени/номеру — кандидат только задача человеку; авто-merge отсутствует как класс навсегда в этом контуре до отдельного решения владельца). Не показывать защищённое содержимое в карточке ревью дубля; не показывать полный идентификатор в ревью (только маска). Не переносить разговоры между кейсами FK-обновлением (связь — отдельная таблица; разговор Y всегда принадлежит кейсу B). Не обновлять/удалять строки историй (грантов нет; «текущее» — производная). Не раскрывать существование чужого Tenant/кейса/идентификатора (404/генерические тексты). Не выдумывать tenant-конфигурацию методов (словарь канала фиксирован; конфигурация на Tenant — после реальных верификаторов, честно отложено). Не строить AI-детекцию дублей (правила словаря — только). Не создавать cross-case Customer Profile (OQ-16). Не доставлять подтверждение клиенту в канал (нет исходящих; шаблон текста — оператору). Не выдумывать policy-outcome P1–P6 (2-6). Не писать значения идентификаторов в operational exceptions/телеметрию.

## I/O & Edge-Case Matrix

- Given кейс A (разговор X) без единой проверки, when оператор открывает карточку, then панель assurance показывает «личность: не проверена / полномочия: не требуются или не проверены» текстом; работа с WI/фактами/таймлайном доступна как в 2-2 (AC-1: обслуживание не блокируется).
- Given оператор пытается связать канал без проверки, when команда исполняется, then честный отказ «недостаточный уровень: требуется verified, разрешённые методы канала: …» (список методов словаря канала X); связывание не создаётся; публичный путь не тронут (AC-2).
- Given оператор фиксирует проверку знанием (knowledge_check, provider ok, evidence-событие, где клиент назвал детали заказа), when команда исполняется, then запись хранит полный канонический набор (kind identity, метод, passed, basic, subject handle, issuer-оператор, время, срок 24ч, evidence); панель показывает basic; связывание всё ещё отказано (требуется verified) с перечислением step-up методов (лестница уровней честна).
- Given оператор фиксирует проверку перезвоном (known_number_callback, provider ok, нота «перезвонил на номер из факта, абонент подтвердил»), when команда исполняется, then passed/verified/срок 1ч; повтор команды с тем же ключом — replay исхода без второй записи (идемпотентность).
- Given проверка с provider-кодом no_match, when исполняется, then канонический failed; assurance не растёт; оператору предъявлены варианты словаря (повторить разрешённым способом / продолжить без защищённых данных / обратиться к человеку) — тексты генерические, без значений идентификаторов (AC-4);WI/факты доступны.
- Given две записи failed в течение часа, when приходит третья failed, then записывается третья, состояние step_up_required (производная окна), той же транзакцией пишется исключение identity_step_up (без секретов и значений идентификаторов); последующие StartVerification и BindChannel честно отказываются; WI/факты/таймлайн доступны; когда самая старая failed выходит из окна 1ч (детерминированный тест с часами), состояние спадает, попытки снова возможны (AC-10).
- Given verification passed валидна, when оператор связывает Y→X/A (consent_handoff, purpose, evidence-событие согласия), then binding активна (anti-join пуст); таймлайн кейса A показывает события X и Y в порядке received_at; кейс B показывает «разговор связан с кейсом A»; оператору предъявлен шаблон подтверждения для клиента без внутренних идентификаторов (AC-8); повтор команды — replay.
- Given binding активна, when приходит новое событие сессии Y, then оно attach к разговору Y по правилу продолжения 2-1 (ingest не меняется), видно в единой вьюхе A; нового кейса не создаётся.
- Given ошибочное связывание, when уполномоченный оператор отменяет (причина), then пишется binding_reversal; события Y остаются в кейсе B и истории; вьюха A больше не показывает события Y (пересчёт производной); повторная связь — новая строка binding; replay отмены идемпотентен (AC-9).
- Given клиент действует от имени организации (on_behalf), when оператор фиксирует authority (mandate_note, scope «заказы компании N», срок 30д) И identity verified, then связывание on_behalf проходит; панель показывает authority со scope и сроком отдельно от identity (AC-5); identity verified без authority записи при on_behalf — честный отказ (подтверждённая личность ≠ полномочие).
- Given authority просрочена (тест часами), when связывание on_behalf, then честный отказ; запись остаётся в истории.
- Given факт «телефон» записан в кейсах A и B с одинаковым нормализованным значением, when вторая запись исполняется, then токены совпали (HMAC того же ключа), создан candidate (причина exact_identifier, уверенность high, кейсы A/B, замаскированное значение — последние 2 символа); карточка ревью не содержит payload/фактов; кейсы раздельны; replay факта не создаёт второго кандидата (материальная уникальность пары кейс+токен).
- Given ревьюер решает same_client (evidence-нота), when команда исполняется, then пишется resolution И binding Y_B→X_A (метод duplicate_review, actor=решающий) одной транзакцией; ревью закрыто (производная); единая вьюха A включает Y_B (AC-7 исход-линк).
- Given ревьюер решает separate, when исполняется, then пишется resolution; кейсы остаются раздельными; кандидат остаётся в истории со статусом решения (производная); никакого merge не происходит.
- Given факт с ключом «телефон», но значением-объектом или не-строкой, when команда факта исполняется, then факт записывается как обычный факт 2-2, токенизация не выполняется (честная граница словаря); отдельного отказа нет (токенизация — надстройка, не блокатор).
- Given две конкурентные команды bind одного Y (разные операторы), when исполняются, then детерминированные advisory-локи X,Y сериализуют; ровно одна связь создаётся, вторая — честный 409; replay любой из них — исходный исход (материал консистентен).
- Given конкурентные verification-записи одного разговора, when исполняются, then обе пишутся (append-only безопасен), threshold-производная детерминирована (интерливинг-независимый подсчёт окна).
- Given пользователь другого Tenant или без права review, when читает верификации/кандидаты/связи или шлёт команды, then RLS и серверная авторизация блокируют (404 без раскрытия существования / 403); ответ не подтверждает существование чужого профиля, кейса или идентификатора (AC-11).
- Given проверочные поверхности на клавиатуре/screen reader/320 px, when оператор работает, then assurance/authority/сроки/ограничения текстом, ошибки связаны с полями, focus предсказуем после step-up-отказа и действий, горизонтального скролла нет, цели ≥44×44 px (AC-12).

- Given участник проходит проверку, when исход записывается, then тип/метод/уровень/subject/issuer/время/срок/evidence сохранены; код/пароль/секрет не сохраняются нигде; provider-код преобразован в канонический исход.
- Given проверка не пройдена/истекла/отменена/неоднозначна, when защищённый запрос повторяется, then доступ не предоставляется; предложены повтор/продолжение без защищённых данных/человек; причина не раскрывает сведения для подбора чужой личности.
- Given человек действует от имени другого, when требуется authority, then личность и полномочия проверяются раздельно; подтверждённая личность не даёт право; authority имеет scope и срок.
- Given разрешённые нормализованные идентификаторы указывают на возможный существующий кейс, when система ищет дубли, then создаётся candidate с причиной и уверенностью правила; защищённое содержимое не показывается до достаточной проверки; модель не объединяет записи сама.
- Given несколько возможных совпадений, when автоматическое связывание небезопасно, then создаётся задача уполномоченному человеку с минимальными сведениями; до решения обращение существует отдельно.
- Given подтверждены личность/полномочия/purpose и явное согласие, when участник продолжает в другом канале, then новая session связывается с существующими Conversation и Case; method/actor/purpose/время/linked identifiers сохранены; клиенту предъявлено подтверждение без внутренних идентификаторов.
- Given ошибочно связанный канал, when уполномоченный человек отменяет, then auditable unlink/correction; исходные события и история доступов не уничтожаются; доступные факты/вьюхи/permissions пересчитываются для последующих операций.
- Given серия неудачных проверок, when достигнут порог, then rate limit/step-up/human review применяются; защищённые данные не раскрываются; событие регистрируется без проверочных секретов.
- Given пользователь другого Tenant/неподходящей роли, when ищет/связывает/разъединяет дубли, then RLS и серверная авторизация блокируют; ответ не подтверждает существование чужого профиля/кейса/идентификатора.
- Given verification и duplicate-review интерфейс, when клавиатура/screen reader/320 px, then assurance/authority/сроки/ограничения текстом; формы не полагаются только на голос/изображение; ошибки связаны с полями; step-up сохраняет и восстанавливает focus предсказуемо.

## Implementation Notes

- Идемпотентность — единый механизм 2-2: command_records до стражей, replay исхода; advisory-локи — сортированный lock-план (прецедент ExecuteWork).
- Ingest 2-1 не меняется ни строкой: связывание влияет только на производные чтения; событие сессии Y продолжает находить разговор Y по session key — единство вьюхи кейса A через JOIN активных binding.
- HMAC-токены: ключ тенанта INSERT-only при первом ударе; ротация/уничтожение по retention — deferred-work (AD-10); нормализация словаря — детерминированные правила, юнит-покрытие каждой пары (вход → нормализованное → токен стабильный).
- Provider→canonical: словарь `ok|no_match|expired|cancelled|unclear` → `passed|failed|expired|cancelled|ambiguous`; адаптер verificationsyn — eligibility + пропуск кода; реальные верификаторы подставят код из provider API (AG-4) без изменения домена.
- Нота-evidence: домен отклоняет чистые цифровые коды как note (≥3 символа без пробелов и букв) с честной ошибкой — превентивная защита от случайного сохранения кода (юнит + интеграция).
- Threshold-окно: производная `COUNT(failed|ambiguous) WHERE conversation=X AND issued_at > now-1h ≥ 3`; часы — порт Clock (детерминированные тесты входа/выхода окна, прецедент voice-retention).
- Маска ревью: последние 2 символа нормализованного значения + kind; полные значения доступны оператору только через обычные поверхности фактов по праву review (не в карточке ревью).
- Фикстура journeys: мир 2-1/2-2 + два канала (звонок + второй звонок с нового номера) + проверка + связывание + дубль + панель на 320 px (паттерн cases_fixture).
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...` (UTC + TZ=Europe/Moscow), `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`; регресс 2-1/2-2 зелёный обязательно.
