## Intent

**Problem:** Между закрытой классификацией запроса детали 4-3 (PartRequestDigest — «точная версия запроса», контуры 4-4..4-9 обязаны пиннить) и будущими предложениями 4-5 применимость НЕ существует как объект: совпадение номера закреплено Constant-словом «не доказательство» (4-3), но самого доказательства нет вовсе — менеджер исследует каталог в фактическом интерфейсе ABCP/Laximo (маршрут parts_catalog_abcp НЕ допущен реестром 4-1: OQ-5/AG-4 open, AdapterImplemented false), результат исследования нигде не записывается и не трассируется (FR-52: «основание подбора сохраняется для менеджерской проверки и аудита»), задача менеджеру не создаётся (AC-7: действие только в интерфейсе менеджера → decision-ready задача), статусы применимости {proven, ambiguous, conflicted, unknown, stale} не выводятся, несколько модификаций и противоречие источников не передаются человеку (AC-5/AC-9), изменение версий входов (Vehicle Profile / Part Request) не помечает зависимые результаты устаревшими (AC-11), а позиция без доказательства неотличима от подтверждённо подходящей (AC-6/AC-12). Domain Policy применимости (типы связей, глубина cross-цепочки, источники, допустимый возраст) нигде не объявлена версионированно — риск зашить словарь магазина в код ядра.

**Approach:** Модуль internal/cases — применимость есть ВЫВОД над записанным материалом менеджерского каталогического исследования: спека добавляет FitmentPolicy в Domain Pack auto-parts@5.0.0 (типы связей + глубина + источники + TTL — приходит в cases через существующий структурный порт PackTaxonomy +1 метод PackFitmentSchema по прецедентам PackIdentificationSchema/PackPartRequestSchema), результат исследования записывается новой append-only таблицей 00020_fitment_evidences (материальные поля AC-2 + пины ProfileDigest/PartRequestDigest — точные версии входов AC-1/AC-11; прецеденты append-only столов 00007/00013), домен fit.go выводит состояния read-time (GuardFitmentEvidence со словарями пака + DeriveFitment — лестница состояний с честными словами и FitmentDigest). Менеджерский путь: панель рекомендует слово fitment_research — задача менеджеру идёт СУЩЕСТВУЮЩЕЙ машиной 2-13 (словарь причин +1 слово, SQL-зеркало 00021 по прецеденту 00019) с материалом 2-14; результат менеджер фиксирует новой командой записи (PRG-форма на странице кейса + JSON API по прецеденту операторских маршрутов записи). Поверхность — панель «Применимость» после панели «Запрос детали» 4-3.

**Ядро честности среза:** автоматического запроса к каталогу НЕТ и НЕ заявляется — маршрут parts_catalog_abcp НЕ допущен (OQ-5 safe state: «без inferred fitment/UI-scraping; человеческая задача либо лицензированный переиспользуемый каталог-коннектор»; AG-4: без реальных credentials); продюсер доказательства — оператор-менеджер, записывающий результат фактического исследования с полным материалом записи (источник, идентификатор записи, версия, время — трассируемость до ответа Owning System по дисциплине 2-7). Позиция называется подходящей ТОЛЬКО в состоянии proven; совпадение номера ≠ применимость (Constant 4-3 reused); LLM-сходство, RAG и память прошлого разговора — НЕ доказательство (FR-52), cross-reference — единственный разрешённый тип связи аналога, цепочка сохраняется ЦЕЛИКОМ, глубина и источники ограничены паком (AC-4). Отсутствие доказательства НЕ преобразуется ни в отрицательную, ни в положительную применимость (unknown — честное слово, AC-10); наиболее вероятная модификация НЕ выбирается (ambiguous → вопрос/handoff, AC-5); противоречие источников → conflicted + человек с ОБЕИМИ доказательствами (AC-9); любое изменение версий входов (дайджесты 4-2/4-3) устаревает зависимые доказательства read-time (AC-11). Менеджерское решение — scope ОДНОГО кейса с пинами точных версий входов (AC-8): НЕ универсальное правило для других автомобилей или Tenant — структурно (запись привязана к work item кейса). Молчаливых исправлений НЕТ ни в одном пути: guard-проверки отказывают словами со словарём, слова вне словарей невозможны (compile-time словари домена + SQL-CHECK + контракт-тест зеркал).

## I/O & Edge-Case Matrix

- Given кейс с пином auto-parts@5.0.0, подтверждённым профилем (ProfileDigest D_v, 4-2) и запросом exact_repeat (PartRequestDigest D_p, 4-3), записи доказательства НЕТ, when панель «Применимость», then статус unknown с честным словом «применимость не проверена — доказательства нет; отсутствие доказательства не является ни подтверждением, ни отрицанием» + Constant-слово 4-3 «точное совпадение номера не считается доказательством применимости» + рекомендация слова fitment_research; идемпотентность: повторная деривация — байт-стабильный JSON, записей НЕТ.
- Given оператор создал Human Handoff со словом fitment_research по рекомендации панели, when создание, then слово в словаре 00021 (SQL-зеркало), задача в подтверждённом Inbox существующей машиной 2-13/2-4, карточка decision-ready 2-14 (профиль 4-2 + запрос 4-3 + дайджесты + отсутствие доказательства словом + рекомендуемый следующий шаг «записать результат исследования каталога»), клиенту — существующие слова текущего owner и ожидаемого обновления 2-13/2-16.
- Given менеджер записал доказательство (позиция: узел «Фильтр салона» + артикул WF2B196K666AA; link_type original; catalog_vehicle_ids [ABCP-12345]; источник abcp_catalog с идентификатором записи, версией и временем; пины D_v/D_p актуальны), when запись + DeriveFitment, then состояние proven, FitmentDigest 64 hex байт-стабильный, панель показывает позицию «подтверждённо подходит» со словом, материалом источника записи и версией доказательства; age ≤ TTL.
- Given доказательство аналога (link_type cross, цепочка [оригинальная позиция → кросс-запись источника → аналог] глубиной 2), when запись + деривация, then цепочка показана ЦЕЛИКОМ (AC-4), FitmentDigest пиннит цепочку; исходная позиция, оригинал и аналог различаются типом связи и местом в цепочке (AC-12).
- Given цепочка глубиной 4 при MaxCrossDepth 3 пака, when команда записи, then отказ ДО SQL честным словом «слишком длинная cross-цепочка: глубина 4 превышает разрешённые 3 — Domain Policy пака» (AC-13 eval-ряд «слишком длинная цепочка»).
- Given менеджер записал не-найдено (источник abcp_catalog исследован, идентификатор автомобиля каталога отсутствует), when деривация, then unknown с честным словом «источник исследован, доказательство не найдено» — НЕ «неприменимо»; позиция НЕ в списке подтверждённо подходящих.
- Given не-найдено от abcp_catalog И найдено от laximo_catalog на ту же позицию (текущие записи обоих источников), when деривация, then conflicted: позиция НЕ предлагается подходящей, панель показывает ОБА доказательства материалом записей, рекомендация Human Handoff существующим словом unresolved_contradiction (4-3), человеку передаются оба доказательства с источниками и версиями (AC-9).
- Given найдено с catalog_vehicle_ids [V1, V2] (несколько модификаций), when деривация, then ambiguous: наиболее вероятная модификация НЕ выбирается, минимальный вопрос недостающего признака профиля (например vehicle.trim 4-2) либо Human Handoff (AC-5); подтверждённые признаки НЕ переспрашиваются.
- Given подтверждённый part-факт получил новую версию (PartRequestDigest изменился на D_p'), when деривация, then ВСЕ записи с пином D_p → stale «доказательство относилось к прежней версии запроса» + слово «перед новым предложением выполняется повторная каталогическая проверка»; новая запись с пином D_p' → proven снова (AC-11).
