## Intent

**Problem:** Между закрытой идентификацией автомобиля 4-2 (подтверждённый Vehicle Profile с ProfileDigest) и будущим каталогическим доказательством применимости 4-4 запрос детали живёт НЕструктурированно: тип work item «поиск детали» и title несут слова клиента, но материал запроса (какая деталь, сторона, количество, известные номера, предпочтение оригинала/аналога, ограничения, симптом) не записан фактами, режима запроса не существует (названная деталь / точный повтор по OEM / выбор оригинала или аналога / диагностика по симптому — FR-51), граница диагностики не исполняется (симптом может молча стать каталогическим заказом — FR-54), safety-critical узлы не останавливают подбор, противоречия источников не передаются человеку со всем материалом, а исправление клиентом существенной части запроса не помечает зависимые результаты устаревшими. Обязательность полей нигде не объявлена версионированно — риск зашить словарь магазина в код ядра.

**Approach:** Модуль `internal/cases` — запрос детали есть материал разговора: факты 2-2 уже несут append-only версии с полным provenance и подтверждениями к ТОЧНЫМ версиям; спека добавляет схему запроса детали в Domain Pack auto-parts@4.0.0 (материал-ключи с ролями + словарь режимов с приоритетами и обязательными наборами + safety-маркеры — приходит в cases через существующий структурный порт PackTaxonomy +1 метод по прецеденту PackIdentificationSchema 4-2), домен part.go с тремя чистыми семействами: нормализация номера флагами (VIN-дисциплина), детерминированная классификация режима над материалом (лестница приоритетов пака, семантику извлекает оператор/события — домен НЕ угадывает), read-time вывод Part Request с полнотой/digest/уверенностью/границами. Границы диагностики, safety и противоречий — слова вывода + рекомендация Human Handoff: словарь причин 2-13 расширяется на +3 слова (миграция 00019 — единственный SQL), задача менеджеру идёт существующей машиной 2-13/2-4 с материалом 2-14, клиенту — существующие слова owner/обновления 2-13/2-16. Поверхность — панель «Запрос детали» страницы кейса рядом с панелью 4-2; клиентские исправления part-фактов идут существующей публичной формой 2-10 (цель fact_correction принимает любые факт-ключи) — новой клиентской формы НЕ создаётся.

**Ядро честности среза:** Part Request — ВЫВОД, а не хранимая строка: read-time деривация над append-only фактами (идемпотентность байт-в-байт, ноль записей). Режим — детерминированная функция записанного материала с прозрачным основанием-словом, НЕ мнение модели: симптом доминирует над названной деталью всегда («вероятностное предположение не превращается в каталогический запрос» AC-7), названная при симптоме деталь — кандидат, причина не доказана. Молчаливых исправлений НЕТ ни в одном пути: NormalizePartNumber — флаги (Raw дословно, нормализованное — вывод, кириллица детект без замены), MissingKeys — только не-confirmed (повторное переспрашивание подтверждённого запрещено AC-3), пустое optional-поле — честное отсутствие, не догадка. Уверенность — ConfidenceWord выводом подтверждённости (числовые выдумки запрещены). Точное совпадение номера — НЕ доказательство применимости (Constant-слово; каталогический контур — 4-4). Несколько деталей — split 2-2 + честное слово: один структурированный набор на кейс (ключ-пространство фактов 2-2 — material key уникален на кейс; эволюция набор-на-элемент — deferred-work, НЕ долг).

## Boundaries & Constraints

**Always:** новая версия Domain Pack `auto-parts@4.0.0` в `internal/employee/packs/catalog.go` (surgical — версии 1.0.0/2.0.0/3.0.0 НЕ изменяются, immutability пинов 1-4; UpgradeFrom 3.0.0 compatible, Changed [part_request]); порт PackTaxonomy +1 метод PackPartRequestSchema (простые типы порта — прецедент PackIdentificationSchema); домен `internal/cases/domain/part.go` (новой): NormalizePartNumber + DerivePartRequestMode + DerivePartRequest + словари честных слов; словарь причин Human Handoff +3 слова в `human_handoff.go` (surgical: HandoffReasons/HandoffReasonTexts + комментарии расширения — новая версия словаря по прецеденту gateDictionary 4-1); миграция `migrations/cases/00019_part_request_handoff_reasons.sql` — ЕДИНСТВЕННЫЙ SQL среза: human_handoffs.reason CHECK 1→4 слова append-only honest-Down (прецедент 00018 use_kind); панель «Запрос детали» на странице кейса (read-time, honest-деградация без схемы пака — прецедент 4-2); OpenAPI словари-зеркала (mode enum 4 / reason enum 4 = зеркало 00019 / материал-ключи part.* enum-зеркалом / preference values 3) + контракт-тест; тесты поимённо: part_test.go режимная матрица + идемпотентность JSON ×2 + зонд hardcoded 0; регресс полным контуром после каждого шага (build/vet/unit/интеграция ×2 TZ/journeys/скан); записи DEVLOG + conventional commits + пуш после каждого подшага.

**Never:** НЕ выполнять запрос в каталоге ABCP/Laximo и НЕ заявлять «кандидатов детали» или применимость (ABCP-адаптер не реализован — AdapterImplemented false, AG-4/OQ-5 держат; применимость — 4-4, точное совпадение номера — не доказательство); НЕ подключать реальный AI-классификатор/LLM (режим — детерминированный вывод; семантическое извлечение — оператор/события с provenance; AD-7 контур реального планировщика придёт со своими stories; synthetic proposer — только фикстуры тестов); НЕ строить предложения/сравнение вариантов/заказ (4-5/4-6); НЕ создавать новых таблиц (Part Request — read-time вывод; единственный SQL — расширение CHECK 00019; 0 CREATE TABLE); НЕ трогать замороженные секции 2-2/2-6/2-13/1-4 (только словарные расширения по прецеденту; безусловность клиентского запроса 2-13 неприкосновенна — новые причины ПАРАЛЛЕЛЬНЫ клиентской, не заменяют её); НЕ расширять публичную форму 2-10 и её цели (part-факты проходят существующим путём fact_correction — SQL purposes 00010 не трогается); НЕ добавлять part.oem_number в IdentifierKinds токенизации 2-3 (duplicate-контур — отдельная эволюция, честная граница среза); НЕ заводить несколько одновременных структурированных part-наборов в одном кейсе (ключ-пространство фактов 2-2: material key уникален на кейс; несколько деталей = существующий split 2-2 + честное слово на панели; эволюция набор-на-элемент — запись в deferred-work этим же PR); НЕ выводить числовую «уверенность модели» (только ConfidenceWord подтверждённости); НЕ заполнять отсутствующие значения догадкой (AC-3: optional-отсутствие — честное отсутствие, mandatory-отсутствие — вопрос).

## I/O & Edge-Case Matrix

- Given кейс с пином auto-parts@4.0.0 и фактом part.symptom «грохот при торможении на кочках» (без part-идентичности), when деривация, then режим diagnostic, DiagnosticBoundary-слово «симптом не является названной деталью: подбор остановлен — диагноз у специалиста; соберите разрешённые наблюдения и передайте человеку», handoff-рекомендация diagnostic_uncertainty; MissingKeys = [part.symptom] пока симптом не подтверждён.
- Given факт part.symptom подтверждён (v2) И записан part.kind «тормозные колодки», when деривация, then режим diagnostic (симптом доминирует всегда) + кандидат-слово «названная деталь — КАНДИДАТ при симптоме: причина неисправности не доказана (AC-7)» + SafetyBoundary (маркер «тормоз»): стоп-слово «автоматический подбор остановлен: safety-узел с диагностической неопределённостью» + handoff-рекомендация safety_critical.
- Given факт part.oem_number « wf 2b19 6k666 aa » (пробелы, нижний регистр) + part.kind «фильтр салона», when нормализация номера, then Raw сохранён дословно, Normalized «WF2B196K666AA» (вывод: верхний регистр, пробелы выкинуты, «_»/«.» унифицированы в «-»), флаги чистые, режим exact_repeat, Constant-слово «точное совпадение номера не считается доказательством применимости к подтверждённому автомобилю (AC-4)»; идемпотентность: повторная деривация без изменений мира — байт-стабильный JSON, записей НЕТ.
- Given номер с кириллическими «А», «В» среди латиницы (позиции i), when нормализация, then CyrillicAmbiguities [{i, символ, look-alike}] по Unicode-блоку, normalized сохраняет кириллицу ДОСЛОВНО (замены НЕТ — VIN-дисциплина 4-2), слово «сверьте номер посимвольно», атрибут остаётся unverified.
- Given номер со спецсимволами вне разрешённого алфавита (буквы/цифры/«-»/«_»/«.»/пробел), when нормализация, then AlphabetOK false + слово с перечислением позиций, режим остаётся exact_repeat (материал есть), панель НЕ предлагает продолжение без подтверждённого номера (AC-12 «ошибочный OEM» блокирует маршрут).
- Given факты part.kind «топливный насос» + part.preference «both» (клиент просит выбор), when деривация, then режим original_vs_analog + слово «выбор оригинала или аналога: предложения и сравнение — контур 4-5; слово „аналог“ не разрешает любую найденную кросс-позицию (AC-5) — применимость доказывается каталогом 4-4».
- Given part.kind «щётки стеклоочистителя» + part.preference «analogs» + part.quantity 2, when деривация, then режим named_part (preference = ограничение, НЕ выбор), полнота по набору [part.kind, part.quantity] — complete, PartRequestDigest 64 hex, ConfidenceWord «материал подтверждён» при подтверждённых ключах.
- Given кейс пина 4.0.0 без единого part-факта, when панель, then «запрос не структурирован — запишите материал детали» + словарь ключей схемы с подписями (честное отсутствие режима, НЕ догадка).
- Given кейс с пином auto-parts@3.0.0 / montagio-services@1.0.0 / unreadable pin, when панель, then панель «Запрос детали» отсутствует с честным словом «схема запроса детали пака не определена» (деградация 4-2; чтение НИКОГДА не падает).
- Given named_part с part.kind confirmed и part.quantity НЕ записан, when деривация, then MissingKeys = [part.quantity] ТОЛЬКО (подтверждённый kind НЕ переспрашивается — AC-3) + вопрос-слово «уточните: сколько нужно?»; optional-ключи (side/budget/deadline/brands/constraints) отсутствуют = НЕ missing (честное отсутствие).
- Given клиент исправил существенную часть: part.kind подтверждён (v3), оператор записал v4 «другая деталь», when деривация, then атрибут conflicting (read-time 2-2) + stale-слово «подтверждение относилось к прежней версии (v3)» + PartRequestDigest ИЗМЕНИЛСЯ + слово «зависимые результаты (поиск, применимость, сравнение, commitment — контуры 4-4..4-9) обязаны пиннить digest запроса и считать прежние устаревшими (AC-10); дальнейшая работа — только новая подтверждённая версия».
- Given два значения part.kind от разных источников (channel_event и operator), when деривация, then conflicting + ContradictionBoundary-слово «Staffy не выбирает наиболее вероятный вариант (AC-9)» + handoff-рекомендация unresolved_contradiction + материал для человека: исходный запрос (слова клиента — события кейса), подтверждённый автомобиль (профиль 4-2 + digest), спорные факты списком, выполненные проверки (флаги номера/VIN).
- Given оператор создал Human Handoff со словом diagnostic_uncertainty по рекомендации панели, when создание, then запись в словаре 00019 (SQL-зеркало), задача в подтверждённом Inbox (существующая машина 2-13/2-4), карточка decision-ready (2-14): профиль 4-2 + запрос 4-3 + исходные слова + ConfidenceWord + неоднозначность + рекомендуемый следующий вопрос (первый MissingKey), клиенту — существующие слова текущего owner и ожидаемого обновления (2-13/2-16).
- Given в кейсе активных work items типа «поиск детали» больше одного (клиент просил колодки и фильтр — оператор разделил split 2-2), when панель, then SeveralPartsWord «обращение содержит несколько деталей: материал ведёт один структурированный набор на обращение — разделяйте элементы работы; одновременные структурированные наборы вне первого среза (deferred-work)»; split/merge — существующие команды 2-2 без изменений.
- Given safety-маркер пака входит в нормализованный part.kind («тормоз» в «тормозные колодки») и материал НЕ содержит симптома/конфликтов, when деривация, then SafetyNote-слово «safety-узел: подтверждённый материал обязателен; менеджерский гейт 4-7 стоит до поставщика» — подбор НЕ останавливается (остановка — при диагностической неопределённости или конфликте, AC-8), список маркеров — декларация пака, честное слово «список safety-узлов — эвристика пака; при сомнении передайте специалисту».
