## Intent

**Problem:** 2-1 назначил первоначального владельца и честно заморозил остальное: `conversations.response_owner_epoch` зажат CHECK = 1, `writable_surface` — единственным значением `inbox`, спека 2-1 прямо оставила «ротация владельца и смена surface — 2.4». Механики передачи владения не существует: нет команд взять/передать/принять/отклонить, нет compare-and-swap переходов, epoch не двигается никогда (FR-13 AC-4); «assigned» и «acknowledged» не различаются (AC-5); backup owner и acknowledgement deadline из human coverage 1-13 невидимы оператору; недоступность владельца не обнаруживается (AC-9). Серверного гейта клиентской записи не существует: исходящего ответа клиенту нет как класса (2-1 «автоответ не отправляется», 2-3 «реальная доставка в канал отложена») — нечему и некому запрещать писать; требование «скрытие кнопки в интерфейсе не заменяет серверную проверку» нечем исполнять (AC-3). Единого владельца объединённого диалога нет: связывание 2-3 дало единую вьюху событий, но клиентская запись ничем не governится — владение размечено по сессиям в момент создания, «смена канала не создаёт второго Response Owner или параллельного записывающего Inbox» не гарантируется механизмом (AC-7). Истории владения нет: ни append-only переходов с previous/target/actor/reason/timestamps/acknowledgement/epochs, ни versioned ownership event в outbox (AC-11). Evidence-гейта writable surface не существует: внешний human Inbox не выбирается и не отклоняется по доказательствам capabilities — «Jivo или другой Inbox не считается one-writer-capable по названию продукта» нечем исполнять (AC-8).

**Approach:** Первый срез строит владение целиком на append-only-дисциплине (прецедент 2-1/2-2/2-3: история не редактируется, «текущее» — производная чтения), с минимальным расширением ingest (ровно один INSERT) и без единого изменения лестницы адмиссии. Логическая Conversation FR-13 = кейс (единый диалог 2-1/2-3: кейс + связанные связыванием 2-3 разговоры): владение и записывающая поверхность живут на кейсе, сессии-разговоры наследуют governing-кейс через производную активных связей. (1) **Ownership terms:** append-only `cases.ownership_terms` — один термин на период владения: (tenant, case, epoch — материальная уникальность, монотонность), owner_kind `human|staffy`, owner_ref (участник Tenant либо Employee кейса), writable_surface из словаря, origin `ingest_initial|take|transfer_acknowledge|reassign`, previous owner, actor, reason ≤200, requested_at/acknowledged_at, created_at; текущее владение — производная (строка максимального epoch кейса); колонки conversations остаются снимком создания (CHECK epoch=1 и surface='inbox' миграции 00001 не трогаются — живое состояние в терминах). Ingest 2-1 расширяется ровно одной записью: та же транзакция пишет initial-термин (epoch 1, владелец из human coverage, surface `inbox`) — лестница и логика не меняются, регресс 2-1 обязан остаться зелёным. Очередь, отдел или неподтверждённый кандидат владельцем быть не могут: owner_kind+owner_ref обязан разрешаться в участника (MembersFacts) либо Employee кейса — доменная валидация с честным отказом (AC-1). (2) **Переходы владения (CAS):** команды `TakeOwnership` (участник с `review`; разрешён только в «забираемых» состояниях — дедлайн подтверждения истёк без решения, либо владелец недоступен; здоровое владение — честный отказ «запросите передачу»), `RequestTransfer` (текущий владелец либо обладатель `configuration`; цель — участник (проверка MembersFacts: существует и активен) либо Staffy (Employee кейса); причина ≤200; дедлайн — AckDeadlineMinutes из human coverage действующего решения маршрута, перечитка RouteFacts; недоступность покрытия — честный fail-closed отказ; висящий запрос один на кейс — advisory-лок кейса + производная, конкурент — честный 409), `ResolveTransfer` (acknowledge — только цель: атомарно resolution + новый термин epoch+1 + outbox event; decline/отмена — цель или автор запроса: resolution без смены владельца; таймаут — производная времени: запрос без решения и deadline < now, опоздавший acknowledge — честный отказ `request_expired`), `ReassignOwnership` (обладатель `configuration`: прямой термин epoch+1 с причиной, гасит висящий запрос resolution-отменой той же транзакцией; путь надзора). Все команды идемпотентны (command_records, прецедент 2-2: replay исхода до стражей; словарь команд +5), несут expected_epoch ≥ 1; любой переход — INSERT термина под материальной уникальностью (tenant, case, epoch) + advisory-лок кейса (сортированный lock-план, прецедент 2-2/2-3): две одновременные попытки с одной исходной версией → ровно один переход, проигравший — честный конфликт с текущим владельцем и epoch для безопасного перечитывания (AC-4). Подтверждённая передача меняет владельца, surface и epoch атомарно (одна транзакция: термин + resolution + outbox); новый владелец получает актуальное состояние кейса, старый немедленно теряет право клиентской записи — следующая его команда записи отказана гейтом (AC-10). (3) **Гейт записи (серверный):** команда `SendClientReply` — единственный клиентский исходящий путь среза: actor обязан быть текущим владельцем-человеком (сверка principal против производной текущего термина; owner_kind=staffy → честный отказ «цифровой сотрудник не отправляет в этом срезе» — его автономное поведение 2-5); expected_epoch обязан совпадать; состояние здоровья — не `reassignment_required`; висящий неподтверждённый запрос НЕ блокирует текущего владельца (AC-5). Разговор-цель обязан принадлежать кейсу либо быть активно связанным (производная активных связей 2-3): governing-кейс = цель связывания; владелец исходного кейса B, пишущий в связанный разговор Y, — честный отказ с текущим владельцем объединённого диалога и разрешённым способом запросить передачу (AC-7: смена канала не создаёт второго владельца). Отказ гейта несёт текущего владельца (kind + имя), epoch и путь передачи — «пользователь видит текущего владельца и разрешённый способ запросить передачу» (AC-3); скрытие кнопки в UI — только UX, гарант — сервер. Запись: `cases.client_replies` (governing-кейс, разговор, снимок владельца, epoch, surface, снимок маршрута разговора (connection/provider/канал+направление), снимок lineage релиза (employee, decision_no, profile_version из перечитки RouteFacts), контент ≤2000, created_at) + outbox `case.client_reply_prepared` — persist-before-emit, одна транзакция (AC-2: исходящее связано с Conversation, текущим владельцем, epoch, channel route и Release Manifest). Внутренних заметок как класса в контуре нет: единственный путь клиентского текста — команда (инвариант «внутренние заметки других участников не отправляются клиенту» — по построению). (4) **Execute-time revalidation:** `DrainClientReplies` (замена воркера, прецедент `DrainOutbox` 2-1; bounded-батч, идемпотентность материальная — уникальность исхода на ответ + производная состояния): для каждого prepared-ответа переоценивает перед отправкой — владелец/epoch не изменились (текущий термин совпадает), участник активен, кейс открыт, маршрут допущен действующим решением (RouteFacts): свежий → append-only `cases.client_reply_outcomes` `dispatched` + outbox `case.client_reply_dispatched` (синтетическая доставка контура: реальная отправка в канал — исходящие диалоги, честно отложено; `dispatched` — запись факта записи, не заявление доставки клиенту); устаревший (epoch/владелец ушли) → исход `stale_needs_review`: payload НЕ пересылается новому владельцу автоматически, состояние видно в карточке (AC-6); той же транзакцией при наблюдении истёкшего без решения запроса передачи либо недоступного владельца пишется operational exception `ownership_attention` (без PII; материальная уникальность гасит повторы) — точка «система обнаружила проблему» (AC-9). (5) **Health/overdue — производные чтения:** DeriveOwnershipState: `stable` (владелец-участник активен, запроса нет), `transfer_pending` (запрос в дедлайне; текущий остаётся владельцем — AC-5; производная объявлена для будущих автономных поверхностей — «заморозка несовместимых автоматических действий» потребляется ими), `transfer_timed_out` (дедлайн истёк — запрос погашен производной, take разрешён), `reassignment_required` (владелец-участник не существует/неактивен — сверка MembersFacts на чтении карточки и на гейте записи): прежний владелец остаётся записанным до безопасного перехода, новые исходящие блокируются, карточка показывает backup owner из human coverage, дедлайн и безопасный путь переназначения (take резервным владельцем / reassign надзора) (AC-9). Часы доступности человека и heartbeat/lease — честно отложено: детекция среза — по дедлайну подтверждения и активности участника. (6) **Writable surface + evidence-гейт:** словарь `inbox|external_inbox`; `inbox` — проверенная минимальная Staffy operator surface (прецедент 2-1; OQ-17); `external_inbox` выбирается только при действующем account-scoped evidence write/ownership-capability соединения (ConnectionFacts: capability направления outbound, операция command/event, state `verified`, не истёк и не stale): по названию продукта (Jivo) поверхность НЕ считается one-writer-capable (AC-8); без доказательства — честный отказ `surface_not_evidenced`, используется минимальная Staffy surface либо маршрут не допускается. В контуре мутирующие capabilities не верифицируемы (блок AG-4 из 1-9) — external_inbox недостижим честно: доменный юнит-тест доказывает положительную ветку на синтетическом capability-слове, интеграция — fail-closed. Поверхность меняется только переходом владения (термин несёт surface; смена surface без смены владельца в срезе не существует). (7) **Поверхность оператора:** Response Owner Control в карточке кейса: текущий владелец (kind + имя участника либо «цифровой сотрудник»), epoch, surface, состояние передачи текстом (цель, дедлайн, remaining; assigned и acknowledged — разные тексты, спутать нельзя — AC-12), overdue/reassignment-состояния + backup owner + безопасный путь переназначения; формы take/request/resolve/reassign/reply PRG; основное действие соответствует текущему состоянию (владелец → «отправить ответ»/«передать»; цель запроса → «принять»/«отклонить»; посторонний → только «запросить передачу»); focus после конфликта — к обновлённой информации (flash-focus прецедент 2-2/2-3); таймлайн показывает исходящие записи с честным состоянием (prepared/dispatched/stale); доступность: клавиатура, screen reader, 320 px без горизонтального скролла, цели ≥44×44 px; Work Control Card — 2-14 (честно отложено).

## Boundaries & Constraints

**Always:** Append-only: `ownership_terms`, `transfer_requests`, `transfer_resolutions`, `client_replies`, `client_reply_outcomes` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, грантов UPDATE/DELETE нет; текущее владение / состояние запроса / состояние ответа — производные (максимальный epoch термина / отсутствие resolution / исход drain-а), не хранимые state-колонки. Идемпотентность команд — прецедент 2-2/2-3: `cases.command_records` (UNIQUE tenant+actor+command+key, request-hash, replay исхода до стражей), словарь команд расширяется `take_ownership|request_transfer|resolve_transfer|reassign_ownership|send_client_reply`; `DrainClientReplies` — sweep-команда с материальной идемпотентностью (UNIQUE (tenant, reply) исхода + производная состояния; прецедент `DrainOutbox` 2-1, в словарь command_records не входит). CAS: каждая переходная команда несёт expected_epoch ≥ 1; переход — INSERT термина под UNIQUE (tenant, case_id, epoch) + advisory-лок кейса (сортированный lock-план); конфликт — честный 409 с текущим владельцем (kind, имя) и epoch; конкурентные гонки детерминированы интеграционными тестами (ровно один переход, проигравший — безопасное перечитывание). Initial-термин пишет та же транзакция ingest, что создаёт Case/Conversation (лестница адмиссии, словари отказов и логика 2-1 не меняются ни строкой; тесты 2-1 не правятся); отсутствие допустимого первоначального владельца — существующий отказ `no_response_owner` (маршрут не допущен до внешнего трафика, AC-1). Дедлайн подтверждения — только из human coverage действующего решения маршрута (RouteFacts перечитка, AckDeadlineMinutes > 0 по валидации 1-13); недоступность покрытия — честный fail-closed отказ; выдумывание дедлайна словарём или параметром команды запрещено. Outbox: `case.ownership_changed` v1 (снимок термина: epoch, owner, surface, origin, actor) — той же транзакцией, что термин; `case.client_reply_prepared`/`case.client_reply_dispatched` v1; доставка — существующий `DrainOutbox` (не меняется). Полномочия применяются на сервере до SQL: take/resolve (цель)/drain — участник с `review`; request — текущий владелец либо `configuration`; reassign — `configuration`; send_client_reply — только текущий владелец-человек (гейт); не-участник Tenant — 404 без раскрытия существования; межтенантная изоляция — RLS во всех новых таблицах. Privacy: новые таблицы — класс `case-operations` (чтение `review`/`audit`, команды — `review`; контент ответа ≤2000 следует классу операционных записей кейса, как значения фактов 2-2); TestPerimeterIntegrity синхронно заявляет все новые таблицы; в exceptions/телеметрию/outbox-конверты — только идентификаторы, словарные состояния и времена, без содержимого ответов и без PII. Транспорт: операторские формы PRG + машинный JSON-контракт, OpenAPI синхронно (пути 5 команд + drain + OwnershipView + список исходящих), контракт-тест ассертит словари и форму отказа гейта (current_owner kind+name, epoch, permitted_path). UI: владение/передача/дедлайн/remaining/состояния текстом; assigned и acknowledged — разные текстовые подписи; ошибки связаны с полями; flash-focus после конфликта/действия; цели ≥44×44 px; 320 px без горизонтального скролла. Регресс 2-1/2-2/2-3 обязан оставаться зелёным (build/vet/unit/интеграция обеих TZ/journeys/контракт/diff); файлы тестов прошлых срезов не правятся (кроме механических расширений фикстур, если неизбежно — с честной записью в Change Log).

**Never:** Не менять колонки и ограничения миграции 00001 (CHECK epoch=1, CHECK surface='inbox') — живое состояние в терминах, «текущее» — производная; UPDATE/DELETE историй владения и ответов не существует (грантов нет). Не давать записывать клиенту никому, кроме текущего владельца-человека через единственную команду (никаких «системных» отправителей и обходных путей; адаптеры реальной доставки — будущие исходящие, не этого среза). Не пересылать устаревший payload новому владельцу автоматически (stale — только видимое состояние needs review). Не считать assigned за acknowledged; не менять владельца без acknowledge (кроме явного reassign надзора и take в «забираемых» состояниях). Не назначать владельцем очередь, отдел или неподтверждённого кандидата (owner обязан разрешаться в участника или Employee кейса). Не выбирать внешний Inbox поверхностью без действующего verified account-scoped write/ownership capability evidence (название продукта — не доказательство; мутирующие capabilities без AG-4 недоказуемы — fail-closed). Не выдумывать дедлайн подтверждения (только human coverage; недоступно — отказ). Не писать содержимое ответов в exceptions/логи/outbox-конверты (payload живёт только в записи ответа). Не заявлять реальную доставку в канал (`dispatched` — запись факта в синтетическом контуре; реальная доставка — исходящие диалоги, AG-4). Не блокировать входящие события состоянием владения (ingest и его правила продолжения не трогаются; единый таймлайн живёт по 2-1/2-3). Не доверять UI-скрытию кнопки как гейту (сервер — единственный гарант; UI только следует состоянию). Не делать автоматические переходы владения (истечение дедлайна — производная, погашающая запрос; смена владельца — только команды человека). Не строить в этом срезе: Staffy-автономию и раскрытие (2-5), Work Control Card (2-14), heartbeat/ownership lease, детекцию по часам доступности человека, внутренние заметки как класс, фоновые воркеры (drain-команда — замена), real-time push карточки. Не выдумывать вторую записывающую поверхность для одного кейса (один термин — одна surface; связанный разговор управляется governing-кейсом).

## I/O & Edge-Case Matrix

- Given новое обращение на допущенном маршруте с валидным human coverage, when ingest исполняется, then в одной транзакции создаются Case/Conversation/Work Item/payload/outbox как в 2-1 И initial-термин владения (epoch 1, владелец из human coverage, surface `inbox`, origin `ingest_initial`); оператор видит во Response Owner Control владельца, epoch 1, surface; очередь/отдел владельцем быть не могут (домен отвергает owner_ref, не разрешающийся в участника/Employee — AC-1).
- Given покрытие маршрута без валидного владельца, when ingest доходит до ступени владельца, then существующий отказ `no_response_owner`, маршрут не допущен, кейса нет (AC-1, регресс 2-1).
- Given участник без владения пытается отправить клиентский ответ (UI-форма, прямой API, любая будущая отложенная задача), when команда исполняется, then серверный отказ с текущим владельцем (kind + имя), текущим epoch и разрешённым способом запросить передачу; записи нет; скрытие кнопки в интерфейсе ничего не меняет (AC-3).
- Given текущий владелец-человек отправляет ответ через назначенную surface, when команда исполняется, then prepared-запись связана с разговором, governing-кейсом, снимком владельца, epoch, surface, снимком маршрута разговора и lineage релиза (employee, decision_no, profile_version); той же транзакцией outbox `case.client_reply_prepared`; в таймлайне видна исходящая запись с состоянием prepared (AC-2).
- Given два участника одновременно берут владение с одной исходной версией (expected_epoch совпадает), when обе команды исполняются, then ровно один новый термин epoch+1; проигравший — честный 409 с текущим владельцем и epoch, безопасное перечитывание; replay любой из них — исходный исход (AC-4).
- Given запрос передачи создан (assigned, дедлайн из coverage), when цель ещё не подтвердила, then текущий владелец остаётся владельцем и может отправлять ответы; производная `transfer_pending` объявлена (заморозка несовместимых автоматических действий потребляется будущими автономными поверхностями — в срезе автономных нет); второй запрос одновременно — честный 409 (AC-5).
- Given цель подтверждает передачу (acknowledge) в дедлайне, when команда исполняется, then атомарно: resolution + термин epoch+1 (владелец=цель, surface по запросу) + outbox `case.ownership_changed`; карточка показывает нового владельца; прежний владелец на следующей попытке ответа — отказ гейта с новым владельцем (AC-10).
- Given цель отклоняет (decline) либо автор отменяет, when команда исполняется, then resolution без смены владельца и epoch; карточка показывает прежнего владельца; повторный запрос — новая строка (AC-5).
- Given prepared-ответ, затем владение перешло (epoch ушёл), when drain готовит отправку, then execute-time revalidation: исход `stale_needs_review`, payload не пересылается новому владельцу, состояние видно в карточке; тот же drain для свежего ответа (владелец/epoch/адмиссия/активность/открытость без изменений) — исход `dispatched` + outbox `case.client_reply_dispatched` (синтетическая запись; реальной отправки в канал нет) (AC-6).
- Given запрос передачи с истёкшим дедлайном без решения, when любая команда владения или drain наблюдает его, then производная `transfer_timed_out` (запрос погашен), take становится разрешён; drain фиксирует `ownership_attention` один раз (материальная уникальность); опоздавший acknowledge — честный отказ `request_expired` (AC-9/AC-5).
- Given владелец-участник покинул Tenant или деактивирован, when гейт записи либо чтение карточки сверяет MembersFacts, then прежний владелец остаётся записанным, состояние `reassignment_required`, новые исходящие блокируются честным отказом, карточка показывает backup owner (из human coverage), дедлайн и безопасный путь переназначения; take резервным владельцем и reassign надзора доступны (AC-9).
- Given разговор Y активно связан с кейсом A (binding 2-3), when продолжают поступать события сессии Y, then единый таймлайн живёт по правилам 2-1/2-3 без изменений; клиентский ответ через Y допускается только текущему владельцу A (governing-кейс); владелец кейса B — отказ гейта с указанием владельца объединённого диалога; после отмены связи (unlink) Y снова управляется кейсом B; второго владельца или параллельной поверхности не существует (AC-7).
- Given запрошена surface `external_inbox`, when гейт читает capability facts соединения, then без действующего verified account-scoped write/ownership evidence (outbound, command/event, state verified, не истёк) — честный отказ `surface_not_evidenced`, выбор минимальной Staffy surface либо блокировка маршрута; Jivo или иной Inbox по названию продукта — не доказательство; в контуре ветка недостижима (мутирующие capabilities без AG-4) — доменный юнит доказывает положительную ветку синтетическим словом (AC-8).
- Given любое изменение владения завершилось, when транзакция закоммичена, then append-only история хранит previous owner, target owner, actor, reason, timestamps, acknowledgement, from/to epochs; outbox публикует versioned ownership event; replay команды идемпотентен — второго перехода нет (AC-11).
- Given Response Owner Control с клавиатуры, screen reader, увеличенным текстом или шириной 320 px, when оператор работает, then владелец, surface, epoch, дедлайн, remaining и состояние передачи доступны текстом; assigned и acknowledged не спутать; основное действие соответствует текущему состоянию; focus после конфликта переходит к обновлённой информации (AC-12).

- Given подготовленный или поставленный в очередь исходящий ответ с устаревшим response_owner_epoch, when worker-замена (drain) готовится отправить его, then execute-time revalidation блокирует отправку; устаревший payload не пересылается новому владельцу автоматически; создаётся видимое состояние `stale_needs_review`.

- Given текущий владелец потерял роль, соединение или способность ответить, when система обнаруживает проблему (гейт/чтение/drain), then прежний владелец остаётся записанным до безопасного перехода, Conversation получает `reassignment_required`; новые исходящие блокируются; видны backup owner, acknowledgement deadline и безопасный путь переназначения.
- Given разрешённое переназначение подтверждено, when новый владелец принимает Conversation, then владелец, writable surface и epoch изменяются атомарно; новый владелец получает актуальную версию Case; старый немедленно теряет право клиентской записи.
- Given любое изменение владения, when транзакция завершается, then append-only история сохраняет previous owner, target owner, actor, reason, timestamps, acknowledgement и epochs; outbox публикует versioned ownership event; повтор события не создаёт повторный переход.

## Implementation Notes

- Идемпотентность — единый механизм 2-2/2-3: command_records до стражей, replay исхода; advisory-лок кейса — сортированный lock-план (прецедент ExecuteWork/bind 2-3); drain — материальная идемпотентность (UNIQUE (tenant, reply) + производная), прецедент DrainOutbox.
- Ingest: ровно один дополнительный INSERT (initial-термин) в существующей транзакции приёма; лестница, словари и порядок ступеней 2-1 не меняются; тесты 2-1 остаются зелёными без правок.
- Владение по кейсу (логическая Conversation FR-13); governing-кейс связанного разговора Y — производная активных связей 2-3 (та же производная, что вьюха карточки) — гейт и карточка читают один источник.
- Дедлайн — AckDeadlineMinutes human coverage действующего решения (RouteFacts перечитка); Clock-порт — детерминированные тесты входа/выхода дедлайна и опоздавшего acknowledge (прецедент threshold-окна 2-3).
- Evidence-гейт surface — доменная функция над capability-словом из ConnectionFacts (outbound, command/event, state verified, expires); юнит-набор — положительные и отрицательные ветки на синтетических словах; интеграция — fail-closed (мутирующие capabilities без AG-4 не верифицируемы).
- Отказ гейта машинно читаем: current_owner (kind, name), current_epoch, permitted_path (request_transfer) — UI показывает напрямую, без второй логики.
- Outbox: 3 новых типа событий v1 (`case.ownership_changed`, `case.client_reply_prepared`, `case.client_reply_dispatched`), канонический JSON + dedup key по прецеденту 2-1; доставка — DrainOutbox без изменений.
- Фикстура journeys: мир 2-1/2-3 + два оператора + передача с acknowledge + stale + overdue + панель/формы на 320 px (паттерн cases_fixture).
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...` (UTC + TZ=Europe/Moscow), `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`; регресс 2-1/2-2/2-3 зелёный обязательно.
