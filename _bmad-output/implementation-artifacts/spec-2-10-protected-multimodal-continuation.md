## Intent

**Problem:** Защищённого продолжения не существует ни в каком виде: клиенту, которому неудобен текущий канал (VIN, документ, фото, выбор варианта, Commitment Review — AC-блок 1), некуда «перейти» — purpose-bound ссылки нет (ни таблицы, ни команды, ни словаря), «связанную с Tenant, Case, Work Item, участником, разрешёнными операциями и сроком действия» (AC-1) нечему нести, «ссылка не предоставляет общего доступа к Case» (AC-1) нечем обеспечить. Клиентской web-поверхности в контуре НЕТ — до 2-9 все страницы операторские (спека 2-9 честно вынесла «клиентский re-open — story 2-10»): страницы «Tenant, AI-роль, цель, краткое резюме подтверждённых фактов и открытый вопрос» (AC-блок 3) не существует; «позволяет исправить перенесённый факт» (AC-блок 3) нечем исполнять — факты 2-2 пишутся только операторскими командами; «событие продолжения в том же Case» (AC-блок 10) не производится; «Вернуться в разговор»/«Позвать человека» (AC-блоки 11–12) — нечему нажимать. Управление жизненным циклом ссылки отсутствует: «истекла, отозвана, уже использована за пределами consumption limit либо Tenant control generation изменилась → доступ блокируется без раскрытия Case» (AC-блок 9) — нет ни деривации состояния, ни честных отказов, ни «безопасного способа получить новую ссылку». FR-16 проверяемое следствие «основной канал показывает, доставлена ли ссылка… связывает с запросом ровно одну отправку и позволяет прекратить ожидание» — не работает: связки reply↔ссылка нет, команды отзыва нет. Проверяемые следствия FR-82 (modality/источник/время/consent-access-контекст на каждом фрагменте; извлечённый факт доступен для focused correction) — для modality text не имеют носителя: канал записи клиентских данных = protected continuation не существует.

**Approach:** Первый срез — детерминированный серверный скелет purpose-bound ссылки продолжения и защищённой страницы (модальность text; прецедент 2-5…2-9: AI Runtime в контуре НЕТ, продюсер размечает — машина гейтит). Пять частей: (1) словари Domain Pack v0: цели ссылки v1 = {fact_correction} (набор непуст, подмножество словаря); виды использования use_kind = {fact_correction_submitted, human_requested, returned_to_conversation}; ttl = 5..120 минут (короткоживемость), consumption_limit = 1..10; деривация состояния ссылки — read-time DeriveContinuationLinkState = {valid, expired (now > expires_at), revoked (есть строка отзыва), consumed (принятых fact_correction-отправок ≥ limit), owner_stale (текущий response_owner_epoch кейса ≠ пинутого), unknown (токен не найден)} — состояния нигде не мутируются (прецедент DeriveConfirmationValidity 2-9/DeriveObservationState 2-7); capability-токен v1 = base64url(tenant_id 16B ‖ random 32B): случайные 256 бит делают угадывание непрактичным, в БД хранится ТОЛЬКО SHA-256(random 32B) (bytea 32, UNIQUE), URL не раскрывает ни кейса, ни WI, ни участника (opaque); токен = предъявляемая клиентом учётная запись-возможность — прецедент короткоживущего одноразового подписанного playback-permit AD-6 (request-carried credential); AD-10-честность: tenant-кандидат из токена ВЕРИФИЦИРУЕТСЯ хешем ДО чтения какого-либо материала кейса (неверный tenant → хеш не найден в RLS-скоупе → generic-отказ без раскрытия), скоуп материала ставится только из строки ссылки; (2) append-only `cases.continuation_links`: link_id, пины (case, WI, participant_ref — адрес канала клиента, owner_epoch на момент выдачи, question 1..500 — «открытый вопрос», explanation 1..1000 — «переход объясняет цель»), purpose-set jsonb (словарь-подмножество, CHECK), expires_at = issued_at + ttl, consumption_limit, token_hash, actor, issued_at; `cases.continuation_link_uses` (append-only: link, use_kind, material ref для коррекции, submitted_at); `cases.continuation_link_revocations` (append-only: link, actor, reason, revoked_at); команда `issue_continuation_link` (оператор review, гейт скоупа ДО материальных стражей — прецедент M1 2-5/2-7/2-8/2-9): гейты → участники → не-терминальный WI → гварды домена → insert + outbox `case.continuation_link_issued` (метаданные: link_id, purpose-set, expires_at — БЕЗ токена: токен существует только в ответе команды и на стороне оператора); токен-URL вплетается в исходящий sales-reply (продюсер): +1 nullable колонка client_replies.link_id (прецедент связки commitment-пары 2-9; reply несёт URL текстом — канал доставки тот же, «ровно одна отправка» = связка одной reply-строки); команда `revoke_continuation_link` (оператор: «прекратить ожидание») — строка отзыва, ничего не мутирует; (3) публичная защищённая страница `GET /continue/{token}` (без сессионной аутентификации — токен и есть гейт; страницы-отказы generic без раскрытия кейса и без различения причин «неизвестный токен/чужой tenant»): валидна → шапка (имя Tenant — транспорт читает identity-сервисом, AI-роль — employee-контекст не читается, роль = «ИИ-сотрудник» константа среза, честная граница), explanation («цель перехода»), краткое резюме ПОДТВЕРЖДЁННЫХ фактов WI (confirmed-версии 2-2; только этого WI — «не раскрывает… другие Work Items или данные другого участника» AC-блок 3), question (открытый вопрос), форма исправления перенесённого факта (select подтверждённых фактов + новое текстовое значение), постоянно доступные «Позвать человека» и «Вернуться в разговор»; consumed → терминальная страница «материал отправлен, ссылка завершена» (ссылка не восстанавливается); (4) клиентские действия `POST /continue/{token}/{correct|human|return}` — PRG: correct → гейты (состояние valid → лимит не исчерпан → факт принадлежит WI этой ссылки → значение проходит гварды факта 2-2) → append-only НОВАЯ версия факта в состоянии неподтверждённой (исходная запись не уничтожается — AC-блок 10; provenance: channel=protected_continuation, source_ref=link_id — след FR-82 modality/источник для text) + use-строка (потребляет лимит) + outbox `case.continuation_submitted` (метаданные: link_id, WI, факт, номер новой версии — БЕЗ значения факта, «кандидат не покидает строку») → редирект ?submitted=1 → страница объявляет «отправлено — оператор проверит» (aria-live, AC-блок 12); human → use-строка (НЕ потребляет лимит — запрос, не отправка данных) + outbox `case.continuation_human_requested` → «оператор свяжется с вами»; return → use-строка + outbox `case.continuation_returned` → «возвращайтесь в ваш разговор — обращение и всё сохранённое продолжаются, повторный набор вопросов не нужен» (AC-блок 11: серверно ничего не мутирует, WI/факты/Response Owner не меняются неявно); повторный POST коррекции сверх лимита → терминальная страница (PRG-двойной-клик честно ограничен лимитом; default limit=1 = «ровно одна отправка» FR-16); (5) панель оператора на карточке кейса: ссылки (link_id, цели, состояние деривации, delivered-бейдж по связке reply, uses/limit, истечение, PRG-кнопка отзыва), лента событий (submitted/human/returned) — «основной канал показывает, доставлена ли ссылка, ожидается ли ответ, завершена ли отправка или истёк ли срок» (FR-16) и «прекратить ожидание» = revoke. a11y среза: 320 px без горизонтального скролла, цели ≥44×44 px, статусы объявляются (aria-live=polite), данные не теряются при ошибке (форма сохраняет введённое), confirm-подобное основное действие не preselected/не autofocus (прецедент 2-9 AC-12).

**Решение владельца:** Ожидает CHECKPOINT 1 — предъявление нетехническим пересказом в ответе сессии; Dev не стартует до явного одобрения (дисциплина 52-sm: самопродолжение «продолжай» чекпоинт не закрывает).

## Boundaries & Constraints

**Always:** append-only `cases.continuation_links` / `cases.continuation_link_uses` / `cases.continuation_link_revocations` — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; идемпотентность операторских команд: тот же command-ключ с тем же материалом → replay исходной записи (command_records 2-1, +2 слова словаря команд issue_continuation_link/revoke_continuation_link), тот же ключ с иным материалом → ErrCommandKeyConflict 409; операторские гейты: скоуп review ДО материальных стражей (403 словами скоупа, прецедент M1), не-участник → 404 ×пути, чужой tenant → RLS 404; словари целей/видов использования — CHECK-подмножества (никогда конфигурация тенанта); токен: random 32B crypto/rand (прецедент id.NewV7 rand.Read), хранение ТОЛЬКО SHA-256(random) bytea=32 UNIQUE (tenant, token_hash), токен целиком никогда не в БД/outbox/логах/исключениях (маска в панелях: «токен выдан»); URL /continue/{token} — токен не содержит case/WI/участника (opaque); public-маршрут: никакой сессионной/операторской аутентификации, никакой раскрытие существования кейса при отказе (единая generic-страница «ссылка недействительна или истекла — свяжитесь с нами по каналу обращения» + безопасный путь «позвать человека» без данных), различение причин отказа НЕ показывается клиенту (внутренне: панель оператора видит точное состояние деривации); AD-10: tenant-скоуп ставится ТОЛЬКО после верификации хеша (lookup = SELECT … WHERE tenant=scope AND token_hash=$1 под RLS; scope-кандидат из токена проверяется хешем до чтения материала; неверный → пусто → generic-отказ); consumption: считаются ТОЛЬКО принятые fact_correction-отправки (human/return — события, не отправки); use-строки append-only, каждая несёт submitted_at; коррекция: только подтверждённые факты этого WI (select), значение — гварды факта 2-2 (та же валидация, что у операторской record-ветки), новая версия — состояние неподтверждённая (оператор подтверждает штатной командой 2-2 — поверхность НЕ подтверждает сама); provenance: channel=protected_continuation (слово словаря каналов фактов 2-2 +1), source_ref=link_id; client_replies.link_id — nullable, только sales-строки (гейт как 2-9 pair: нейтральный/защищённый → 400 словарём), связка только реально существующей ссылки того же кейса; outbox-типы continuation_link_issued/continuation_submitted/continuation_human_requested/continuation_returned (+4) — метаданные (id/link/WI/факт-версия/use_kind) без токена, без значений фактов, без текстов question/explanation; страницы: content-type text/html; PRG — все клиентские POST (303 + anchor); a11y: 320 px, ≥44×44 px, aria-live=polite статусы, без autofocus/preselect, введённое не теряется при ошибке валидации (re-render со значением + текст ошибки), статусы не отличимы только цветом; OpenAPI: +2 операторских пути (issue/revoke) со схемами, зеркальными словарям; публичные HTML-маршруты — вне JSON-контракта (честная граница: клиент — человек, не API-потребитель); journeys-цепь на реальном транспорте (fixture-identity резолвер — public-маршрут не проходит сессионную аутентификацию, fixture-сервер не требует).

**Never:** не строить media-поверхность НИ В КАКОМ ВИДЕ (Media Uploader, состояния selected/uploading/uploaded/scanning/accepted/rejected/failed, quarantine, malware/content scanning, безопасный render, type/size/signature/safe-name проверки, consent-разделение на загрузку/AI-обработку/передачу человеку — AC-блоки 4–6, FR-82 модальности image/document: media edge AD-6 — второй срез; «необязательное фото не выбирается заранее» и «отказ предлагает текстовый путь» — текстовый путь срезом покрыт, медиа-ветки нет); не строить risk-based step-up на клиентской поверхности (AC-блок 2: «когда риск требует дополнительной проверки» — конфигурации риска в срезе нет; ссылка-возможность = единственный гейт; повторное подтверждение уже подтверждённых фактов не запрашивается — их показ не вопрос; механика step-up 2-3 переиспользуется будущим срезом; failed/expired/cancelled verification → «Case без изменений» — нечему ломать: коррекция и так unverified-вход); не строить подтверждение Commitment с клиентской поверхности (AC-блок 10 «новые версии Facts ИЛИ Commitment» — Commitment-ветка второго среза: требует предъявление 2-9 и authority-гейты поверх public-поверхности; в срезе только факты); не строить resume/upload-состояния и «local и server versions» (AC-блок 8 — слабая сеть: media-зона); не строить rate-limiting/anti-bruteforce публичного маршрута и учёт попыток (256-бит random делает перебор непрактичным; честно в deferred-work: пороги/задержки — будущий срез); не доставлять URL коннектором/SMS/email (доставка = текст операторского sales-reply в существующем канале; коннектор-обвязка — не срез); не строить клиентскую идентификацию помимо токена (участник = предъявивший валидный токен; SMS-коды/логины — не срез); не роутить human_requested в Inbox 2-4 как заявку (v1 — outbox-событие + бейдж/лента панели оператора; очередь Inbox — будущий срез); не мутировать Response Owner/WI/факты действием return/human (только события; «Response Owner и writable surface не меняются неявно» AC-блок 11 — нечему меняться: машина не трогает); не пинать release manifest/profile (owner_epoch — пин 2-4-эпохи; lineage — вторичный срез при Commitment-ветке); не показывать токен/причины отказа/unverified-черновики оператора на клиентской странице; не трогать гейты/лестницы/миграции 2-1..2-9 (кроме: +1 nullable колонка client_replies.link_id, +2 слова словаря команд, +4 outbox-типа, +1 слово словаря каналов фактов — все через новую миграцию 00010, прецедент 00009); не раскрывать другие WI кейса и данные другого участника (страница — только WI ссылки и только его подтверждённые факты).

## I/O & Edge-Case Matrix

- Given кейс с действующим WI (in_work) и оператор review, when issue_continuation_link (purposes={fact_correction}, ttl 30 мин, limit 1, question, explanation), then append-only строка (link_id, пины case/WI/participant/owner_epoch, expires_at, token_hash), outbox-метаданные без токена; ответ команды несёт URL для вплетения в reply; панель показывает ссылку valid (AC-1).
- Given оператор audit-only, when issue/revoke, then 403 словами скоупа ДО стражей (прецедент M1); не-участник → 404 ×пути; чужой tenant → RLS 404 (регресс 2-1).
- Given WI терминальный (resolved/cancelled), when issue, then 400 work-rule лестницей 2-2 — продолжение не выдаётся на закрытый элемент.
- Given issue с ttl вне 5..120 либо limit вне 1..10 либо пустыми текстами question/explanation, then 400 словарём гвардов (домен до SQL).
- Given повторная issue с тем же command-ключом и материалом, then replay исходной записи (идемпотентность 2-1); с иным материалом → 409 ErrCommandKeyConflict.
- Given ссылка issued, when send_client_reply класс sales со связкой link_id и текстом-URL, then reply проходит лестницу 2-4→2-5→2-6→2-8 байт-в-байт и несёт связку — delivered-бейдж на панели (FR-16 «доставлена»); нейтральный/защищённый reply со связкой → 400 словарём; связка несуществующей/чужой ссылки → 400.
- Given валидный токен, when GET /continue/{token}, then защищённая страница: имя Tenant, «ИИ-сотрудник», explanation, краткое резюме подтверждённых фактов этого WI, открытый вопрос, форма исправления, «Позвать человека» и «Вернуться в разговор» (AC-блок 3, 12); другие WI и данные другого участника отсутствуют.
- Given неизвестный/искажённый токен либо чужой tenant в токене, when GET, then generic-страница «ссылка недействительна или истекла…» без раскрытия кейса и без различения причин (AC-блок 9); HTTP-код единый для всех причин отказа.
- Given now > expires_at (expired) ИЛИ есть строка отзыва (revoked) ИЛИ epoch кейса ≠ пину (owner_stale), when GET/POST, then та же generic-страница (клиенту) — состояние различается ТОЛЬКО на панели оператора; «старая ссылка не восстанавливается повторным запросом» — деривация read-time от текущего материала (AC-блок 9).
- Given ссылка valid, when POST /continue/{token}/correct (выбран подтверждённый факт WI, значение проходит гварды 2-2), then append-only новая неподтверждённая версия факта (channel=protected_continuation, source_ref=link_id), use-строка (потребляет лимит), outbox-метаданные без значения; PRG ?submitted=1; страница объявляет «отправлено — оператор проверит» (AC-блоки 3/10/12).
- Given повторный POST коррекции при исчерпанном лимите (consumed), then терминальная страница «материал отправлен, ссылка завершена» — повторная отправка невозможна (FR-16 «ровно одна отправка» при limit=1; двойной клик PRG честно ограничен).
- Given значение не проходит гварды факта 2-2 (тип/пустота/пределы), when correct, then re-render формы с сохранённым вводом и текстом ошибки (данные не теряются, AC-блок 12); лимит не потреблён.
- Given выбран НЕ подтверждённый факт ИЛИ факт чужого WI/кейса, when correct, then 400 словарём поверхностных гейтов; лимит не потреблён.
- Given POST human ИЛИ return при valid-ссылке, then use-строка (не потребляет лимит) + outbox-событие + текст страницы («оператор свяжется» / «возвращайтесь в разговор…») (AC-блоки 11/12); серверных мутаций WI/фактов/owner нет.

## Implementation Notes

- Токен v1 = base64url(16B tenant_id ‖ 32B crypto/rand); хранится SHA-256(32B random) — preimage не восстанавливаем из БД; entropy — единственный секрет (в отличие от HMAC content-binding 2-9: там связка контента, здесь — bearer-возможность; прецедент playback-permit AD-6). URL-алфавит base64url без padding; длина 64 символа.
- Consumption default = 1 (FR-16 «ровно одну отправку»): оператор волен поднять до 10 (многовопросный сценарий будущих срезов); считаются только принятые коррекции — события human/return свободны.
- Коррекция факта — НЕ подтверждение: новая версия в неподтверждённом состоянии; оператор подтверждает штатным путём 2-2 (машина поверхности не доверяет клиентскому значению — «unverified до требуемого подтверждения» AC-блок 7 — тот же принцип для text-входа).
- Public-маршрут и RLS: lookup строго под tenant-скоупом (scope-кандидат из токена верифицируется хешом; неверный → пустой выборке → generic-отказ);материал читается только после попадания в строку ссылки; никакого административного обхода RLS.
- Двойной клик PRG: повторный POST коррекции при limit=1 → терминальная страница «отправлено» (вторая отправка невозможна); повторный GET после submit показывает состояние consumed — страница стабильна (повторный рендер без потери).
- Связка delivery: client_replies.link_id — одна nullable колонка (прецедент policy_outcome_id 2-6 / objection_id 2-8 / commitment-пары 2-9); delivered = существование связанной reply-строки; «ожидается ответ» = valid && uses==0; «завершена отправка» = consumed; «истёк срок» = expired (FR-16 статусы — деривация панели, не хранимое состояние).
- Outbox-гигиена: 4 новых типа несут id-метаданные только; токен, тексты question/explanation, значения фактов, participant_ref — никогда (панель оператора показывает participant_ref — операторский контур, не outbox).
- a11y-срез страницы: single-column 320px; touch-цели ≥44×44px; aria-live=polite для статусов отправки/ошибок; поля с label; ошибка — текст + фокус к описанию (прецедент 2-9); «Позвать человека»/«Вернуться в разговор» — persistent header/footer действия.
- Контрольная ветка: существующие тесты 2-1..2-9 не меняются (аддитивность: +1 колонка, +2 команды, +4 outbox, +1 канал фактов; регресс байт-в-байт).
