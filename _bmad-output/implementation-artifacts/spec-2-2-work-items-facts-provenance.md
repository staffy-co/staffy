## Intent

**Problem:** Epic 2 имеет вход (2-1): Case/Conversation с единственным Work Item `untriaged`, Channel Events с запечатанным payload и таймлайном. Но кейс нельзя обслуживать: Work Item заперт в `untriaged` (CHECK миграции) — нет типа, названия, лестницы состояний и версионной классификации; несколько намерений клиента нельзя разделить (FR-12 «несколько намерений ведутся как отдельные Work Items с собственным состоянием»), а фрагменты одной задачи — объединить с сохранением порядка событий; в системе не существует ни одного факта с provenance (FR-10: источник, время, канал, статус подтверждения) — знания оператора о клиенте живут только в запечатанном payload, вне доменной модели; противоречащие значения не удерживаются (нет conflicting-семантики, нет версий); подтверждение клиента не привязывается к точной версии значения; повторная обработка того же источника дублирует сведения; операторская поверхность показывает «запрос ещё не классифицирован» без единого действия. Work Control Card (UX-DESIGN) не существует. Разделение труда «факт с provenance против предположения модели» — ядро FR-10/FR-12 — не начато.

**Approach:** Первый срез делает кейс рабочим, целиком на append-only-дисциплине (прецедент 2-1: «история не редактируется»). (1) Work Item становится версионируемым якорем: каждая команда (классификация, переход состояния, разделение, объединение, создание) пишет новую строку `work_item_versions` (actor, причина, время, вид команды); текущее состояние/type/title — производная максимальной версии, `work_items.state` удаляется миграцией; тип — только из journeys Domain Pack, закреплённого в решении, допустившем обращение: пин пака (id+version) сохраняется на Case при ingest (той же транзакцией, из RouteCandidate — та же запечатанная версия профиля, что дала владельца; обновление пака не меняет словарь открытого кейса, работа не зависит от текущей адмиссии). Лестница состояний: `untriaged → in_work → waiting|resolved|cancelled` (+ терминальные `split`/`merged` от команд разделения/объединения); переходы валидирует домен, команды несут `expected_version` (optimistic concurrency, FOR UPDATE якоря), завершение одного WI не закрывает Conversation/Case. (2) Разделение: ≥2 новые цели, каждая типизирована и названа; исходный → терминальный `split`; факты не переносятся автоматически (ре-скоуп явной командой — новой версией факта); объединение: источники → терминальный `merged` со ссылкой `merged_into`, факты ре-скоупятся версиями (строки фактов не дублируются), линки событий объединяются, порядок — по `received_at` событий; каждое разделение/объединение оспариваемо: команда спора создаёт операционное исключение (человек решает; прецедент 2-1). (3) Факты: материальный ключ (нормализованный, ≤64) + значение (канонический JSON ≤2КБ, дисциплина UseNumber 2-1) + provenance (source_type `channel_event|operator` — словарь `connector|system` зарезервирован без продюсеров; source_id — идентификатор события или ключ команды; канал; actor; observed/received раздельно); идемпотентность материальна: UNIQUE (tenant, source_type, source_id, material_key, value_digest) — точный повтор возвращает исходный исход, тот же ключ с иным значением — новая версия и конфликт; подтверждение — append-only `fact_confirmations`, привязанная к ТОЧНОЙ версии, с confirmer-типом (словарь `client|owning_system|operator_relay`; в срезе продюсер только `operator_relay` — оператор фиксирует слова клиента с evidence-ссылкой на событие кейса или нотой; client/owning_system прибудут с исходящими диалогами и write-path коннекторами); подтверждённая версия не перезаписывается — новое значение есть новая неподтверждённая версия; `conflicting` — производная на чтении (последняя версия ≠ последней подтверждённой либо ≥2 различных значения без подтверждения), авто-выбора значения нет и не будет без объявленной authority rule (Owning System / State-Authority Matrix — архитектурный артефакт, честно отложен); разрешение конфликта — подтверждение конкретной версии человеком, след остаётся. (4) Поверхность оператора: Work Control Card по каждому WI (тип/название, состояние, подтверждённые и спорные факты с обеими значениями, рекомендуемое следующее действие — словарь по состоянию, без AI), provenance раскрывается по запросу (источник, оба времени, версия, evidence), исходная запись доступна по полномочию; формы классификации/перехода/разделения/объединения/записи факта/подтверждения/линка событий с подтверждением переходов; новые события существующей сессии растят таймлайн без пересоздания фактов, привязка события к WI — только явной командой (CreateWorkItem для нового намерения в существующем диалоге; автосвязи нет как класса). (5) Доступность — прецедент 2-1: текст статусов, подтверждения переходов, предсказуемый focus, 320 px без горизонтального скролла.

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 1-9…1-14/2-1): демо-путь — принятый звонок (2-1) → оператор классифицирует WI (тип «поиск детали» из пина auto-parts запечатанного решения, название) → записывает факты из payload (материальные ключи «автомобиль», «деталь»; source: событие) → подтверждает факт со ссылкой на событие → второе событие приносит иное значение того же ключа → поле конфликтное, обе версии с provenance видны → оператор разделяет WI на два намерения → ре-скоупит факты → одно в waiting, второе resolved — диалог и кейс живы → сливает обратно со спором (исключение человеку) → replay команд идемпотентен → гонка версий отклоняется optimistic concurrency → WCC показывает всё на 320 px. Клиентские подтверждения и Owning System в контуре отсутствуют честно (нет исходящих, нет write-path коннекторов) — механика подтверждения готова к их приёму.

## Boundaries & Constraints

**Always:** Версии — истина: `work_item_versions`, `work_item_event_links`, `fact_versions`, `fact_confirmations` — INSERT/SELECT-гранты только; текущее состояние WI и факта — производная максимальной версии; конфликт — производная на чтении; никакая строка истории не обновляется и не удаляется (work_items — якорь; `state`-колонка удаляется миграцией 00002). Все команды идемпотентны по tenant-scoped ключу (прецедент connector 1-9: replay сохранённого исхода по ключу + payload digest до стражей). Optimistic concurrency: команда несёт `expected_version`, домен сверяет с максимальной версией под FOR UPDATE якоря; несовпадение/недопустимый переход — честный отказ, материал не меняется. Тип WI — только из journeys пина пака, сохранённого на Case (пин пишется при ingest из RouteCandidate расширенного фасада employee: `PackID`/`PackVersion` запечатанной версии; NULL-пин — отказ «taxonomy неизвестна», только до-миграционные данные). Материальный ключ факта — trim+lower, ≤64; значение — канонический JSON (UseNumber), ≤2КБ; UI подсказывает CriticalEntities пака, домен не ограничивает словарь ключей (факты произвольны по FR-10). Provenance обязателен: source_type/source_id/канал/actor/observed_at/received_at на каждой версии; провайдерское время никогда не подменяет время приёма (прецедент 2-1); для source `channel_event` — source_id обязан быть принятым событием этого кейса, канал наследуется от события, observed_at = провайдерское время события; для source `operator` — ключ команды в source_id, канал из словаря (9 каналов + `operator`). Подтверждение: confirmer-тип из словаря `client|owning_system|operator_relay`, evidence — событие кейса (существующее) или нота ≤200 (одно обязательно); привязка к точной версии; подтверждение версии не меняет другие версии. Завершение WI (`resolved|cancelled|split|merged`) никогда не закрывает Conversation и Case, пока есть активные WI (case остаётся `active` — закрытие кейса вне среза). Split: ≥2 цели, каждая с типом из taxonomy и названием ≤200; исходный → терминальный `split` с обратной ссылкой целей; Merge: ≥1 источник + цель, источники → терминальный `merged` + `merged_into`, факты источников ре-скоупятся НОВЫМИ версиями (строки фактов уникальны per (case, material_key), дублирования нет), линки событий переносятся на цель (append, прежние остаются), порядок событий — `received_at`; спор (Dispute) — append-only операционное исключение с correlation ID, вид `work_item_dispute`. Автоматическая связь событий с WI отсутствует (только LinkEvent/CreateWorkItem оператором). Privacy: `work_item_versions`/`work_item_event_links` — класс `case-operations`; `facts`/`fact_versions`/`fact_confirmations` — класс `case-content` (значения — контент кейса): чтение фактов — `review`/`audit` (как payload 2-1), чтение WI-метаданных — `review`/`configuration`/`audit`, управление (команды) — `review`; RLS во всех новых таблицах, TestPerimeterIntegrity синхронно; не-участник — 404 без раскрытия Tenant. UI: статусы/версии/конфликты текстом; переход состояния требует подтверждения формы; focus предсказуем после действия/ошибки; цели ≥44×44 px; 320 px без горизонтального скролла; recommended next action — фиксированный словарь по состоянию (untriaged → «классифицируйте запрос»; in_work → «запишите факты и проверьте подтверждения»; waiting → «проверьте условие возврата»; conflicting → «разрешите конфликт: подтвердите точную версию»), никогда не выдаёт себя за AI. IngestEvent 2-1 расширяется минимально в той же транзакции: пин пака на Case, version 1 начального WI (kind=create, state=untriaged), линк первого события ↔ начального WI; регресс 2-1 обязан оставаться зелёным (все 15 cases-тестов, обе таймзоны).

**Never:** Не обновлять и не удалять строки версий, подтверждений, линов и фактов (грантов UPDATE/DELETE нет; «текущее» — всегда производная). Не выбирать значение факта автоматически — ни по уверенности модели, ни по времени получения, ни по источнику: выбор значения = только подтверждение человеком с evidence; authority rules / Owning System / State-Authority Matrix не выдумываются (отложены честно). Не записывать AI confidence как подтверждение или статус факта; extraction-результаты не являются источниками фактов в срезе (AI в контуре нет; факты записывает оператор). Не создавать факты автоматически из событий. Не связывать события с WI автоматически (слабых совпадений нет как класса — прецедент «никакого merge по имени/номеру» 2-1). Не подтверждать «за клиента»: типы confirmer `client|owning_system` зарезервированы словарём без продюсеров; продюсер среза — только `operator_relay` с evidence. Не закрывать Case/Conversation завершением WI. Не переписывать подтверждённую версию (новое значение = новая версия; подтверждение остаётся на своей версии). Не принимать команды с несовпавшей версией (stale) — молчаливого слияния нет. Не показывать значения фактов без `review`/`audit`; не раскрывать Tenant не-участнику. Не расширять taxonomy: тип вне journeys пина — отказ; обновление пака не меняет словарь открытого кейса. Не выдумывать recommended next action: только словарь по состоянию. Не доверять провайдерскому времени как времени приёма. Не переносить факты автоматически при split/merge (ре-скоуп — явная версия с actor и причиной).

## I/O & Edge-Case Matrix

- Given Case с принятым событием (демо-мир 2-1, пин auto-parts на Case), when оператор классифицирует начальный WI (тип «поиск детали», название «Подбор детали на Civic», причина), then WI переходит untriaged → in_work, пишется версия 2 (actor, причина, время), исходное событие остаётся связанным (линк с ingest); повтор команды (тот же ключ) возвращает исходный исход без второй версии.
- Given классификация с типом вне journeys пина (например «уточнение услуги» Montagio на кейсе auto-parts), when домен валидирует, then честный отказ; версия не пишется.
- Given активный WI in_work, when оператор переводит в waiting с причиной, then версия пишется (actor/причина/время); Conversation и Case остаются active; недопустимый переход (resolved → waiting) и устаревший expected_version отклоняются, материал не меняется.
- Given одно обращение с двумя независимыми намерениями, when оператор разделяет WI (2 цели, каждая типизирована и названа), then исходный → терминальный `split`, создаются два новых WI in_work с обратной ссылкой; факты остаются на исходном (видны в его карточке-истории), ре-скоуп — явными версиями; завершение одного не закрывает второй.
- Given два WI одной задачи, when оператор объединяет (источник + цель), then источник → терминальный `merged` с `merged_into`, факты ре-скоупятся новыми версиями (строк фактов не прибавляется), линки событий объединяются на цели, порядок — received_at; спор создаёт операционное исключение (корреляция, вид work_item_dispute), видимое оператору.
- Given оператор читает payload события и записывает факт («автомобиль» = `{"model":"Civic","year":2020}`, source channel_event, event_id), when команда исполняется, then версия 1 факта хранит полный provenance (канал события, actor-оператор, observed = провайдерское время, received = часы приёма); точный повтор (тот же source_id+ключ+digest) — replay исходного исхода, второй версии нет.
- Given тот же материальный ключ от другого источника с иным значением (`{"model":"Civic","year":2019}`), when записывается вторая версия, then обе версии и их provenance удерживаются, поле помечается `conflicting` (производная), авто-выбора нет; WCC показывает оба значения со статусами.
- Given спорное значение, when оператор подтверждает точную версию (confirmer operator_relay, evidence — событие кейса, где клиент назвал год), then append-only подтверждение привязано к этой версии, конфликт снят (поле больше не conflicting), истории обеих версий доступны.
- Given подтверждённая версия, when третий источник приносит иное значение, then новая неподтверждённая версия пишется, подтверждённая не перезаписывается (её подтверждение остаётся), поле снова conflicting.
- Given новое событие существующей сессии (продолжение 2-1), when событие принято, then таймлайн растёт, нового WI нет, факты не пересоздаются; оператор создаёт новый WI (новое намерение) и линкует событие явной командой — автосвязи нет.
- Given две конкурентные команды над одним WI (один expected_version), when исполняются, then ровно одна применяется, вторая отклоняется optimistic concurrency (материал консистентен).
- Given пользователь другого Tenant или без полномочий, when читает факты/WI/подтверждения, then RLS и серверная авторизация блокируют (404 без раскрытия Tenant); значения фактов — только `review`/`audit`.
- Given Case, созданный до миграции (NULL pack pin), when оператор пытается классифицировать, then честный отказ «taxonomy неизвестна» (только до-миграционные тестовые данные; новых таких кейсов не бывает).
- Given Work Control Card на клавиатуре/screen reader/320 px, when оператор работает, then тип/название/состояние/версии/конфликты текстом, переход — с подтверждением, focus предсказуем, горизонтального скролла нет, цели ≥44×44 px.

**Acceptance Criteria:**
- Given начальный WI untriaged, when оператор классифицирует, then тип из taxonomy пина, название, состояние и версия с actor/причиной/временем; исходное событие связано; переклассификация — новая версия, история не переписывается.
- Given несколько независимых намерений, when разделяет, then отдельные WI с собственными состояниями/фактами; завершение одного не закрывает остальные; Conversation/Case живы при активных WI.
- Given фрагменты одной задачи, when объединяет, then оба события и их порядок сохранены, факты не дублированы, объединение прослеживается и оспаривается (исключение человеку).
- Given факт из события, when записывается, then полный provenance (тип/значение/источник/канал/actor/оба времени/скоуп/версия/статус); недостаточный provenance — `unverified`; AI confidence нигде не подтверждение.
- Given подтверждение, when оператор фиксирует слова клиента со ссылкой на событие, then подтверждение привязано к точной версии с evidence; изменение значения — новая версия; прежнее значение и подтверждение доступны в истории.
- Given два источника с разными значениями, when оба сохранены, then обе версии и provenance удержаны, поле `conflicting`, авто-выбора нет; разрешение — подтверждение человеком.
- Given повторная обработка того же источника, when создаётся факт, then source key и digest предотвращают дублирование; тот же ключ с иным значением — конфликт; подтверждённый факт не перезаписывается.
- Given переход в waiting/resolved/cancelled, when разрешён состоянием, then actor/причина/время/версия сохранены; недопустимый или устаревший переход отклонён optimistic concurrency.
- Given новое событие известной сессии, when принято, then таймлайн показывает продолжение без пересоздания подтверждённых фактов; состояния WI видимы; автосвязи нет.
- Given Work Control Card, when оператор просматривает, then намерение/состояние/подтверждённые и спорные факты/следующее действие; provenance по запросу; исходная запись доступна по полномочию.
- Given клавиатура/screen reader/320 px, when оператор работает, then связи/версии/состояния/конфликты текстом, переходы с подтверждением, focus предсказуем, горизонтального скролла нет.

## Implementation Notes

- Версии = истина: чтения JOIN LATERAL максимальной версии; якорь work_items под FOR UPDATE сериализует команды (optimistic concurrency по expected_version); идемпотентность команд — прецедент connector 1-9 (replay исхода по ключу до стражей).
- Пин пака на Case пишется при ingest из RouteCandidate (расширение фасада: PackID/PackVersion из Refs запечатанной версии) — той же транзакцией; journeys разрешаются фасадом PackJourneys (packs.Get — манифесты неизменяемы в бинарнике, TOCTOU нет).
- IngestEvent расширяется минимально (version 1 + линк первого события + пин); регресс 2-1 — зелёный обязателен (15 тестов, обе таймзоны).
- Канонизация значения факта — тот же код, что payload 2-1 (UseNumber, точность чисел); digest по каноническим байтам.
- Material key: trim+lower, ≤64; UI подсказывает CriticalEntities пака (деталь, артикул, автомобиль) — домен словарь не ограничивает.
- Evidence подтверждения: событие кейса (проверяется существованием) или нота ≤200; confirmer `operator_relay` — единственный продюсер среза (client/owning_system — словарь без продюсеров, честная пометка).
- Conflicting-деривация: последняя версия ≠ последней подтверждённой ИЛИ (нет подтверждений И ≥2 разных digest); вычисляется на чтении, не хранится.
- Фикстура journeys: мир 2-1 + классификация + факты + конфликт + split/merge на 320 px (паттерн cases_fixture).
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...` (UTC + TZ=Europe/Moscow), `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`.

## Design Notes

- Чистый append-only: ни одной UPDATE/GRANT-операции на новом материале; «текущее» и «конфликт» — производные; подтверждение — отдельная таблица, привязанная к точной версии (AC-5 исполняется структурой, а не статусом в строке версии).
- Пин пака на Case — provenance-решение: словарь типов стабилен на весь жизненный цикл кейса, работа над кейсом не зависит от текущей адмиссии (маршрут может быть отозван — обслуживание продолжается, принцип «существующие обязательства продолжаются»).
- Честные вечные границы среза: confirmer-типы client/owning_system без продюсеров (исходящие диалоги и write-path коннекторы — будущие stories); extraction-источники фактов (AI в контуре нет); authority rules/Owning System/State-Authority Matrix (архитектурный артефакт — deferred-work); автосвязь событий (2-3 — человек); закрытие кейса; open questions/options/Commitments (2-6/2-9 — скоуп-модель готова); recommended next action — словарь, не интеллект.
- Связь с deferred-work 2-1: ingress_rejections для нераскодируемых тел, provider-клеймо, envelope по измеренным значениям — не трогаются (вне 2-2).
