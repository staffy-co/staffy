## Intent

**Problem:** Между закрытым доказательством применимости 4-4 (FitmentDigest — «точная версия доказательства», контуры 4-5..4-9 обязаны пиннить) и будущим заказом 4-6 коммерческие условия НЕ существуют как объект: менеджер видит предложения фактически подключённых поставщиков в интерфейсе ABCP (маршрут parts_catalog_abcp НЕ допущен реестром 4-1: OQ-5/AG-4 open, AdapterImplemented false), результат нигде не записывается и не трассируется (FR-53: «читать текущие цену, наличие, поставщика и срок»; проверяемое следствие «устаревшая цена или наличие не переиспользуются без нового чтения»), сравнение вариантов не группируется по типу связи и подтверждённой применимости (AC-5), приоритеты клиента (бюджет/бренд/срок — подтверждённый материал запроса 4-3: part.budget, part.brands, part.deadline) не применяются детерминированной версионированной политикой (AC-6), выбор клиента не фиксируется с точными версиями четырёх входов (AC-13), возраст предложения и изменение цены/наличия/срока/состава не помечают зависимые результаты устаревшими (AC-9/AC-10), позиция без актуальных предложений неотличима от доступной к заказу, а старая цена может повторяться как действующая (AC-12). Comparison Policy (валюты, допустимый возраст предложения, критерии и тай-брейки ранжира, размер ограниченного набора) нигде не объявлена версионированно — риск зашить политику магазина в код ядра.

**Approach:** Модуль internal/cases — сравнение есть ВЫВОД над записанным материалом менеджерского запроса условий: спека добавляет ComparisonPolicy в Domain Pack auto-parts@6.0.0 (валюты + допустимый возраст предложения + критерии ранжира + тай-брейки + ограниченный набор — приходит в cases через существующий структурный порт PackTaxonomy +1 метод PackComparisonSchema по прецеденту PackFitmentSchema 4-4), предложение записывается append-only таблицей 00022_supplier_offers (материальные поля AC-2 + пины ProfileDigest/PartRequestDigest обязательны + FitmentDigest опционален — точные версии входов; прецеденты append-only столов 00007/00013/00020), выбор клиента — append-only таблицей 00023_selection_snapshots (пины ВСЕХ ЧЕТЫРЁХ дайджестов AC-13 + количество + известная клиентская сумма арифметикой), домен offers.go выводит сравнение read-time (GuardSupplierOffer/GuardClientSelection со словарями пака + DeriveComparison — группировка по типу связи и подтверждённой применимости, детерминированный ранжир с объясняющими словами, лестница состояний {current, stale, unknown} со словами изменений и повторного запроса; OfferDigest/SelectionDigest — точные версии для контуров 4-6..4-9). Менеджерский путь: панель рекомендует слово offers_research — задача менеджеру идёт СУЩЕСТВУЮЩЕЙ машиной 2-13 (словарь причин +1 слово, SQL-зеркало 00024 по прецедентам 00019/00021) с материалом 2-14; предложения и выбор менеджер фиксирует новыми командами записи (PRG-формы на странице кейса + JSON API по прецеденту операторских маршрутов записи 4-4). Поверхность — панель «Предложения и сравнение» после панели «Применимость» 4-4.

**Ядро честности среза:** автоматического обращения к поставщикам НЕТ и НЕ заявляется — маршрут parts_catalog_abcp НЕ допущен (OQ-5 safe state: без inferred данных; AG-4: без реальных credentials); продюсер записи — оператор-менеджер, переносящий фактические условия подключённых поставщиков с полным материалом трассируемости (источник, идентификатор записи источника, версия, время — дисциплина 2-7). Клиентская цена — ТОЛЬКО записанная разрешённая цена ABCP: модель НЕ рассчитывает скидку, наценку или итоговую стоимость (AC-3); известная сумма = арифметика количества и записанной цены, всегда со словом «без доставки и сбора — окончательная стоимость не рассчитана» (AC-4). Закупочная цена — внутренние данные: записи принадлежит, клиентскому материалу НЕ принадлежит (AC-2 — структурно: поле отсутствует в клиентских формах домена + зонд). Наличие предложения НЕ изменяет статус каталогической применимости (AC-1 — DeriveFitment 4-4 не тронут, сравнение читает его вывод); позиция рекомендуется ТОЛЬКО при proven-применимости и подтверждённом критерии с объяснением «почему вариант соответствует указанным приоритетам» (AC-6/AC-7); «лучший» без определённого основания НЕ объявляется — короткий уточняющий вопрос либо ограниченный разрешённый набор; неподтверждённые заявления о качестве, ресурсе или превосходстве НЕ создаются (AC-5 — зонд маркетинговых слов в прод-файлах среза). Срок — оценка поставщика, НЕ обещание магазина и НЕ подтверждённый факт исполнения (AC-8, слово при каждой дате). Возраст сверх TTL пака → stale с повторным запросом цены/наличия/срока (AC-9); изменение цены/наличия/срока/состава позиции → слово изменений + «требуется новая точная версия подтверждения» (AC-10); старая цена НЕ повторяется как действующая (AC-12). Выбранного количества нет у одного поставщика → разрешённые альтернативы словом, разбие́ние заказа между поставщиками и изменение количества без явного правила и подтверждения клиента НЕ выполняются (AC-11). Selection Snapshot пиннит точные версии ВСЕХ четырёх входов (AC-13) и НЕ создаёт ABCP Order, НЕ отправляет заказ поставщику (fence OQ-3/OQ-4 — SPINE: supplier_form/send отсутствует в Action Catalog; контур 4-6 строит Business Action create_abcp_customer_order по своему подтверждению). Молчаливых исправлений НЕТ ни в одном пути: guard-проверки отказывают словами со словарём, слова вне словарей невозможны (compile-time словари домена + SQL-CHECK + контракт-тест зеркал).

## Implementation Notes

- Решение модуля: коммерческие условия — материал кейса (cases), политика сравнения — материал Domain Pack (employee/packs): связка через существующий структурный порт PackTaxonomy (прецедент PackFitmentSchema 4-4); ядро НЕ знает словарей магазина.
- Supplier Offer — записываемый материал, НЕ чистый вывод (как Fitment Evidence 4-4): менеджерский запрос условий — событие мира; потому CREATE TABLE 00022 (прецеденты append-only 00007/00013/00020); суперсид записи поставщика — НОВЫМ номером per (позиция, поставщик), обновлений и DELETE нет. ДВА объекта среза (предложение + выбор) — честное отличие от прецедента 4-4 (один объект): story несёт два РАЗНЫХ материала — условия поставщика и выбор клиента; оба append-only.
- Пины точных версий входов: предложение несёт ProfileDigest (4-2) и PartRequestDigest (4-3) обязательно, FitmentDigest (4-4) опционально (предложение может существовать до доказательства — записывается честно, НЕ рекомендуется); DeriveComparison сверяет пины с текущими дайджестами — AC-10 «изменились цена, наличие, срок или состав позиции» исполняется read-time без триггеров; GuardClientSelection требует ВСЕ четыре пина текущими ДО записи (AC-13).
- Клиентская цена: модель НЕ рассчитывает скидку/наценку/итог (AC-3) — единственная арифметика среза: известная клиентская сумма = количество × записанная клиентская цена (АС-13 «фиксирует количество и известную клиентскую сумму»), всегда со словом «без доставки и сбора — окончательная стоимость не рассчитана» (AC-4); доставка/сбор НЕ оцениваются и НЕ обещаются.
- Закупочная цена (AC-2): поле записи — внутренние данные магазина; клиентский материал домена НЕ содержит поля структурно (клиентские формы без него + зонд); панель оператора показывает её со словом «внутренние данные: клиенту не раскрывается»; «согласно полномочиям» — запись менеджера с полными полномочиями, поле опционально (отсутствие = не видел/не записал, НЕ ноль).
- Ранжир (AC-6/AC-7): детерминированная тотальная последовательность — первичный критерий из подтверждённого материала запроса (budget → цена asc; brands → принадлежность списку; term → срок asc), тай-брейки пака price→term→brand(алфавит)→supplier; сортировка НЕ зависит от закупочной цены и позиции записи (скрытая выгода поставщика ≠ интерес клиента — зонд); без критерия — вопрос либо ограниченный набор MaxVisibleVariants, «лучший» НЕ объявляется.
- Voice-блок AC-14: панель несёт короткое слово для телефона (ключевые различия до 3 + рекомендуемый по подтверждённым критериям вариант + предложение полного сравнения в разрешённом канале); один Case при переходе — существующая машина кейса, новых клиентских поверхностей срез НЕ строит.
