## Intent

**Problem:** слово-обещание из 4-9 — «отмена — слово-граница контура 4-10» и «спор/recovery — существующие контуры 2-13/3-8» — механики обслуживания НЕ существует: клиент, обратившийся повторно по СУЩЕСТВУЮЩЕМУ заказу, не зафиксирован нигде (FR-62 «повторное обращение связывается с существующим Order» — пути нет: запрос клиента о статусе/изменении/отмене/возврате/споре не сохраняется как материал); поиск заказа по названному клиентом признаку НЕТ (внешние ID живут в квитанциях 4-6 / перечитах 4-8 / фактах 4-9, но lookup-команды не существует — оператор ищет глазами); гейт раскрытия «до проверки личности не раскрывать наличие, состав или состояние» (AC-1) не существует как машина (assurance 2-3 живёт в кейсе, но НИЧТО не связывает его с показом заказного материала — оператор может пересказать статус без всякой записи проверки); различение отмены «запрос / подготовленное действие / подтверждение / невозможность» (AC-7) не существует словами (отмена вообще не произносится: catalog декларирует семантику, слов для клиента нет); «знание номера заказа — не доказательство» (AC-3) не подкреплено структурой (номер ищется и показывается без гейта); «отсутствие результата не раскрывает сведения о другом клиенте» (AC-2) не сформулировано; клиента и оператора нечем обслуживать повторное обращение как один контур (a11y AC-16).

**Approach:** модуль action (якорь — операция create_abcp_customer_order и её append-only окружение, прецедент 4-9). Пять частей: (1) миграция `migrations/action/00009_order_servicing_requests.sql` — 1 append-only таблица запросов обслуживания с UNIQUE полного ключа (tenant, case, actor, intent, identifier_kind, identifier_value, proof_state) — повтор команды = идемпотентный replay BY KEY; (2) домен `internal/action/domain/order_servicing.go` — словари compile-time (8 интентов + слова-границы; 2 типа признаков поиска + слова источников; 3 исхода поиска; proof-состояния — зеркало словаря 2-3 BY NAME; 2 исхода раскрытия) + DeriveServicingClientWords (read-time: verified → client_words живой проекции 4-9 + слова интента; иначе — слово гейта) + DeriveCancelFeasibility (4 состояния над OrderStatusProjection) + гварды; (3) app-сервис `internal/action/app/order_servicing.go` — ОДНА команда RecordOrderServicingRequest (rights gate Review → живой кейс → живое чтение assurance кейса обращения через НОВЫЙ порт AssuranceSource → lookup BY KEY живого материала (квитанции ∪ перечиты при abcp_client_order_id / факты при supplier_order_id) → гварды → идемпотентный replay BY KEY → append с proof-пинами) + OrderServicingView (список запросов кейса + живые деривации слов); (4) панель «Обслуживание заказа» на странице кейса после «Статуса заказа» + форма записи запроса + JSON-маршрут + PRG-форма + OpenAPI-зеркала; (5) интеграционная eval-матрица AC-14 поимённо + journeys z47.

**Ядро честности среза:** обслуживание — ЗАПИСАННОЕ событие, не автоматический ответ (каналы не подключены OQ-1/OQ-2 — клиентских исходящих НЕТ, оператор пересказывает client_words руками); запрос append-only всегда (даже без проверки личности — «фиксирует запрос, но не утверждает результат» AC-6), но РАСКРЫТИЕ (включая факт наличия заказа) гейтится живым verified уровня кейса обращения — proof-пины копируются в запись (scope/уровень/время — AC-4), Caller ID/имя профиля/знание номера НЕ доказательство структурно (гейт читает только verification_records); lookup — ТОЧНЫЙ поиск BY KEY над материалом контура (перечисления НЕ существует: исходы unique_match/not_found/ambiguous BY NAME; not_found — generic слово без раскрытия; ambiguous — слово без перечня); «через разрешённый Connector» — OQ-18/AG-4 слово-граница (адаптеров чтения нет, lookup читает только записанный контуром материал); поиск по телефону НЕ существует (OQ-16: case-scoped only — сопоставление личности через кейсы не строится); отмена различается ЧЕТЫРЬМЯ состояниями read-time и НИКОГДА не обещается (каталог без cancel — OQ-3 fence; квитанции нет — не подтверждено; факты поставщика → «не отменяется как обычное редактирование — человеку»); изменение — ручной контур AG-4, утверждение об изменении НЕ делается до человеческого подтверждения; claim/dispute — режимы словами + существующие контуры 3-8/2-13, юридическая ответственность не признаётся; повторное обращение НЕ создаёт новую операцию заказа (FR-62 структурно: единственный пишущий путь — append запроса); машины 2-3/2-13/3-8/4-6..4-9 НЕ трогаются (новая панель после «Статуса заказа», чтение их материала существующими портами).

## Boundaries & Constraints

**Always:** таблица запросов append-only — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; CHECK-словари интентов/типов/исходов = compile-time словари домена (миграция зеркалит); UNIQUE полного ключа запроса (tenant, case, actor, intent, identifier_kind, identifier_value, proof_state) — повтор команды = сохранённый исход (идемпотентность BY KEY, прецедент фактов 4-9); proof-пины копируются из ЖИВОГО чтения assurance при записи (уровень/метод последней passed записи/время выдачи/срок — два времени никогда не смешиваются, прецедент 2-7/4-9); якорь записи — живой кейс обращения (RLS) + найденная операция заказа (resolved_operation_id FK, nullable — не найден/неоднозначен); запись запроса — actor с Review-скоупом (живая грант-матрица identity), серверная истина актёра; lookup — точное совпадение BY KEY в одной транзакции записи, tenant-scoped, RLS; раскрытие — производная proof-пина записи И живой проекции 4-9 при чтении панели (client_words перечитываются, не сохраняются); все слова — словари домена; OpenAPI зеркалит; панель собирает ТОЛЬКО чтением живых панелей/портов; регресс — build/vet/unit + интеграция ×2 TZ + journeys + скан.

**Never:** НЕ строить клиентскую поверхность доставки (Jivo/телефон не подключены — OQ-1/OQ-2: уведомления/исходящие/проактивные сообщения НЕ отправляются, панель = единственная поверхность, прецедент 4-9 Never; Commitment-машина 3-3 не трогается; доставка/прочтение не фиксируются); НЕ строить автоматическую AI-классификацию интентов (интент и слова клиента фиксирует оператор — автоматического клиентского пути в срезе НЕТ); НЕ строить lookup через Connector/адаптеры чтения ABCP/1С/поставщика (AG-4/OQ-18: поиск читает ТОЛЬКО материал контура — квитанции диспетчера, перечиты 4-8, факты 4-9); НЕ строить поиск по телефону/email/перебор признаков (OQ-16: cross-case профиль не строится — case-scoped only; «чужой телефон» = честное слово-граница); НЕ показывать перечень заказов никогда (исходы unique_match/not_found/ambiguous; ambiguous — слово «признак соответствует нескольким заказам — уточнение у менеджера» БЕЗ списка; not_found — generic слово, не раскрывающее существование чужих заказов); НЕ раскрывать до verified НИЧЕГО заказного (включая факт наличия: клиентские слова неуверифицированного запроса = слово гейта + методы канала, без исхода поиска); НЕ считать Caller ID/имя профиля/знание номера доказательством (гейт читает только verification_records 2-3); НЕ обещать отмену (четыре состояния различаются словами; подготовленное действие/подтверждение = «не существует» с пинами: каталог без cancel — OQ-3 fence, квитанции нет); НЕ исполнять отмену/изменение заказа (ручной контур AG-4: менеджер в ABCP; коррекция подбора — контур 4-8; «затронувший поставщика» — факты {formed, sent} 4-9 → «человеку»); НЕ признавать юридическую ответственность/НЕ обещать компенсацию (claim/dispute — слова + контуры 3-8/2-13); НЕ объединять профили/кейсы (связывание обращений — контуры 2-3/2-10, не этот срез); НЕ трогать замороженные машины: 2-3 верификации, 2-13 handoff, 3-6 лестницу диспетчера, 3-8 recovery, 4-6..4-9 панели (новая секция после «Статуса заказа»; слово 4-9 «отмена — контур 4-10» исполняется панелью обслуживания); НЕ показывать закупочные цены в клиентских словах (ценовых полей в servicing-вью 0 — зонд, наследование фенса 4-9); НЕ расширять словари рантаймом; НЕ создавать operation/RUN-путём (FR-62: повторное обращение не создаёт новую операцию — зонд count операций unchanged).

## I/O & Edge-Case Matrix

- Given клиент назвал номер заказа (ABCP), оператор (Review) записывает запрос intent=order_status, identifier abcp_client_order_id=значение, when команда, then lookup BY KEY по квитанциям диспетчера 4-6 ∪ перечитам 4-8 (оба источника — раздельные пины BY NAME при показе); ровно одна операция → resolved_operation_id записан, исход unique_match; proof-пины записаны; повтор той же команды тем же оператором при том же proof-состоянии — идемпотентный replay (второй записи нет — UNIQUE ключа AC-9-дух).
- Given то же значение найдено у ДВУХ разных операций (расхождение внешних ID разных кейсов), when lookup, then исход ambiguous — слово «признак соответствует нескольким заказам: уточнение у менеджера» БЕЗ перечня; resolved_operation_id пуст; запрос записан (AC-2: перечисление не существует).
- Given номер не существует в материале тенанта, when lookup, then исход not_found — generic слово «заказ по названному признаку не найден: проверьте номер с клиентом или передайте менеджеру»; ответ НЕ подтверждает и НЕ опровергает существование заказов другого клиента (AC-2/AC-12); запрос записан.
- Given proof-состояние кейса обращения НЕ verified (none/basic/step_up) на момент записи, when команда, then запрос записан (append-only — «фиксирует запрос» AC-6), поле disclosure=denied, proof-пины записаны (уровень фактический); клиентские слова = слово гейта «раскрытие требует проверки личности (уровень verified); разрешённые методы канала: …» + fallback-слова 2-3; исход поиска в клиентских словах ОТСУТСТВУЕТ (факт наличия не раскрывается — AC-1; операторская панель показывает исход оператору — его Review-право).
- Given клиент прошёл проверку (verification passed, уровень verified, срок жив), оператор повторяет запрос (тот же intent/признак), when команда, then НОВАЯ запись (proof_state в ключе изменился: none→verified — replay НЕ срабатывает, обе записи в истории); disclosure=allowed; клиентские слова = живая деривация client_words OrderStatusView 4-9 найденной операции (стадии/свежесть/следующий шаг/три слова срока/ограничения) + слово интента (AC-5: только подтверждённые сведения из Order Status Projection).
- Given verified запись просрочена (срок истёк — живая деривация 2-3), when запись запроса, then proof-пины уровня none (просроченная запись в assurance не считается — словарь 2-3), disclosure=denied со словом гейта; оператору — панель assurance кейса рядом (существующая машина 2-3 не тронута).
- Given клиент просит объяснить статус/условия (intent=clarification) при verified, when панель, then клиентские слова = client_words проекции (факты системы) + слово «объяснение: факты системы отделены от оценки (три слова срока 4-9); при неизвестном — проверка человеком или согласованный callback (контур 2-13/2-16)» (AC-6: понятным языком, факты vs оценка).
- Given intent=cancel при verified и фактов поставщика НЕТ (нет formed/sent 4-9), when деривация, then CancelFeasibility четыре состояния: «запрос на отмену записан (append-only)» / «подготовленное действие не существует: cancel отсутствует в каталоге действий (OQ-3 fence; декларация 4-1 — отмена подготовки отдельная команда до отправки, которой нет)» / «подтверждённая отмена не существует: квитанции отмены нет — не подтверждено; отмена не обещается» / «невозможность как обычное редактирование: не определена — фактов поставщика нет»; панель показывает слово «отмену выполняет менеджер вручную (AG-4): до человеческого подтверждения заказ НЕ считается отменённым» (AC-7).

## Implementation Notes

- Решение модуля: servicing живёт в ACTION-модуле (якорь — операция заказа и её append-only окружение, прецедент 4-9); assurance читается ЖИВЫМ порт-чтением AssuranceSource (composition-root адаптер поверх cases API по прецеденту CaseMaterialSource — модуль не тянет cases-домен в import-graph: зонд AD-10/import-graph шага-05).
- Identity Proof Gate — производная ЗАПИСИ (proof-пины скопированы при записи: «scope, уровень и время проверки сохранены» AC-4 — материал не переписывается задним числом), раскрытие слов — производная ЧТЕНИЯ (client_words перечитываются живой проекцией 4-9 — не сохраняются). Гейт НИКОГДА не выводится из заявленного значения/Caller ID — только из verification_records 2-3 (структурный зонд: клиентские слова неуверифицированного запроса не содержат исхода поиска).
- Lookup BY KEY — не поиск-перечисление: исходы {unique_match, not_found, ambiguous}; «через разрешённый Connector» — OQ-18/AG-4 слово-граница (lookup читает только записанный контуром материал: внешние ID квитанций диспетчера 4-6, перечитов 4-8, фактов 4-9 — три источника раздельно BY NAME); поиск по телефону — OQ-16 слово-граница (case-scoped only).
- Идемпотентность повтора: UNIQUE полного ключа (tenant, case, actor, intent, identifier_kind, identifier_value, proof_state) — повтор команды при том же состоянии доверия = сохранённый исход (прецедент фактов 4-9: duplicate → перечитка → честный реплей); ИЗМЕНИВШЕЕСЯ состояние доверия (none→verified) = НОВАЯ запись (обе в истории — лестница доверия видна).
- CancelFeasibility — read-time над OrderStatusProjection: «затронул поставщика» = существуют факты {formed, sent} 4-9 (человеческие записи BY NAME); «подготовленное действие не существует» пинится каталогом (OQ-3 fence + декларация 4-1 + deferred-work №215 — исполнителей отмены нет); «подтверждённая отмена не существует» — квитанции нет; запрос записан — append-only. Отмена НИКОГДА не обещается и НЕ исполняется (ручной контур AG-4).
