## Intent

**Problem:** слово-обещание из 4-7 «запущена коррекция — контур 4-8» — механики НЕТ: blocked-решение проверки пишет позиции+причину и слово, но Correction Work Item не существует ни в одной таблице (нет owner/deadline/лестницы), «заказ остаётся заблокированным от дальнейшего продвижения» нечему держать (assign новой задачи проверки 4-7 открыт; авторизация НОВОГО create_abcp_customer_order по пересобранной версии технически возможна — single_use потребляется на подтверждение, не на кейс: второй заказ не блокирован ничем, AC-9 «новый дублирующий заказ не создаётся» не держится структурно), состояние pending_correction не существует словами ни на одной панели, «прежде Human Verification Receipt становится неприменим» при коррекции не выводится (неприменимость 4-7 — только по дайджесту). Экрана коррекции не существует: менеджер не имеет одной собирающей поверхности с заблокированными позициями/причиной, рекомендуемым объяснением клиенту (различия прежний→новый текстом + «прежде вариант поставщику не отправлялся»), путём пересборки, формой записи перечита и итогом. Замена не связывается с исходом: новая версия предложения 4-6 строится EDIT-лестницей, но связь «коррекция ↔ подтверждённая клиентом версия» и валидация «перечит сверяет живой состав с подтверждённым» не существуют — повторное использование старого Confirmation не блокируется на этом пути (AC-15). Итог коррекции (человеческие действия/клиентский ответ/итог/длительность — материал пилотных метрик) не записывается.

**Approach:** модуль action (якорь — committed-операция заказа + blocked-событие задачи проверки; обе сущности живут в action-модуле). Восемь частей: (1) домен `internal/action/domain/order_correction.go` — типы, гварды поимённой матрицы, словари compile-time (дедлайны {correct_4h, correct_1d}, причины прекращения {client_refused, not_needed, abandoned}, исходы {corrected, ceased}), слова состояний/границ, DeriveOrderCorrectionState (read-time: последний opened → owner/deadline/эпоха; reread/ceased закрывают; overdue по часам — авто-действий структурно нет) + DeriveOrderCorrectionDiff (пин материала операции → живая деривация, по позиции); (2) миграция `migrations/action/00007_order_corrections.sql` — 2 append-only таблицы с RLS/CHECK-зеркалами; (3) app-сервис 4 команд (open/reassign/reread/cease) с CAS эпохи и переносом материала blocked-события SQL-истиной; (4) ДВА структурных гейта продвижения (assign 4-7 отказ 409 при открытой коррекции; авторизация 3-5 нового заказа отказ ДО транзакции); (5) экран «Коррекция заказа» на странице кейса (карточка/дифф/рекомендуемое объяснение/формы); (6) маршруты JSON+PRG; (7) OpenAPI-зеркала; (8) интеграционная eval-матрица AC-15 поимённо + journeys z45.

**Ядро честности среза:** коррекция — append-only Work Item над заблокированным решением, НЕ переписывание истории (исходная квитанция/подтверждения/проверки читаются, пины переносятся поимённо); изменение ABCP-заказа — ТОЛЬКО ручное действие менеджера в контуре магазина: Staffy не изменяет заказ, не создаёт новый (структурно: гейт авторизации) и не отправляет поставщику (supplier-send не существует); перечит — слова менеджера (Staffy не читает ABCP, AG-4), но закрытие corrected требует НОВОЕ подтверждение клиента точной версии и живую сверку состава с ним (скрытое ухудшение запрещено структурно: расхождение = отказ + явные различия); прежде подтверждение не переносится (superseded BY NAME); заказ возвращается на проверку только НОВОЙ задачей (лестница verification_no, прежняя проверка не переиспользуется); отмена заказа — контур 4-10 словом-рекомендацией, отсутствие согласия клиента не превращается в замену.

## Boundaries & Constraints

**Always:** обе таблицы append-only — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; CHECK-словари исходов/дедлайнов/причин = compile-time словари домена (миграция зеркалит); UNIQUE (tenant, case, correction_no) и UNIQUE (tenant, case, correction_no, event_no) — монотонность, история никогда не правится; частичный UNIQUE одной открытой коррекции на операцию; якорь — committed-операция create_abcp_customer_order + ПОСЛЕДНЯЯ закрытая blocked задача проверки (позиции/причина переносятся из blocked-события одной транзакцией чтения SQL-истиной); open/reassign — actor с Review-скоупом (живая грант-матрица identity), owner — участник с Review-скоупом; reread/cease — actor=owner коррекции (серверная истина), ожидание assignment-эпохи — CAS под локами; reread валидирует: пин подтверждённой версии {proposal, version, confirmation} — версия последняя ∧ подтверждена ∧ живая DeriveOrderCommitmentMaterial == дайджесту версии (тот же код ре-деривации, что лестница 4.5/забор 4-7 — reuse, НЕ новый шаг dispatch); гейт авторизации — ДО транзакции резервирования (ничего не потребляется, superseded-лестница 3-4 не задета); гейт assign 4-7 — теми же словами, что панель; экран — сборка ТОЛЬКО чтением живых панелей/портов и материала операции (новых записывающих путей данных нет, кроме 4 команд); все слова — словари домена; OpenAPI зеркалит; регресс — build/vet/unit + интеграция ×2 TZ + journeys + скан.

**Never:** НЕ строить изменение ABCP-заказа действием/адаптером/командой каталога (AG-4: change-команды в живой декларации 4-1 НЕТ — каталог НЕ расширяется; адаптер nil; OQ-3 safe state = manual reread + human receipt; «Staffy не имитирует изменение заказа» — слово + структура); НЕ создавать новый заказ при открытой коррекции (гейт авторизации 3-5 — ДО транзакции; лестница 3-6 НЕ тронута: никаких новых шагов dispatch, порядок шагов неприкосновенен); НЕ строить отмену заказа (контур 4-10: cessation client_refused = запись + слово-рекомендация; Autonomy Class отмены — вне среза); НЕ строить фиксацию канала связи с клиентом и доставку уведомлений (Jivo/телефония OQ-1/OQ-2 открыты; контакт — ручной контур магазина; рекомендуемое объяснение — материал панели; прецедент 2-13 Never); НЕ строить перечит ABCP адаптером (AG-4: читающий адаптер НЕ wired — перечит записывается словами менеджера); НЕ переносить прежнее Confirmation автоматически (AC-7: закрытие corrected требует пин НОВОГО подтверждения; старое = superseded BY NAME — отказ); НЕ строить авто-закрытие/воркеры/таймеры/backup-переключатель (AG-4/AD-14: overdue — read-time слово; fallback = явный reassign владельцем); НЕ строить отдельную replacement-сущность (замена = новая версия предложения 4-6 EDIT-лестницей; связь — через запись перечита; «ручное мнение без доказательства не выдаётся за каталогичность» — существующие гварды 4-4/4-5/билдера 4-6 не расшряются); НЕ строить новые механизмы версионирования входов (AC-3 исполняется существующей версионирующей машиной 4-2..4-5: новые версии Vehicle/Part Request — разрешённым процессом оператора; «stale» прежних Fitment/Offers/Selection/Confirmation — существующие read-time живые деривации vs пины); НЕ превращать единичную коррекцию в глобальное правило подбора (Domain Pack не тронут); НЕ строить аналитику/метрики (события = материал, расчёт — вне среза); НЕ трогать замороженные машины: таблицы/словари/команды 2-13, лестницу 3-6 (persist-квитанции тоже), термы владения 2-4, persist 3-6, команды 2-15 (операторская коррекция фактов — ДРУГОЙ контур, различие именами order_correction); НЕ мутировать записи операций/квитанций/проверок (пины читаются); НЕ расширять словари рантаймом; НЕ показывать закупочную цену без Commercial-скоупа; supplier-send — НИКОГДА (fence OQ-3: «passing OQ-3/OQ-5 does not authorize supplier-send»; полей/действий/маршрутов отправки не существует).

## I/O & Edge-Case Matrix

- Given кейс с committed-квитанцией create_abcp_customer_order и ПОСЛЕДНЕЙ закрытой blocked задачей проверки (позиции/причина записаны), when open_order_correction (actor с Review-скоупом; owner — участник с Review-скоупом; deadline словом {correct_4h, correct_1d}), then одна транзакция: строка order_corrections correction_no=1 (пины operation_id/verification_no/receipt identity/исходный внешний ABCP Order ID/creator) + событие opened (owner/deadline словом/deadline_at/позиции+причина из blocked-события ПОИМЁННО/эпоха event_no=1); панель «Коррекция заказа»: слово «коррекция открыта: заказ заблокирован от продвижения до исправления и новой проверки» + owner поимённо + дедлайн честным текстом + заблокированные позиции/причина текстом (AC-1/AC-2; исходные записи не переписываются — append-only).
- Given операция без blocked-решения (задача активна/approved/задач нет), when open, then честный отказ «коррекция открывается по решению проверки „Нужна коррекция“ — заблокированного решения нет» (якорь BY NAME).
- Given активная коррекция операции, when повторный open, then 409 «коррекция заказа уже открыта — дождитесь исхода либо переназначьте» (вторая не создаётся; прецедент 4-7 409).
- Given закрытая коррекция (corrected/ceased), when open той же операции по НОВОМУ blocked-решению, then НОВАЯ correction_no+1 (лестница повторной коррекции; история не переписывается).
- Given owner не участник/без Review-скоупа / deadline чужим словом / actor без Review-скоупа / чужой кейс / терминальный кейс, when open/reassign, then 400 словарём гвардов / 403 словами скоупа / 404 RLS-слепота / 400 work-rule (прецеденты операторских поверхностей).
- Given открытая коррекция, when assign_order_verification (4-7) той же операции, then 409 «коррекция заказа открыта — проверка вернётся после исправления» (AC-2 «заказ остаётся заблокированным от дальнейшего продвижения» структурно: новая задача проверки не создаётся до закрытия коррекции).
- Given открытая коррекция на кейсе, when авторизация НОВОГО create_abcp_customer_order (подтверждённая пересобранная версия), then честный отказ ДО транзакции «коррекция заказа открыта: изменение существующего заказа выполняется вручную в контуре магазина; новый заказ не создаётся» (AC-9/AC-10 структурно; ничего не потребляется — replay-идемпотентность и superseded-лестница 3-4 не задеты).
- Given открытая коррекция, when пересборка заказа (маршрут order-proposals) и подтверждение клиентом новой версии (3-4 step-up), then работает существующей машиной: EDIT-лестница AD-7 версии+1, прежняя версия superseded BY NAME — прежнее Confirmation не переносится (AC-3/AC-4/AC-7: подбор заново по разрешённому процессу, «stale» — живые деривации).
- Given actor=owner коррекции, when record_reread (внешний ID перечитанного ABCP Order + пин подтверждённой версии {proposal, version, confirmation}), then валидации: версия ПОСЛЕДНЯЯ (не superseded) ∧ подтверждена ∧ живая DeriveOrderCommitmentMaterial == дайджесту версии → событие reread (внешний ID/пины/manager identity/время/эпоха) закрывает коррекцию исходом corrected; панель: слово «исправлен — заказ возвращается на проверку менеджера (pending_manager_verification); новая задача проверки — решением владельца» + слово «перечит подтверждён словами менеджера: Staffy не читает ABCP (AG-4) — состав сверён с подтверждённой клиентом версией» (AC-12: прежняя проверка не переиспользуется — новая задача по лестнице verification_no).
- Given пин СТАРОЙ подтверждённой версии (исходной операции, superseded), when record_reread, then отказ BY NAME «подтверждение клиента устарело (superseded) — требуется новое подтверждение» (AC-15: повторное использование старого Confirmation блокирует маршрут).
- Given живая деривация ≠ дайджесту подтверждённой версии (цена/наличие/срок изменились ПОСЛЕ подтверждения клиента), when record_reread, then отказ «состав изменился после подтверждения клиента — требуется обновлённое подтверждение» + экран показывает ЯВНЫЕ различия пин→живое по позиции (AC-13: скрытое ухудшение запрещено структурно — закрытие на неподтверждённом составе невозможно).
- Given actor=owner, when cease (причина словом {client_refused, not_needed, abandoned}), then событие ceased (причина/identity/время/эпоха) закрывает коррекцию исходом ceased; client_refused → панель несёт слово-рекомендацию «отмена заказа — ручной контур менеджера (контур 4-10)»; отсутствие согласия клиента НЕ превращается в замену — структурно: замены без нового подтверждения не существует (AC-11).
- Given reread/cease не-owner / по старой эпохе / два менеджера одновременно, then ровно один (CAS ожидаемой эпохи под локами); второй — честный отказ текущим состоянием словами; takeover = явный reassign владельцем.
