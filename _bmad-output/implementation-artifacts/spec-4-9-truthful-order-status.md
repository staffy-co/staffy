## Intent

**Problem:** слово-обещание из 4-6 «правдивый статус за пределами receipt-состояния — 4-9» и из 4-7 «статус читается отдельно из ABCP/1С» — механики НЕТ: пять стадий жизненного цикла AC-3 живут разрозненными словами трёх машин (квитанционное слово pending_manager_verification 4-6, состояния задачи 4-7, состояния коррекции 4-8), единого read-time представления «этап + evidence-пины (owning system/внешний ID/время/источник/свежесть)» не существует (AC-1); стадии «заказ поставщику сформирован»/«отправлен» не существуют как слова-стадии вообще — только честные отрицания (boundary-слово 4-6), пути записи человеческих фактов формирования/отправки поставщику НЕТ (AC-6: supplier order ID/связь/время/действие некуда сохранять — менеджер работает в ABCP руками, Staffy не видит ничего); ленты переходов с evidence нет (аудит-материал разбросан по трём машинам); свежесть статуса не выводится (AC-10); различение оценки срока/подтверждённой даты/фактического события словами не существует (AC-11); специальное состояние коррекции не входит ни в один статусный агрегат (AC-12); источники фактов не различаются (системная квитанция vs слова менеджера — AC-5); клиенту и оператору нечем пользоваться как одной поверхностью статуса (AC-16).

**Approach:** модуль action (якорь — операция create_abcp_customer_order и её append-only окружение). Пять частей: (1) миграция `migrations/action/00008_order_supplier_facts.sql` — 1 append-only таблица человеческих фактов с UNIQUE полного ключа факта (tenant, case, operation, kind, supplier_order_id) — повтор команды = идемпотентный replay; (2) домен `internal/action/domain/order_status.go` — словари compile-time (5 стадий, виды фактов {formed, sent}, источники {system_receipt, manager_record}, слова состояний/границ/свежести/срока), DeriveOrderStatusProjection (чистая read-time функция: упорядоченный fold над материалом трёх машин + факты — стадии поимённо с подтверждённостью, per-system раздельность, timeline, freshness) + DeriveOrderStatusTimeline; (3) app-сервис `internal/action/app/order_status.go` — ДВЕ команды записи фактов (RecordOrderSupplierFormed/RecordOrderSupplierSent: rights gate Review → живая операция заказа → гварды → sent требует prior formed с тем же supplier_order_id → append) + сборка OrderStatusView одним чтением материала; (4) панель «Статус заказа» на странице кейса после «Коррекции заказа» + форма записи факта + 2 маршрута JSON+PRG + OpenAPI-зеркала; (5) интеграционная eval-матрица AC-15 поимённо + journeys z46.

**Ядро честности среза:** статус — ЧИСТАЯ деривация чтения над append-only материалом (расчётное представление не становится новым источником истины — AC-2: проекция перечитывается событиями, не записывается); каждый факт несёт источник BY NAME — системная квитанция диспетчера ИЛИ человеческая запись менеджера (AG-4: адаптеры чтения не подключены — сообщение менеджера не отображается как системный receipt, AC-5); «сформирован» и «отправлен» — разные состояния, переход только с evidence, отправка без записанного формирования не выводится (гвард записи — дисциплина машины, не утверждение о реальности); 1С — unknown (OQ-4: создание ABCP Order не является синхронизацией, успех интеграции не предполагается); расхождение внешних ID (квитанция vs перечит 4-8) — оба факта раздельно, благоприятная версия не выбирается (AC-8); оценка срока не превращается в гарантию (AC-11); коррекция не скрыта за «в работе» (AC-12); история не переписывается (AC-14 — структурно append-only); Staffy не читает ABCP/1С/поставщика и не отправляет ничего (AG-4/OQ-3) — только записывает и правдиво показывает человеческую реальность контура магазина.

## Boundaries & Constraints

**Always:** таблица фактов append-only — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; CHECK-словари видов/источников = compile-time словари домена (миграция зеркалит); UNIQUE полного ключа факта — повтор команды = сохранённый исход (идемпотентность BY KEY, прецедент 2-1); якорь факта — живая операция заказа (operation_id FK) + case/work_item; ДВА времени — happened_at (названное менеджером, как provider-observed 2-7) + recorded_at (серверное, никогда не смешиваются); запись фактов — actor с Review-скоупом (живая грант-матрица identity), серверная истина актёра; sent — только после formed с тем же supplier_order_id (лестница записи BY NAME, отказ честным словом); проекция — чистые функции домена над материалом, НОЛЬ записей; все слова — словари домена; OpenAPI зеркалит; панель собирает ТОЛЬКО чтением живых панелей/портов; регресс — build/vet/unit + интеграция ×2 TZ + journeys + скан.

**Never:** НЕ строить адаптеры чтения ABCP/1С/поставщика (AG-4: credential-bearing реализации нет — источники фактов только квитанции диспетчерного контура и человеческие записи); НЕ отправлять/формировать поставщику НИЧЕМ (fence OQ-3: supplier-send отсутствует в Action Catalog — факты ТОЛЬКО записывают человеческую реальность; typed-схемы фактов закрытой формы БЕЗ полей отправки); НЕ строить webhook-приёмник/polling/callback (AG-4: интеграций нет — дедуп AC-9 исполняется идемпотентностью команд BY KEY и упорядоченным fold монотонных событий); НЕ строить доставку уведомлений и проактивные сообщения (OQ-1/OQ-2, прецедент 2-13 Never: панель = единственная поверхность состояния; Commitment-машина 3-3 не трогается; доставка/прочтение не фиксируются — честное слово); НЕ строить воркеры/таймеры/авто-обновление/поллинг внешних систем (AG-4/AD-14: живая деривация при открытии панели — «время следующего обновления» = честное слово, расписания НЕТ); НЕ расширять authorityMatrixV1 (2-7) новыми строками (OQ-19 открыт: матрица полномочий жизненного цикла заказа живёт словарями этой спеки; расширение матрицы 2-7 на заказные поля — будущий срез с OQ-19 evidence); НЕ гвардить факты против «обхода проверки» (человеческая реальность записывается какая есть: формирование при непроведённой проверке записывается, панель показывает ОБА факта — не скрывает и не блокирует правду); НЕ выбирать между расходящимися источниками (оба факта раздельно с источниками BY NAME); НЕ превращать оценку срока в гарантию (AC-11: три разных слова); НЕ переписывать историю (append-only: «новая версия статуса не переписывает историю предыдущих evidence» AC-14 структурно); НЕ трогать замороженные машины: лестницу диспетчера 3-6 (persist-квитанции тоже), машину 2-13, термы владения 2-4, команды 2-15, наблюдения 2-7; существующие панели 4-6/4-7/4-8 НЕ правятся (новая секция после «Коррекции заказа»; слово 4-7 «статус читается отдельно» исполняется новой панелью); НЕ показывать закупочные цены на статусной панели (ценовых полей в статус-вью 0 — зонд); НЕ расширять словари рантаймом.

## I/O & Edge-Case Matrix

- Given операция заказа committed (контур диспетчера, квитанция с внешним ID), when проекция, then стадия client_order_created подтверждена (время/квитанция/внешний ID/источник system_receipt), стадии выше — «не подтверждено» со своими словами; per-system: ABCP «создан (квитанция диспетчера)», 1С «unknown — синхронизация не доказана (OQ-4)» — существующее слово, поставщик «не записано» (AC-1/AC-2/AC-3/AC-7).
- Given операция заказа dispatch_blocked (nil-адаптер AG-4 — производственный контур), when проекция, then честные слова: «заказ создаётся вручную в контуре магазина (AG-4, рекомендация order_creation 4-6)»; стадии выше не подтверждаются; reread 4-8 (если был) — внешний ID со своим временем и источником manager_record (AC-5: человеческая запись ≠ системный receipt — слова раздельны).
- Given активная задача проверки 4-7 (assigned/acknowledged/overdue), when проекция, then стадия pending_manager_verification подтверждена (+owner/дедлайн живой деривацией 4-7); approved — стадия manager_verified (+receipt identity проверки); blocked + открытая коррекция 4-8 — специальное состояние «коррекция открыта — заказ не „в работе“: продвижение остановлено» (AC-12: не скрыто за общим статусом) + стадии с её учётом (лестница вниз читается историей).
- Given менеджер записал факт formed (supplier order ID + happened_at), when проекция, then стадия supplier_formed подтверждена (+ID/время/источник manager_record + слово «записано менеджером: чтение ABCP адаптером не подключено (AG-4)»); повтор той же команды — идемпотентный replay (тот же факт, второго нет — UNIQUE ключа AC-9); formed с ДРУГИМ supplier order ID — второй факт (несколько поставщиков поимённо).
- Given formed(S1) записан, when запись sent(S1), then факт sent (+ID/время) — стадия supplier_sent подтверждена, когда ВСЕ записанные формирования покрыты отправками (частичная отправка — поимённые слова «отправлен частично: S1 отправлен, S2 сформирован и не записан как отправленный», стадия НЕ подтверждена — честный агрегат).
- Given sent(S3) без formed(S3), when запись, then отказ BY NAME «отправление записывается после записи формирования того же заказа поставщику — сначала запишите формирование (дисциплина истории, время формирования назовите фактическим)» (AC-6: «сформирован» и «отправлен» разные состояния структурно).
- Given квитанционный внешний ID ≠ внешнему ID перечита 4-8 (или ≠ записанному факту), when проекция, then ОБА значения показываются раздельно со своими источниками/временами — выбора «наиболее благоприятной версии» не существует (AC-8; конфликт-слово словаря существует, вывод конфликта двух систем невозможен в срезе — 1С unknown как класс, честное слово-граница OQ-4).
- Given события материала приходят «не по порядку» (перемешанные времена чтения), when деривация, then упорядоченный fold по монотонным якорям (event_no/лестницы/created_at) — ТОТ ЖЕ результат: старое событие не откатывает подтверждённое новое, история переходов неизменяема (AC-9 — юнит-тест тасованием).
- Given любая проекция, when свежесть, then поле «последний подтверждённый факт: <время>» + слово «живая деривация при открытии; внешние чтения ABCP/1С/поставщика не подключены (AG-4)» — устаревшее значение НЕ представляется текущим, времени «следующего обновления по расписанию» НЕТ (AC-10 — честное слово, воркеров нет).
- Given предложение заказа несёт срок, when панель статуса, then ТРИ раздельных слова: «оценка срока предложения» (материал 4-6) / «подтверждённая дата — не существует: подтверждения поставщиком нет» / «фактическое событие — запись отправки с временем» (AC-11: оценка не превращается в гарантию магазина).
- Given оспаривание статуса клиентом (внешний контур), when панель, then слова-границы: «исходное сообщение сохранено (append-only история); проверка источников — запрос человека (контур 2-13); новая версия статуса не переписывает историю» (AC-14 структурно + recovery-контур 3-8 словом).
- Given проактивные уведомления «настроены» (гипотеза AC-13), when срез, then НЕТ: панель несёт слово «уведомления о переходах не отправляются: канал не подключён (OQ-1/OQ-2); панель — единственная поверхность состояния; доставка и прочтение не фиксируются» (прецедент 2-13 Never; полей/маршрутов доставки 0 — зонд).
- Given actor без Review-скоупа / чужой кейс / операция не существует / терминальный кейс / вид/ID/время вне словарей и гвардов, when запись факта, then 403 словами скоупа / 404 RLS-слепота / 404 «операция заказа не найдена» / 400 work-rule / 400 словарём гвардов (прецеденты операторских поверхностей).
- Given foreign scope / не-участник, when чтение статуса, then RLS-слепота 404 / 403 правами; audit-only — 403 (прецеденты).
- Given панель при клавиатуре/screen reader/320px/увеличенном тексте, then этап/источник/время/свежесть/owner/следующий шаг доступны ТЕКСТОМ; системы и состояния различимы БЕЗ опоры только на цвет (стадии словами, не только бейджами); технические названия (ABCP/1С) сопровождаются понятным объяснением; клиентские слова — блок материала пересказа (AC-16).

## Implementation Notes

- Решение модуля: проекция и факты живут в ACTION-модуле (якорь — операция заказа и её append-only окружение 4-6/4-7/4-8); ZERO записей в деривации — «расчётное представление не становится новым источником истины» (AC-2) структурно: проекция не хранится, перечитывается событиями при каждом открытии.
- Матрица полномочий жизненного цикла (AC-1) = словари этой спеки: клиентский заказ/проверка/коррекция — action-модуль (квитанции диспетчерного контура и события); ABCP-состояние — внешний владелец, в срезе читается только записями контура (квитанция/перечит 4-8/факты); 1С — unknown как класс (OQ-4); поставщик — человеческие записи. Расширение authorityMatrixV1 2-7 на заказные поля — OQ-19 (открыт): будущий срез с gate evidence; НЕ в этом срезе.
- Факты {formed, sent} = человеческая квитанция контура магазина (OQ-3 safe state: manual reread + human receipt): запись НЕ гвардится против «обхода проверки» (правда записывается какая есть — панель показывает оба факта раздельно, AC-12 дух «не скрывать»); единственная лестница записи — sent после formed того же supplier_order_id (дисциплина полной истории, времена называются фактическими).
- «Отправлен» — честный агрегат: стадия supplier_sent подтверждена ТОЛЬКО когда все записанные формирования покрыты отправками; частичная отправка — поимённые слова, стадия НЕ подтверждена (ложное утверждение об отправке невозможно структурно — AC-15).
- Freshness (AC-10) без поллинга: проекция живая при открытии; «источник временно недоступен» в срезе = класс внешних систем (AG-4 — не подключены), слово-граница; время последнего подтверждённого факта — из happened_at/recorded_at фактов и времён событий машин (два времени никогда не смешиваются — прецедент 2-7).
- Отмена заказа — контур 4-10 словом-границей (AC-12); спор/оспаривание — существующие контуры 2-13/3-8 (AC-14: append-only история структурно не переписывается — «новая версия статуса» = новые события).
- Journeys z46: z-префикс по живому правилу соседей (46 z после 45 z order-correction); слот мира — новый сид order-семейства (755-758 заняты order-контуром, 759/770 заняты — следующий по живому регистру слотов); фикстура orderWorld reused (committed-квитанция на входе).
- Eval-матрица = AC-15 дословно + структурные зонды; «повтор webhook» — идемпотентность BY KEY (UNIQUE полного ключа факта, прецедент 2-1); «события не по порядку» — юнит-тасование + интеграционный порядок.
