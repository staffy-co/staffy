## Intent

**Problem:** Внешний Commitment — обещание, предложение, согласованный callback, срок обновления — сегодня не существует как диспетчеризуемый класс (FR-33, AC-блоки 1-11): нет записи со стабильным ID и неизменяемой версией, несущей recipient, purpose, channel, Work Item, существенные условия, valid-until, ожидаемый следующий шаг и требуемое acknowledgement (2-9 — коммерческое предложение с подтверждением клиента, НЕ конверт доставки); нет закона «persist before emit» (AD-5): ни одна исходящая отправка не фиксируется в одной PG-транзакции вместе с outbox record до сетевого вызова — ошибки БД могли бы оставлять внешнюю систему уже затронутой; нет worker-контура над outbox (AD-13: leased at-least-once jobs — фоновых воркеров не существует, дренер 2-4 — только для ownership-проверки replies); нет детерминированного outbound payload с idempotency key из сохранённой версии; нет execute-time stale-заборов (устаревшая версия может уйти), нет обещанной 3-2 enforcement-точки (control EffectiveFor + generation никем не потребляется); нет семантики доставки семь слов {persisted, queued, submitted, delivered, acknowledged, failed, unknown} с различением «submitted ≠ delivered ≠ acknowledged» (2-12 владеет evidence-строками replies, не состояниями конверта); нет unknown/reconciling после timeout с attempt/external correlation ID/следующим шагом и запретом слепого повтора; нет approval-гейта точной версии (ранее утверждённая версия не должна разрешать изменённый текст); нет разделения чувствительного payload и безопасных логов. Честное состояние контура: реальных провайдеров нет (AG-4 — каталог коннекторов честно пуст для паков, команда send-sms синтетической телефонии — тестовый контур), AI Runtime не существует (автором слов может быть только человек — «AI proposes, human acts» 2-6), фоновые демоны не существуют (AD-13 job-фреймворк — будущий срез), reconciliation — story 3-7. Первый срез рождает диспетчерский контур: конверт External Commitment с версиями и пинами, approval точной версии, транзакционный enqueue, дренер с детерминированным payload и stale-заборами, состояния доставки выводом чтения, операторский relay-квитанций — интеграция с control EffectiveFor живая.

## Implementation Notes

- Persist-before-emit — СТРУКТУРНАЯ гарантия: сигнатура транзакционного метода enqueue не содержит адаптера/порта отправки; сетевой вызов физически возможен только в дренере после commit. Тест-зонд сбоя БД — обязательная строка матрицы (rollback → ни outbox, ни вызова адаптера по счётчику).
- Детерминизм payload — из неизменяемости версии: BuildOutboundPayload читает ТОЛЬКО строку версии (immutable by construction); «последующее изменение draft не меняет queued payload» реализовано НЕ снимком, а пином: queued-запись пинит (ext_id, version_no), строка никогда не мутирует, изменённый текст живёт в новой версии и гасит старую очередь забором newer_version на execute-time.
- Idempotency key — производная пина HMAC(tenant, ext_id, version_no): повтор той же версии несёт тот же ключ (провайдер дедупит), изменённая версия НИКОГДА не попадает под старый ключ («тот же ключ с другим payload — конфликт» структурно невозможен). Ключ попытки НЕ включает attempt_no — иначе повтор перестал бы быть безопасным.
- Контрольная интеграция 3-2 — обещанная enforcement-точка: дренер потребляет EffectiveFor(tenant, channel) через composition-адаптер (DAG: case не импортирует control — только порт); честный v1: не-accept гасит ЛЮБОЙ purpose (emergency brake); per-режимная тонкость — второй срез 3-2/admission. Nil/нерезолвция порта = fail-closed гашение с причиной control_mode (модуль не отправляет туда, где не может доказать accept).
- Approval — привязка к точной версии и текущему человеку-владельцу: «ранее утверждённая версия не разрешает изменённый текст» реализовано структурно (enqueue ищет approval строку (tenant, ext_id, version_no) с approver = текущий owner; изменённый текст = version_no+1 = строка не находится). Истечение approval = истечение valid_until самого конверта (отдельного таймера нет — честная граница).
- Повторная доставка outbox — двойной дедуп: события записи (attempt/receipt уже есть → пропуск) + dedup_key outbox (UNIQUE — вторая линия, прецедент 2-1). «Обработка уже началась» (краш между вызовом адаптера и записью события) честно покрывается bounded-попытками и ключом: повтор записи тем же ключом безопасен в пределах гарантии, для не-идемпотентной capability — парковка unknown (слепой повтор структурно исключён).
- Timeout ≠ failed: failed — предотправочный отказ провайдера (внешнего эффекта нет, повтор безопасен); timeout — возможная отправка (unknown, повтор только по гарантии); это различение — ядро AC-8, пиннуто матрицей и текстами страницы.
- Receipt-квитанции — только операторский relay (2-12 ConfirmerOperatorRelay: человек передаёт машинное наблюдение, машина не изобретает) или адаптер с ReceiptLevel delivered/committed; delivered без acknowledged НИКОГДА не показывается как принятие получателем (для ack_required конвертов — различение materially, AC-7/AC-11).
- AG-4 production-граница: реальных провайдеров нет — production root НЕ подключает диспетчер; дренер отказывает честными словами, записи остаются queued (состояние честно видно). Синтетический адаптер — только fixture/интеграционный контур; включение его в production бинар структурно исключено отдельным пакетом адаптера, не импортируемым main.
- Материал и пины никогда не покидают строку: outbox payload = ids/version/purpose/channel/recipient_kind/idempotency key/content digest; dispatch_events.details ≤500 safe-текста (корреляция, исход, причина — не содержание); тексты состояний — рендер-слой, не БД.
- content_token — HMAC над каноническими байтами конверта (пространство канонизации отлично от 2-9: префикс типа записи), ключ commitments_hmac_keys reused (ensure-паттерн INSERT-only 2-9, ротация — прежний honest deferred); дренер перепроверяет токен перед отправкой (AD-5 keyed/versioned commitment token).
