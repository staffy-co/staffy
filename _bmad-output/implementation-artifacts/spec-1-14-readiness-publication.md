## Intent

**Problem:** Epic 1 научился настраивать каждый компонент ИИ-сотрудника и запечатывать конфигурацию: манифест релиза (1-12: версии + digest) и утверждённый Operating Profile (1-13: route states, human coverage, privacy/OQ-11-назначения, coverage matrix, gate-декларации, пороги `pending baseline`) уже выводят честные деривации «для будущего потребителя». Но потребителя нет: нет поверхности, которая собирает состояние всех обязательных элементов релиз-кандидата в один ответ (Brief, Domain Pack, знания, поведение, голос, Connections, capabilities, Entitlement, human coverage, consent, eval, gates), нет общего статуса `incomplete / blocked / ready for <stage>`, нет gate-instance-реестра с машинной дисциплиной PASS (append-only переходы, approver-роли, evidence + hash, supersedes-цепочка, exact-scope), нет карты стадий трафика (GATE-REGISTRY: synthetic → closed_account_test → controlled_real_customer → live) и нет самого события контролируемой публикации — атомарной записи решения о допуске с точными digest'ами манифеста и профиля, approver-ролями и per-route результатами. Технический успех отдельного компонента нигде не отделяется от готовности целого; заблокированный маршрут не показывает требуемое доказательство и рекомендуемый следующий шаг; публикацию нельзя ни зафиксировать, ни аудировать. Направление трафика — Epic 2, но у Epic 2 нет входа: неизвестно, какая версия допущена к какой стадии и по каким маршрутам.

**Approach:** В модуле `employee` (спайн: employee владеет релизом — 1-12 профиль 1-13, продолжение) ввести три вещи. (1) Фиксированный словарь gate-определений платформы в домене — восемь определений из принятого GATE-REGISTRY, участвующих в каре стадий (OQ-11 data route, OQ-12 live voice baseline, OQ-13B recoverability, OQ-14 quantitative admission, OQ-7B route thresholds, AG-1 pilot load envelope, AG-2 accessibility admission, AG-4 runtime dependency readiness): идентификатор, критичность, требуемые approver-роли (метки реестра), требуемое доказательство, safe state, fail-closed fallback, allow_role_coincidence. Карта стадий фиксирована по Execution order реестра: `synthetic` — gate-инстансы не требуются; `closed_account_test` — не требуются (тест-аккаунты, синтетика/минимизация до OQ-11 PASS); `controlled_real_customer` — OQ-11 (route-scoped), AG-1, AG-2, AG-4, для голосовых маршрутов дополнительно OQ-12 и OQ-13B; `live` — всё предыдущее + OQ-14 и OQ-7B. (2) Gate-инстансы — tenant-scoped append-only записи против словарных определений: scope-измерения (route, modality) присутствуют только точно (нет wildcards: отсутствующее измерение = определение не несёт этого измерения), переходы `open → in_test → pass|fail`, любой активный статус может стать `expired`, утверждённое scoped-решение — `not_applicable` (не даёт более широкого разрешения); PASS записывается только с полным покрытием требуемых approver-ролей различными принципалами (кроме явного allow_role_coincidence), непустыми evidence-ссылками и hash доказательства; проваленный/истёкший PASS никогда не перезаписывается — reopening создаёт новый инстанс со ссылкой supersedes (ацикличность проверяется при записи). (3) Readiness-деривация на чтении из живых фактов: состояние каждого обязательного элемента (манифест-ссылки 1-12, capability-факты, entitlement admission_state 1-11, route states/human coverage/OQ-11 из профиля 1-13, eval-ссылки матрицы — честно `linked, not executed`, gates по карте стадий) → общий статус `incomplete / blocked / ready for <stage>` — конъюнкция: технический успех компонента не становится готовностью целого. Публикация — команда `configuration` + step-up (прецедент 1-13): деривация повторяется в той же транзакции, атомарно создаётся append-only решение (номер, стадия, точные manifest_id + config_version + digest и profile version + digest, per-route результаты admitted/blocked с причиной, actor, approver-роли на момент решения, время, digest решения); активный указатель — последняя запись (деривация, паттерн budget current 1-11); стадию нельзя перескочить: решение для стадии N требует действующего решения стадии N−1 того же кандидата (те же digest'ы); гонка конкурентных публикаций — ровно одна запись, конкурент получает честный конфликт с текущим состоянием. Readiness и admission остаются чистой деривацией и портом для Epic 2: срез никогда не направляет трафик и не привязывает Conversations (их не существует) — enforcement остаётся за Epic 2. Отложено честно: исполнение offline eval и synthetic preview (AC-4 — поверхностей eval нет; элемент eval остаётся честным «ссылки без исполнения», блокирующим стадии от controlled и выше), rollback (AC-11), экспирация по расписанию/probes (AC-10 — триггеры хранятся, деривация на чтении честно отражает stale-факты, планировщиков нет), стадия `scale`, компиляция processor graph манифеста в зависимости инстансов (полный release compiler), per-surface scoping AG-2 (инстанс несёт modality-scope), привязка начатых Conversations к версии (Epic 2).

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 1-9…1-13, исполняет вариант А ретроспективы Epic 1): Test & Release Panel локального контура на существующих фактах — словарь определений фиксирован в домене по принятому реестру (роли-метки реестра записываются как утверждение: система проверяет существование участников и структурную полноту покрытия ролей, но не орг-истину «кто действительно Technical Lead» — это governance-факт человека, честная пометка); approver-роли gate-инстансов — метки реестра, публикация — `configuration` + step-up (провайдера step-up нет — продакшн-блок честен, прецедент 1-13, deferred-work); все platform-gates сегодня без единого PASS → стадии от controlled и выше честно заблокированы (демо-путь: synthetic и closed_account_test публикуются end-to-end, высшие стадии выводят честные блокировки с safe state); eval элемент — `linked, not executed` до появления eval-поверхностей (Epic 6): стадии от controlled и выше дополнительно блокированы им; OQ-11-приватность маршрутов потребляется из профиля 1-13 (route-level fail-closed сохраняется).

## Boundaries & Constraints

**Always:** Словарь gate-определений и карта стадий фиксируются в домене по принятому GATE-REGISTRY и не настраиваются на Tenant; расширение словаря — новая версия спеки. Gate-инстанс создаётся и переводится только участником Tenant с командой под step-up (единое правило для всех переходов состояния); переход в `pass`/`fail` требует: полного покрытия approver-ролей определения различными принципалами (каждая требуемая роль присутствует в approved_by; совпадение принципалов в нескольких ролях — только при явном allow_role_coincidence определения), непустых evidence-ссылок (каждая 1–300 символов) и hash доказательства (hex sha256, непустой); participant-ссылки валидируются через MembersFacts (прецедент 1-13). Инстансы append-only (INSERT/SELECT, грантов UPDATE/DELETE нет): проваленный, истёкший или superseded PASS никогда не перезаписывается; reopening — новый инстанс с supersedes-ссылкой, цикл в цепочке отвергается записью. Scope-измерения route и modality присутствуют только точно; отсутствующее измерение означает, что инстанс определения не скопирован по этому измерению; wildcards отсутствуют; `not_applicable` требует обоснования и не расширяет разрешение. Применимость инстанса к проверке маршрута R: route отсутствует (tenant-уровень) или равен R точно; modality аналогично; expired/отсутствующий/failed/superseded инстанс не является PASS. Все применимые gates конъюнктивны: один отсутствующий/проваленный/истёкший держит маршрут fail-closed; порядок работы никогда не переопределяет privacy, identity, safety и legal gates. Readiness выводится на чтении из живых фактов и никогда не кэшируется как хранимая истина: смена фактов (stale capability, новый манифест → профиль неприменим, истёкший инстанс) отражается при следующем чтении немедленно. Общий статус кандидата для запрошенной стадии: `incomplete` (обязательный элемент отсутствует/не заполнен — публикации нет), `blocked` (элементы заполнены, но есть блокировки), `ready for <stage>` — только если все обязательные элементы и все требуемые gates стадии дают pass по хотя бы одному маршруту; технический успех отдельного компонента (манифест запечатан, connector connected) не превращается в общий статус готовности. Обязательные элементы: Brief, Domain Pack, знания, поведение, голос (для голосовых маршрутов; отсутствие голосовых маршрутов — явное `not_applicable` с причиной), Connections, capabilities, Entitlement, human coverage, consent, eval, gates — источники: манифест-ссылки 1-12, ConnectionsFacts/CapabilityFacts, entitlement admission_state (факт-порт, прецедент 1-11), route states/OQ-11 профиля 1-13, eval-ссылки coverage matrix, инстансы словарных определений. Per-route fail-closed: блокировка затронутого маршрута (нет покрытия, fallback без evidence, OQ-11 open, capability не verified, gate без PASS) не блокирует профиль и кандидата целиком — независимые маршруты живут; каждая блокировка несёт причину, владельца разблокирования, требуемое доказательство и рекомендуемый следующий шаг. Entitlement admission_state — обязательный элемент на всех стадиях; блокирует публикацию стадий от closed_account_test и выше (draft/paused/hard limit — «новые admission и публикации блокируются», слова деривации 1-11); для synthetic — отображается честно, публикацию synthetic не блокирует (фикстуры не расходуют коммерческие поверхности). Публикация: команда `configuration` + step-up (`StepUpVerified`, честный `step_up_required` без провайдера); решение создаётся атомарно в одной транзакции с повторной деривацией (TOCTOU закрыт); append-only запись: монотонный номер под блокировкой агрегата сотрудника, стадия, точные manifest_id + config_version + digest и profile version + digest (сверка с записанными строками, как 1-13), per-route результаты (admitted | blocked с причиной), modality и Autonomy Class маршрутов из профиля, actor, approver-роли на момент решения, время, канонический sha256-digest решения; конкурентные публикации того же кандидата — ровно одна запись, конкурент получает честный конфликт с текущим состоянием; активный указатель = последняя запись (деривация). Стадию нельзя перескочить: решение для закрытой стадии N требует действующего решения стадии N−1 того же кандидата (те же digest'ы манифеста и профиля); synthetic — первая стадия, предыдущего не требует. Разрешение одного маршрута/канала/modality/класса не расширяет автоматически остальные — решения per-route, прав расширения нет. Публикация с нулём допущенных маршрутов отвергается честно («ни один маршрут не допущен» с перечнем причин) — пустых публикаций не существует. Полномочия применяются на сервере до SQL: просмотр readiness/gates/истории — `configuration`, `review` или `audit`; команды gate-инстансов и публикации — `configuration` (+роли определения для approved_by-записи); не-участник — 404 без раскрытия Tenant, межтенантная изоляция — RLS во всех таблицах. UI Test & Release Panel: состояния элементов, статусы, блокировки, gates, владельцы и стадии доступны текстом и не только цветом; блокировка показывает причину, владельца, требуемое доказательство и рекомендуемый следующий шаг; единственное основное действие — допустимый следующий шаг (публикация доступной стадии или устранение блокировки); подтверждение публикации — modal с корректным focus trap и возвратом focus; результаты объявляются доступно (aria-live) без неожиданного перемещения focus; клавиатура, screen reader, цели ≥44×44 px, без горизонтального скролла на 320 px; выбор стадии предпросматривает деривацию (dry-run) до подтверждения.

**Never:** Не направлять трафик и не привязывать Conversations: срез выводит решения и указатель, enforcement и привязка начатых диалогов — Epic 2; «ready» никогда не означает «диспетчеризация включена». Не выдумывать PASS: отсутствие инстанса, open/in_test, fail, expired, superseded — не разрешение; `not_applicable` не расширяет разрешение на другие scope; verbal assurance, mock, sandbox success и roadmap никогда не меняют состояние (слова реестра). Не принимать PASS без полного покрытия approver-ролей, различных принципалов (кроме явного allow_role_coincidence), непустых evidence-ссылок и hash. Не перезаписывать и не удалять инстансы и решения (грантов UPDATE/DELETE нет; supersedes — только новый инстанс). Не разрешать перескок стадии и не считать решение другой версии кандидата предыдущей стадией (сверка digest'ов обязательна). Не публиковать с незаполненными обязательными элементами и с нулём допущенных маршрутов. Не расширять разрешение одного маршрута/канала/modality/класса на другие автоматически. Не кэшировать readiness: хранимых «вычисленных» статусов не существует — только факты и записи решений. Не превращать технический успех компонента в общий статус готовности. Не исполнять offline eval и synthetic preview (нет поверхностей; элемент eval — честные ссылки без исполнения, блокирующие controlled и выше до Epic 6). Не выполнять rollback и миграцию/quarantine несовместимых версий (отложено). Не планировать экспирацию планировщиками: триггеры хранятся и отображаются, решения о истечении — ручная команда или повторная деривация фактов (probes отложены). Не включать секреты, подсказки секретов, raw PII, transcripts и содержимое защищённых медиа в инстансы, решения и ответы readiness. Не делать gate-словарь настраиваемым на Tenant и не подменять принятый реестр локальными определениями. Не скрывать блокировки за средним/агрегированным статусом: per-route причины всегда доступны. Не публиковать без step-up. Не подменять Org-истину approver-ролей машинной проверкой: система записывает утверждение и проверяет структуру, кто в организации держит роль — governance-факт (честная пометка на отображении).

## I/O & Edge-Case Matrix

- Given запечатанный манифест и утверждённый применимый профиль, when Owner открывает Test & Release Panel, then показано состояние каждого обязательного элемента (Brief, Domain Pack, знания, поведение, голос, Connections, capabilities, Entitlement, human coverage, consent, eval, gates) с источником факта; общий статус вычисляется `incomplete / blocked / ready for <stage>` для выбранной стадии; технический успех отдельного компонента не даёт общий статус готовности.
- Given отсутствует обязательный элемент или заполнен не полностью (нет ссылки на знания, профиль без human coverage, entitlement не настроен), when запрашивается readiness любой стадии, then общий статус `incomplete` с перечнем незаполненного, ведущим к конкретному элементу; публикация отвергается честно.
- Given отсутствует обязательный Connector, действующая capability, Response Owner, fallback, purpose-specific consent (OQ-11 open) или Evidence Gate, when выполняется readiness-проверка, then затронутый маршрут получает состояние `blocked` с причиной, владельцем разблокирования, требуемым доказательством и рекомендуемым следующим шагом; независимый маршрут остаётся готовым, если его требования выполнены; общий статус не маскирует per-route причины.
- Given capability или манифест стали stale (CapStateStale; новый манифест → профиль неприменим), when любой пользователь читает readiness, then деривация немедленно отражает stale-факты (blocked/stale с причиной) — кэша нет; Owner видит рекомендуемое действие по разблокированию.
- Given gate-инстанс переводится в pass, when одобряющий не покрывает все требуемые approver-роли определения или принципалы совпадают без allow_role_coincidence, then переход отвергается честной ошибкой с перечнем недостающих ролей; инстанс остаётся в прежнем состоянии.
- Given gate-инстанс переводится в pass с пустыми evidence-ссылками или без hash доказательства, when выполняется команда, then переход отвергается валидацией (evidence refs непустые 1–300, hash непустой hex sha256).
- Given цепочка supersedes при reopening, when новый инстанс ссылается на предка, then цепочка проверяется на ацикличность; цикл отвергается записью; проваленный/истёкший/superseded PASS не перезаписывается — история видна.
- Given запрошена стадия controlled_real_customer, when OQ-11, AG-1, AG-2 или AG-4 не имеют действующего применимого PASS (сегодня: ни одного PASS), then затронутые маршруты (или все — для tenant-глобальных AG) получают `blocked` с safe state («до PASS — только synthetic/closed-account»); synthetic-работа продолжает жить в ранее разрешённых пределах.
- Given голосовой маршрут запрашивает controlled_real_customer, when OQ-12 или OQ-13B без PASS, then голосовой маршрут заблокирован, текстовые маршруты оцениваются своими gates; разрешение текстового канала не расширяет голосовой.
- Given запрос на production credentials или controlled-real-customer публикацию, when AG-4 не имеет действующего PASS, then публикация затронутой конфигурации блокируется; интерфейс не предлагает обход gate (основное действие — устранение блокировки, не переключение стадии).
- Given запрос на публичный customer route, when AG-2 без действующего PASS с доказательствами доступности (automated + human assistive-technology evaluation), then маршрут не допускается; автоматические проверки без human-оценки не считаются полным доказательством (требование evidence-текста определения).
- Given запрос на controlled voice traffic или увеличение лимита нагрузки, when AG-1 без подходящего Pilot Load Envelope, then admission блокируется либо остаётся на ранее доказанном лимите (предыдущее решение остаётся активным указателем, откат не выполняется).
- Given запрошена стадия N > synthetic, when нет действующего решения стадии N−1 того же кандидата (те же digest'ы манифеста и профиля), then публикация отвергается честно: перескок стадии невозможен; сообщение называет требуемую предыдущую стадию и её статус.

## Implementation Notes

- Словарь stage map по Execution order принятого реестра: synthetic — []; closed_account_test — []; controlled_real_customer — [OQ-11 (route), AG-1, AG-2, AG-4] + voice [OQ-12, OQ-13B]; live — предыдущее + [OQ-14, OQ-7B]. Стадия `scale` — вне среза (Epic 2+). Tenant-специфичные gates пилотов (OQ-1..10, OQ-19, AG-3…) остаются проектным реестром planning-артефактов — в продукт не заносятся (честное Design Note).
- Роли approver'ов — метки реестра (например «Technical Lead + Operations»); система проверяет существование участников (MembersFacts) и структурную полноту покрытия (каждая роль покрыта, принципалы различны кроме allow_role_coincidence), но не орг-истину — утверждение записывается и отображается с честной пометкой (governance-факт человека).
- OQ-11 в stage map — route-scoped (инстанс с route измерением применим только к точному маршруту); AG-1/AG-2/AG-4/OQ-12/OQ-13B/OQ-14/OQ-7B — tenant-уровень (route отсутствует); modality-измерение — точное или отсутствует (AC-7 AG-2 per-surface глубина отложена, modality-scope — максимум детализации среза).
- Entitlement: факт-порт читает DeriveAdmission (draft/paused/hard limit → blocked «новые admission и публикации блокируются»); synthetic — исключение (фикстуры), задокументированное в спеке; closed_account_test и выше — блокирует.
- Элемент voice: `not_applicable` с причиной «нет голосовых маршрутов», если профиль без voice routes (разрешение не расширяет).
- Элемент eval: единственный источник — eval-ссылки coverage matrix профиля 1-13; состояние `linked, not executed` (прогонов нет — Epic 6); стадии от controlled и выше требуют eval → честная вечная блокировка до eval-поверхностей; synthetic/closed_account_test не требуют.
- Step-up единый на команды инстантов и публикацию: `Principal.StepUpVerified` → честный `step_up_required` (провайдера нет — продакшн-блок, deferred-work, тот же класс что membership/1-13); фикстура journey — существующий переключаемый резолвер.
- Digest решения: каноническая Go-сериализация (фиксированный порядок полей, отсортированные маршруты — прецедент 1-12/1-13), sha256, hex (char(64)); сверка manifest/profile ссылок против записанных строк (как 1-13).
- `gate_instances` и `release_admissions` — INSERT/SELECT only; монотонный decision_no под блокировкой агрегата (паттерн профиля); активный указатель — MAX(decision_no) деривацией (паттерн budget current 1-11).
- Гонка публикаций: блокировка строки агрегата сотрудника; вторая команда после коммита видит действующее решение того же кандидата/стадии — честный конфликт с текущим состоянием (ровно одна запись).
- Stage order: решение стадии N требует действующей (последней, не откаченной — отката нет) записи стадии N−1 с теми же manifest digest и profile version/digest.
- Privacy-класс `release-admission` (privacy/domain/classes.go): инстанты и решения — конфигурация/аудит без PII-содержимого (участники — идентификаторы, evidence — ссылки); purge-агрегат сотрудника расширен (gate_instances — tenant-уровень, входит в tenant-purge границу).
- HTTP: JSON-команды со строгим decode (DisallowUnknownFields), wire-форма сверяется контракт- и transport-тестами (урок M1 1-13); OpenAPI дополняется путями и схемами; навигация «Test & Release».
- Journey-фикстура: step-up резолвер (существующий), JSON API для цепочки release/profile (существующие), префилл элементов из фикстурных фактов.
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...`, `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`.

## Design Notes

- Размещение в модуле `employee` — спайн epic-1-context (employee владеет настройкой, профилем и релизом): манифест (1-12) → профиль (1-13) → readiness/публикация (1-14) — без отклонения от архитектурной строки.
- Admission-enforcement и привязка Conversations — Epic 2: срез выводит решения и указатель; прецедент портов `admission_state` (1-11) и route states (1-13) продолжен — Epic 2 получает готовый вход.
- Честные вечные блокировки среза: (1) step-up-провайдера нет — публикация и переходы инстантов невозможны в продакшн-бинар (запись в deferred-work); (2) ни одного gate PASS — стадии от controlled заблокированы; (3) eval-поверхностей нет — элемент eval `not executed` блокирует controlled+; демо-путь — synthetic/closed_account_test end-to-end.
- Экспирация: триггеры хранятся и отображаются; планировщиков/probes нет — истёкшее состояние фиксируется ручной командой, stale-факты отражаются деривацией на чтении (AC-10 частично честно закрыт чтением; probes — deferred-work).
- Rollback (AC-11) отложен целиком: указатель монотонно растёт, откат отдельным срезом при необходимости (структура решения — per-route digest-записи — совместима).
- AG-2 human assistive-technology evaluation: текст evidence-требования в определении; система записывает и отображает требование, машинной проверки человеческой оценки нет (честная пометка).
- Определения/инстансы проектного реестра (gate-definitions.json / gate-instances.json архитектуры) остаются planning-каноном пилотов; продукт-поверхность tenant-scoped, словарь фиксирован — синхронизация реестров вне среза (SM-заметка).
