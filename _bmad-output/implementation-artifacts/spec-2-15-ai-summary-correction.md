## Intent

**Problem:** Дисциплины коррекции не существует (AC-блок 1, FR-40): оператор видит в контексте 2-14 факт с ошибкой — способ записать исправление КАК осознанный приписанный акт нет; record_fact пишет новую версию, но не несёт связи «эта версия исправляет ту точную версию потому-то» (source_id — ключ команды, семантики коррекции нет; supersedes-связи, автора-оператора с каналом и временем достаточно нет — provenance есть, но коррекционная семантика отсутствует); связь с точной версией сводки 2-14 (deferred-work 2-14: «Correction со связью с точной версией сводки — story 2-15») не существует. Автоподтверждения нет структурно (AC-блок 2 — уже честно): новая версия факта без confirm остаётся conflicting/unverified по DeriveFactStatus (work.go:425); НО «пользователь может подтвердить, изменить или отменить correction» поверхностям нечем: панель контекста не показывает исправленного состояния строк, формы коррекции нет, связь предложение→подтверждение не видна. Спора матричных полей не существует (AC-блок 4): клиент/оператор не согласен с ценой/наличием/статусом заказа (authorityMatrixV1 — observation.go:157: price/availability → catalog, order_status → erp); значение Owning System переписывать НЕЛЬЗЯ (матрица авторности), но сохранить пользовательское значение спором и инициировать повторное чтение нечем — dispute_work_item спорит Work Item (2-2), не материальное поле; словарь наблюдений {ok, failed, unknown} (observation.go:55) слова «спор» не несёт. Staleness-распространения коррекции не видно (AC-блок 5, частично): новая версия факта инкрементирует fact_version_count watermark → DeriveContextStaleness (2-14) честно флипает сводку в stale — механизм ЖИВ, но коррекция в него пока не попадает (нет записи версии), и поверхности это не показывают. Поверхности Correction Panel нет (AC-блок 11): old/new значения, источник, последствия — нечему рендерить; форма «Исправить» на строке факта отсутствует.

## I/O & Edge-Case Matrix

- Given подтверждённый факт (version N, confirm есть) и оператор review, when record_correction (fact_id, version_no=N, proposed_value иное, span из события, reason), then correction_no=1, outcome=applied, новая fact_version N+1 (source operator, source_id correction:<id>), DeriveFactStatus → conflicting (последняя ≠ последней подтверждённой), outbox case.correction_recorded идентификаторами; панель: маркер «исправлено» + строка исхода/№/времени — AC-блоки 1/3.
- Given коррекция applied, when оператор подтверждает точную новую версию confirm_fact_version (evidence событие/нота), then DeriveFactStatus → confirmed, маркер «исправлено» остаётся, спор снят человеком — AC-блоки 2/3 (подтверждение отдельной командой существующей лестницы).
- Given коррекция applied и сводка 2-14 записана ранее, when GET decision-context, then сводка stale: watermark fact_version_count вырос, счётчик «новых версий фактов: N», stale-бейдж aria-live — AC-блок 5 (частично, живой механизм 2-14; зонд пиннит).
- Given цель — матричное поле (price/availability/order_status), when record_correction с proposed_value, then outcome=disputed, строка коррекции с предложенным значением и spans, факт НЕ записан (версий не изменилось), системное значение не переписано, DeriveFactStatus НЕ тронут, сводка watermark НЕ тронут (actual — честная граница: спор не перезапись); панель: маркер «оспорено (значение системы не изменено)» + рекомендация словами повторного чтения — AC-блок 4.
- Given коррекция со summary_no ≥ 1, then сводка принадлежит кейсу (страж 400 чужой), связь зафиксирована строкой (FK) и в outbox идентификатором; сводка НЕ мутируется (append-only 2-14) — AC-блок 1 (связь с ТОЧНОЙ версией сводки).
- Given span НЕ присутствует в источнике (событии/тексте сводки) байт-в-байт, then 400 гвардом (анти-фантазийный зонд 2-8) — AC-блок 2 (source span исправления честен).
- Given proposed_value вне материальной дисциплины (не-JSON, >2048 канонических байт, экспоненциальный литерал), then 400 гвардом домена (прецедент 2-2).
- Given version_no вне [1..версий] / факт чужого кейса / сводка чужого кейса, then 400 стражем стора — AC-блок 8 (точность цели).
- Given повтор той же коррекции (тот же ключ, тот же материал), then replay исходной записи (идемпотентность 2-1); тот же ключ с иным материалом → 409 ErrCommandKeyConflict — AC-блок 8.
- Given ДВЕ разных коррекции одной версии факта (разные ключи), then обе строки + обе версии факта (N+1, N+2), конфликт трёх значений read-time conflicting, молчаливой перезаписи нет — AC-блок 8 (обе сохранены конфликтующими, разрешение — человек).
- Given терминальный кейс, when record_correction, then 400 work-rule; GET контекста отдаёт материал (чтение честно) — прецедент 2-14.
- Given оператор audit-only, when POST corrections, then 403 словами скоупа ДО стражей; не-участник → 404 ×пути; чужой tenant → RLS 404 — регресс 2-1.
- Given кейс БЕЗ коррекций, when GET decision-context/страница, then рендер байт-в-байт прежний (контрольная ветка; маркеры только с материалом) — регресс journeys 2-1..2-14.
- Given PRG-форма «Исправить» отправлена (value/span/reason/summary_no), then 303 → GET #decision-context, маркер на месте (якорь), точная позиция скролла не сохраняется (без JS) — прецедент 2-13.
- Given панель, when клавиатура/screen reader/320px, then old/new значения, источник, исход и последствия текстом; spans раскрываются по запросу (<details> — прецедент 2-14 provider-техника); цели ≥44×44; stale-бейдж aria-live — AC-блок 11.

## Implementation Notes

- Коррекция — акт ОПЕРАТОРА (долг корректности), не гейтится владением разговором (отличие от сводки 2-14 — акта продюсера-владельца): гейт — операторский скоуп review|configuration; клиентский канал-путь — второй срез (клиентский материал попадает сегодня через принятые события в spans-доказательства).
- Applied НЕ подтверждение: машина пишет версию (конфликт read-time), человек подтверждает существующей confirm_fact_version — AC-блок 2 «предложение не становится подтверждённым фактом автоматически» живым разделением команд (прецедент 2-6: AI предлагает, машина гейтит, человек подтверждает).
- Матричный гейт — решение ДОЕННО в словаре 2-7 (MaterialFieldInMatrix): price/availability/order_status → исход disputed без записи факта; повторное чтение — отдельный акт оператора read_owning_system (автоматики NEVER); Human Handoff — по решению оператора существующей командой 2-13.
- Staleness сводок — ЖИВОЙ watermark 2-14 (fact_version_count++): каскада на commitments/policy НЕ строим (честная граница AC-блок 5: обязательства 2-9 несут собственную валидность подтверждения точной версии, коррекция другого факта их не ломает; полный каскад — будущий срез).
- Спаны — дисциплина 2-8 (verbatim, ≤8×200 рун, байт-в-байт в источнике): источник = текст принятого события кейса ИЛИ текст сводки (две честные опоры evidence; гвард проверяет по указанному источнику).
- Source_id заливки 'correction:'+correction_id — в дисциплине 8..200 GuardRecordFact; материальная идемпотентность UNIQUE (tenant, source_type, source_id, material_key, value_digest) даёт replay при повторе — коррекция №N+1 от того же correction_id невозможна (append-only: новая коррекция = новый correction_id = новый ключ).
- Outbox идентификаторами (correction_no/outcome/fact/version/summary/spans-счётчик): proposed_value и spans НИКОГДА (прецедент 2-14 privacy-периметра).
