## Intent

**Problem:** Epic 1 закрыт 14/14: сотрудник настраивается, конфигурация запечатывается манифестом (1-12), правила работы утверждаются профилем с human coverage на каждый маршрут (1-13: Response Owner, часы, fallback), публикация контролируется действующими решениями с per-route admitted/blocked и активным указателем (1-14). Но у Epic 2 нет входа: в системе не было ни одного входящего события. Нет канонического Channel Event — провайдерские DTO не отделены от доменной модели контрактной границей; нет ingress-лестницы проверок (подлинность источника, Connection, Tenant, допустимость события) до создания Case; нет идемпотентного приёма (повторная доставка, digest-конфликты одного provider event ID); нет долговечных Case/Conversation/Work Item со стабильными бизнес-идентификаторами, первоначальным Response Owner из human coverage, `response_owner_epoch = 1` и единственной writable surface; нет protected payload reference (raw payload неотличим от метаданных в логах); нет операторской поверхности Cases (таймлайн, «запрос не классифицирован», текущий владелец); нет честных отказов с безопасной причиной и correlation ID. Архитектурное правило «инициирующий модуль коммитит доменное состояние и outbox record; обработка продолжается идемпотентно» заявлено с первой миграции identity, но ни разу не исполнялось: outbox-таблицы пусты и не имеют ни одного пишущего. Enforcement 1-14 не начат — решения о публикации существуют, но ни один входящий поток не сверяется с действующим решением.

**Approach:** Новый модуль `cases` (архитектурный модуль `case`; пакет Go — `cases`, слово `case` зарезервировано; спайн DAG: `case → identity/api, employee/api, connector/api`, только чтение; privacy и entitlement в DAG модуля не входят — их факты приходят ретрансляцией через employee). (1) Канонический Channel Event — доменная модель и версионированный контракт ingress: tenant, connection, provider, provider event ID, provider session ID, direction (в срезе — только `inbound`), modality (`text`|`voice`), channel + route (канал из словаря Brief + направление), provider timestamp, received timestamp, correlation ID (платформенный `platform/correlation`), payload digest (sha256) и защищённая ссылка (запечатанный blob + HMAC-печать по прецеденту knowledge sources); провайдерский DTO никогда не становится доменной моделью — адаптеры реальных провайдеров вне среза. (2) Ingress-лестница честных проверок ДО создания Case, каждая ступень — чистая функция домена над фактами: разбор envelope (строгий decode, словарные границы размера) → верификация источника порт `SourceVerifier` (в срезе — синтетический верификатор тестового контура: connection существует, окружение `test`; продакшн — fail-closed, реальных провайдеров и схем подписей нет, AG-4) → тенант-скоуп из проверенного connection (доверенные метаданные, не пользовательский принципал) → идемпотентный lookup: повтор того же события с тем же digest возвращает исходный результат ДО проверок admission (retry не зависит от изменившихся состояний) → состояние Connection (connector facts по ID: connected/revoked) → словарь канал→тип коннектора (`phone → SIP/telephony`, остальные восемь каналов → `chat/inbox`; несоответствие — честный отказ) → фасад фактов employee/api `RouteFacts` (по connection: действующие решения 1-14, чей запечатанный манифест содержит ConnectionFact этого connection — ноль решений → отказ «внешний трафик не допущен»; ровно одно → сотрудник и per-route результат; более одного → карантин + операционное исключение «неоднозначная маршрутизация») → первоначальный Response Owner из human coverage той версии профиля, что запечатлена в решении (проверка MembersFacts: участник существует и активен; отсутствие допустимого владельца — отказ, маршрут не допущен до внешнего трафика) → ретрансляция entitlement admission (hard limit → bounded outcome «новые обращения не принимаются») → load envelope (фиксированный консервативный словарь домена; превышение → bounded outcome с причиной и счётчиком). Каждый отказ — запись `cases.ingress_rejections` с безопасной причиной и correlation ID, без payload. (3) Приём — одна транзакция: find-or-create Conversation по (tenant, connection, provider session ID — единственная доказанная связь; не найдена → новый Case с монотонным `case_no` под блокировкой тенанта, прецедент decision_no, + Conversation со стабильным `conversation_no`, response owner, `response_owner_epoch = 1`, `writable_surface = inbox`; provider session ID хранится только как внешний идентификатор) + начальный Work Item `untriaged` (только при новой Conversation) + Channel Event + запечатанный payload + pre-case session record с объявленной capture policy (словарь) + outbox record принятого события (версионированный конверт: тип, версия схемы, aggregate, канонический JSON, dedup key) + outbox record connector-ack (подтверждение отправляется только согласно контракту коннектора; реальная доставка отложена). Повторная доставка идентичного события → идемпотентный результат, вторых записей нет; тот же provider event ID с иным материальным payload → событие `quarantined`, существующий Case не переписывается, создаётся операционное исключение для человека. Слияние обращений по совпадению имени, номера или предположению модели отсутствует как класс (доказанная связь — только продолжение channel session; связывание каналов — 2.3). (4) Поверхность оператора: Cases (список) + Case detail с Conversation Timeline (события — сам таймлайн: канал, modality, время провайдера и приёма, Connection, состояние), Work Item `untriaged` («запрос ещё не классифицирован»), текущий Response Owner, epoch, writable surface, явное «автоответ клиенту не отправляется»; доступность — клавиатура, screen reader, 320 px, aria-live по прецедентам Epic 1. Доступ к payload — серверная авторизация (`review`/`audit`), signed TTL-ссылки отложены. Отложено честно: адаптеры реальных провайдеров и схемы подписей (AG-4; верификатор — порт, продакшн fail-closed), media edge/SIP/RTP и медиа-контент звонков (AC-7: события телефонной сессии принимаются как метаданные сессии, активного media edge не существует), enforcement legal basis против data perimeter (AC-8: pre-case session record и объявленная capture policy хранятся; проверка основания — срез связки privacy, privacy не входит в DAG `case`), фоновые outbox-воркеры/leased jobs (записи + идемпотентная команда `DrainOutbox`; повторный запуск не теряет и не удваивает), метрики/OTel (Epic 6; причины и счётчики — в rejection-записях), bounded-очередь (честный отказ с причиной), классификация Work Item (2.2), связывание Conversations и identity (2.3), текстовые коннекторы (единственный создаваемый сегодня — staffy-synthetic-telephony; словарь и контракт текстовых каналов готовы, сквозной текстовый приём — с появлением chat-адаптера).

**Решение владельца:** ожидает CHECKPOINT 1. Предложение SM (первый срез по образцу 1-9…1-14, исполняет делегированное решение «запуск Epic 2, story 2-1»): демо-путь — inbound-событие телефонной сессии (event.inbound-call, modality voice, метаданные сессии) на синтетическом telephony-connection после публикации synthetic-стадии 1-14 → одна транзакция создаёт Case/Conversation/Work Item/событие/outbox; оператор видит Case и таймлайн; повтор идемпотентен; digest-конфликт карантинится с операционным исключением; честные отказы покрывают каждую ступень лестницы. Продакшн-трафик честно невозможен (нет провайдеров и подписей, нет действующих controlled-решений, AG-4) — enforcement 1-14 начинается ровно здесь: событие принимается только на маршруте, допущенном действующим решением о публикации, с допустимым первоначальным владельцем.

## Boundaries & Constraints

**Always:** Канонический контракт ingress версионирован и строг (DisallowUnknownFields, словарные границы размера envelope и payload-поля); провайдерский DTO не становится доменной моделью — граница адаптера заявлена портом, реальных адаптеров в срезе нет. Тенант-скоуп ingress строится только из верифицированного источника (connection) — доверенные метаданные задания; без скоупа никакого SQL; все таблицы `cases.*` tenant-scoped с RLS, гранты по прецеденту (INSERT/SELECT для append-only записей). Идемпотентность материальна: UNIQUE (tenant, provider, provider_event_id) и уникальный idempotency key; повтор с тем же payload digest возвращает исходный результат (те же идентификаторы, пометка replay) до проверок admission; повтор с иным материальным payload того же provider event ID — `quarantined` (существующий Case не переписывается) + операционное исключение; идемпотентные записи команд не используются для ingress (его идемпотентность — сама запись события, прецедент replay connector 1-9 сохранён семантически). Приём — ровно одна транзакция: Case + Conversation + Work Item + Channel Event + payload + pre-case session + outbox records; сбой любой ступени после источника — коммита нет (кроме записи отказа, которая коммитится отдельно и не содержит payload). Лестница адмиссии исполняется до создания Case в объявленном порядке; каждый отказ несёт вид причины (словарь: malformed, unknown_connection, revoked_connection, production_forbidden, channel_mismatch, route_not_admitted, no_active_release, ambiguous_employee, no_response_owner, entitlement_blocked, envelope_exceeded), безопасный текст и correlation ID; чувствительный payload не попадает в логи, отказы, исключения и ответы API (наружу — только digest и метаданные). Первоначальный Response Owner — только из human coverage версии профиля, запечатлённой в действующем решении 1-14 (route-точное соответствие маршруту события), с проверкой MembersFacts (участник существует и активен); владелец фиксируется при создании Conversation, epoch = 1, writable surface = `inbox` (единственная); ротация владельца и смена surface — 2.4. Маршрут события допускается только действующим решением 1-14 (per-route admitted; стадия решения — минимальная граница, enforcement остальных стадийных правил наращивается по мере поверхностей); событие в существующей сессии при изменившейся адмиссии — честный отказ fail-closed. Стабильные бизнес-идентификаторы: `case_no`/`conversation_no` монотонные под блокировкой тенанта; provider session ID — только внешний идентификатор conversation; слияние обращений по имени/номеру/предположению модели отсутствует как класс; caller ID и display name не доказывают личность (проверка личности — 2.3). Outbox: каждая запись несёт тип события, версию схемы, aggregate, канонический JSON и dedup key; команда `DrainOutbox` идемпотентна (исходы доставки — append-only записи, повтор команды не дублирует доставку); connector-ack записывается как outbox event по контракту коннектора, реальная отправка отложена (честная пометка). Полномочия: чтение Cases/Timeline — участники с `review`, `configuration` или `audit`; payload — только `review`/`audit`; ingress не является пользовательским принципалом; не-участник получает 404 без раскрытия Tenant; межтенантная изоляция — RLS во всех таблицах. UI: канал, modality, время (провайдера и приёма), Connection, состояние, владелец, epoch, surface доступны текстом и не только цветом; таймлайн семантически упорядочен (received_at, provider timestamp виден); «запрос ещё не классифицирован» и «автоответ не отправляется» — явные текстовые утверждения; цели ≥44×44 px, без горизонтального скролла на 320 px, aria-live без неожиданного перемещения focus. Privacy: новые классы словаря (`case-operations` — кейсы/события/метаданные; `case-content` — запечатанные payload с purpose-bound доступом), класс `outbox-events` расширяется таблицей `cases.outbox_events` (TestPerimeterIntegrity требует заявки всех новых таблиц); raw payload не входит ни в один ответ без полномочий. Load envelope — фиксированный консервативный словарь домена (границы envelope/payload и предел in-flight на connection); превышение — bounded outcome (честный отказ с причиной и счётчиком), никогда не приём с последующей молчаливой потерей.

**Never:** Не принимать событие мимо лестницы адмиссии и не создавать Case по непроверенному событию. Не верифицировать источник «позже» — подлинность проверяется до любых долговечных записей, кроме записи отказа. Не переписывать существующие Case, Conversation, Channel Event и outbox (грантов UPDATE/DELETE у событий и кейсов в срезе нет; история не редактируется). Не объединять обращения по совпадению имени, номера, caller ID, display name или предположению модели — вообще никак; слабое совпадение не создаёт задачу автоматического слияния (это 2.3, человеком). Не отправлять клиенту автоответ и любое исходящее сообщение (срез только фиксирует обращение; ответ — последующие stories). Не отправлять connector-ack вне контракта коннектора и не считать outbox-запись доставкой. Не создавать Business Action, Commitment или бизнес-политику на ingress (правило media edge AC-7 распространено на весь срез); состояния `generated`/`sent_to_provider`/provider playback не смешивать с подтверждением клиента — таких состояний в срезе нет, правило зафиксировано. Не хранить raw payload в логах, отказах, операционных исключениях и метаданных событий; не показывать payload без `review`/`audit`. Не выдумывать load envelope: до AG-1/AG-4-доказанных значений — фиксированный консервативный словарь, конфигурации на Tenant нет. Не расширять разрешение: один допущенный маршрут/канал/modality не допускает остальные; решение стадии не шире своих per-route результатов. Не считать идемпотентный replay новой активностью (счётчики и таймлайн не растут от повторов). Не доверять провайдерскому времени как времени приёма (оба сохраняются раздельно). Не пропускать события сверх envelope в очередь без записи (молчаливая потеря запрещена). Не подменять скоуп: ingress-скоуп живёт только внутри транзакции приёма и не становится пользовательской сессией.

## I/O & Edge-Case Matrix

- Given синтетический telephony-connection (окружение test) и действующее решение 1-14, допускающее phone:inbound на synthetic-стадии, when приходит корректное inbound-событие сессии (event.inbound-call, modality voice, метаданные, новый idempotency key и session ID), then в одной транзакции создаются Case (стабильный case_no), Conversation (conversation_no, response owner из human coverage, epoch 1, writable surface inbox), Work Item untriaged, Channel Event с запечатанным payload, pre-case session record и outbox records; оператор видит Case и таймлайн; автоответ не отправляется.
- Given то же событие доставлено повторно (тот же idempotency key и payload digest), when ingress обрабатывает повтор, then возвращается исходный результат (те же идентификаторы, пометка replay); вторых Case, Conversation, Work Item или записей таймлайна нет; счётчики не растут.
- Given тот же provider event ID с иным материальным payload, when digest не совпадает, then новое событие переводится в `quarantined`, существующий Case и Conversation не переписываются, создаётся операционное исключение для человека (видно оператору с correlation ID).
- Given неизвестный connection, отозванный connection, production-окружение, коннектор без верификатора, when источник проверяется, then отказ до создания Case; в `ingress_rejections` — вид причины, безопасный текст, correlation ID; payload не сохранён и не залогирован.
- Given событие заявляет канал, не соответствующий типу коннектора connection (web_chat на SIP/telephony), when проверяется словарь канал→тип, then честный отказ channel_mismatch с именем канала и типа.
- Given connection не входит ни в один запечатанный манифест действующих решений 1-14, when разрешается маршрутизация, then отказ no_active_release «внешний трафик не допущен» — enforcement 1-14 работает на входе.
- Given два сотрудника имеют действующие решения, запечатляющие один connection, when разрешается маршрутизация, then событие карантинится, создаётся операционное исключение ambiguous_employee, Case не создаётся (политика выбора — вне среза, человек решает).
- Given маршрут события admitted, но response owner из human coverage не существует или неактивен (участник покинул Tenant), when проверяется первоначальный владелец, then отказ no_response_owner «маршрут не допущен до внешнего трафика» с идентификатором владельца разблокирования.
- Given entitlement в hard limit (ретрансляция факта через employee), when приходит новое обращение, then bounded outcome entitlement_blocked «новые обращения не принимаются»; запись отказа создана; повтор того же события (уже принятого ранее) всё равно возвращает исходный результат — replay идёт до admission.
- Given входящая нагрузка connection превышает in-flight предел словаря или envelope превышает границы размера, when admission ограничивает приём, then bounded outcome envelope_exceeded с причиной и счётчиком; событие не принято; молчаливой потери нет.
- Given приём закоммичен, но worker/UI временно недоступны, when материал читается позже, then Case, события и outbox долговечны; `DrainOutbox` идемпотентно доводит исходы доставки; повторный запуск процесса не теряет и не удваивает записи (append-only исходы).
- Given событие в существующей сессии (тот же provider session ID на том же connection), when сессия найдена, then событие добавляется в существующие Conversation и Case (нового Work Item нет); если адмиссия с тех пор заблокирована — честный отказ fail-closed, сессия не расширяется.
- Given пользователь другого Tenant или процесс без скоупа, when запрашиваются Case, Conversation, событие или payload, then RLS и серверная авторизация блокируют доступ (404 без раскрытия Tenant); payload — только `review`/`audit`.
- Given Cases и Conversation Timeline на поддерживаемом браузере, when оператор работает с клавиатуры, screen reader, с увеличенным текстом или на 320 px, then канал, modality, время, Connection, состояние, владелец, epoch и surface доступны текстом; таймлайн семантически упорядочен; горизонтального скролла нет; цели ≥44×44 px.

## Code Map

**Acceptance Criteria:**
- Given поддерживаемый connection получает входящее событие, when ingress подтверждает источник, Tenant, Connection и допустимость, then событие преобразуется в канонический Channel Event с полным набором полей и защищённой ссылкой на payload; provider DTO не становится доменной моделью.
- Given событие с неверной подписью/источником, неизвестным Connection, отозванными credentials, недопустимым размером или нарушенным tenant scope, when ingress проверяет, then отказ до создания Case; безопасная причина и correlation ID сохранены; чувствительный payload не попадает в общий лог.
- Given событие с новым tenant-scoped idempotency key, when принимается впервые, then в одной транзакции создаются Case и Conversation, начальный Work Item `untriaged`, response owner из human coverage, epoch 1, одна writable surface; сохраняются событие и outbox records; подтверждение connector — только по его контракту (outbox, доставка отложена честно).
- Given повторно доставлено идентичное событие, when ingress обрабатывает повтор, then вторых записей нет, connector получает идемпотентный результат; replay идёт до проверок admission.
- Given тот же provider event ID с другим материальным payload, when digest не совпал, then `quarantined` + операционное исключение; существующий Case не переписывается.
- Given новое обращение без доказанной связи, when создаётся Conversation, then стабильные бизнес-идентификаторы, channel session ID — только внешний идентификатор; объединения по имени/номеру/модели нет.
- Given приём закоммичен, а worker/UI недоступны, when материал читается позже, then долговечность обеспечена записями и идемпотентным `DrainOutbox`; повторный запуск не теряет и не удваивает.
- Given оператор открывает Cases, when обработка завершена, then видны Case и Conversation Timeline с каналом, временем, Connection и исходным состоянием; «запрос ещё не классифицирован», текущий Response Owner, epoch, writable surface; автоответ не отправляется.
- Given другой Tenant или процесс без скоупа, when запрашиваются данные, then RLS и серверная авторизация блокируют; payload ограничен полномочиями и Tenant.
- Given нагрузка превышает envelope, when admission ограничивает, then настроенный bounded outcome честен, причины и счётчики записаны, молчаливой потери нет.
- Given Cases и Timeline, when клавиатура/screen reader/320 px, then статусы текстом, порядок таймлайна семантически понятен, без горизонтального скролла, цели ≥44×44 px.

## Implementation Notes

- Порядок лестницы заявлен в Intent; replay идёт до admission — retry отправителя не зависит от изменившихся состояний (решение SM по AC-4; записать тестом: entitlement pause после приёма не ломает retry).
- `case_no`/`conversation_no` — монотонные под блокировкой агрегата тенанта (паттерн decision_no 1-14); UUID — технические PK.
- Payload: blob + sha256 digest + HMAC-печать (прецедент knowledge sources 1-5: случайный ключ, наружу не отдаётся); чтение — только `review`/`audit`, signed TTL-URL отложены (deferred-work).
- Outbox: паттерн таблиц существует с 1-1/1-8 (identity/employee/connector); срез впервые исполняет правило записи: тип, версия схемы, aggregate, канонический JSON, dedup key; `DrainOutbox` — команда с append-only исходами (доставка провайдеру отложена — запись в deferred-work).
- RouteFacts-фасад employee: потребляет DeriveActiveRelease + manifest ConnectionFacts + human coverage запечатленной версии профиля + entitlement relay (внутри employee порт entitlement уже существует — 1-14); случай «более одного сотрудника» — карантин, политика выбора вне среза.
- Privacy/entitlement не входят в DAG `case` (архитектура): ретрансляция фактов через employee/api; прямые импорты запрещены — расширить `architecture_test.go` забором `internal/cases/store` и проверить DAG-правило импортов модуля.
- Синтетический верификатор — единственная реализация порта (окружение test; прецеденты authdev/verifier-synthetic 1-9/step-up-фикстура); production fail-closed честно: реальных провайдеров нет, AG-4.
- Текстовые каналы: словарь и контракт готовы; единственный создаваемый коннектор — staffy-synthetic-telephony (SIP/telephony); интеграционные текстовые сценарии проверяют честный отказ channel_mismatch; сквозной текстовый приём — с chat-адаптером (deferred-work).
- Телефонная сессия в срезе — метаданные события (modality voice без медиа); media edge/SIP/RTP — вне среза (AC-7 отложен честно).
- Privacy-классы: словарь 18 → 20 (`case-operations`, `case-content`), `outbox-events` расширяется `cases.outbox_events`; TestPerimeterIntegrity синхронно.
- Journey-фикстура: фикстурный мир с настоящими доменными функциями (паттерн readiness_fixture), BindCases; UI-цепочка: Cases список → detail → таймлайн → повторы → карантин-исключение.
- Проверки на текущем дереве: `go test ./...`, `go vet ./...`, `go test -tags=integration ./tests/integration/...`, `npm test --prefix tests/journeys`, контракт-тест OpenAPI, `git diff --check`.

## Design Notes

- Именование: архитектурный модуль `case`; пакет Go — `cases` (слово `case` зарезервировано языком), миграции — `migrations/cases/`; спайн DAG сохранён (case → identity/api, employee/api, connector/api, только чтение).
- Enforcement 1-14 начинается здесь: действующее решение — вход ingress-адмиссии; стадии выше synthetic сегодня не действуют (ни одного gate PASS, eval not executed) — контролируемый трафик возможен только в тестовом контуре, что и есть демо-путь.
- Честные вечные блокировки среза: (1) реальных провайдеров и схем подписей нет — продакшн-источники fail-closed (AG-4); (2) media edge не существует — телефонные события без медиа; (3) legal-basis enforcement отложен до связки privacy; (4) фоновых воркеров нет — доставка идемпотентной командой.
- AC-7 (media edge), AC-8 (legal basis enforcement), фоновая доставка outbox, метрики, текстовые коннекторы и bounded-очередь — честные отложения среза; «не объединять по имени/номеру» реализовано отсутствием merge-логики как класса.
- Связь с deferred-work 1-14: per-route маппинг capability→маршрут остаётся агрегатным для readiness; ingress идёт route-точным путём через решения 1-14 (расширение факт-порта здесь не требуется).
