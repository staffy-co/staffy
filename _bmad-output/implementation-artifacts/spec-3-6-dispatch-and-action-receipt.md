## Implementation Notes

- Решение «submitted/accepted» слэша эпика: submitted = write-ahead-запись lease-транзакции ДО сетевого вызова (persist-before-emit AD-6; resting-состояние краха между отправкой и записью исхода — lease покажет восстановление), accepted = провайдер подтвердил приём запроса из ответа адаптера (не-терминальное). Оба слова — реальные различимые состояния (AC-13), каждое честно своим текстом; слэш эпика «Operation получает submitted/accepted» исполняется парой переходов. Решение задокументировано как прецедент «step-up на confirm, НЕ на authorize» 3-5.
- exhausted НЕ фенция dispatch-гейта: после успешной авторизации потребление Confirmation — ОЖИДАЕМОЕ состояние (лестница 3-5 {superseded→revoked→expired→exhausted} описывает отказ НОВОЙ авторизации, а не диспетчерство уже созданной Operation). Dispatch-гейт читает ТОЛЬКО {superseded, revoked, expired} — зонд: single_use операция с consumed=1 диспетчится свободно при прочих зелёных. Отзыв/замена/истечение гасят queued intent ДО отправки (FR-28) — «гасит будущие авторизации» 3-5 расширяется на «гасит нераспечатанную отправку» материально.
- Внешний idempotency key — производное ОПЕРАЦИИ (tenant, operation_id), НЕ материала и НЕ клиентского idempotency_key: все попытки одной операции несут ОДИН внешний ключ (провайдер дедупит повторы — AC-10), эквивалентная мутация из другого Case невозможна (cross-case проиграл резервацию 3-5 — до dispatch не доходит). Три пространства ключей (клиентский idempotency_key / business_intent_key / внешний dispatch-ключ) разделены доменными префиксами и назначениями — ни один не выводится из другого.
- «Сверка ответа провайдера с первоначальным payload digest» (AC-10) материализуется пересборкой: worker детерминированно строит payload из неизменяемых строк и свериет DeriveDispatchRequestDigest с записанным в lease первой попытки — совпал = та же операция тому же адресату (честный skip), разошёлся = integrity alarm. Сырой payload не хранится НИКОГДА — сверка идёт по keyed-HMAC следу.
- Гарантия повтора читается из ЗАПИСАННОГО слова исхода attempt (решение повторного drain не перечитывает живую декларацию — прецедент 3-3 «belt over braces»: живое слово может измениться между попытками, записанное — факт аудита). LIVE-декларация читается в момент записи исхода.
- Lease-окно = definition.TimeoutMS + grace 30с: lease переживает возможный вызов (истечение при живом вызове ложно), истёкшая lease = воркер мёртв (крах) — восстановление только по политике. Fencing-токен = attempt_no (монотонный); lease_token идентифицирует держателя при записи исхода.
- Повторная доставка задания моделируется дубликатом outbox строки (PK события — event_id, вторая строка той же операции легальна: UNIQUE на (tenant, operation_id) в outbox НЕТ намеренно — at-least-once семантика очереди). Worker обрабатывает каждое ЗАДАНИЕ, но не каждое задание отправкой: классификация pending-запроса — единственный диспетчер решений.
- Receipt v1 создаётся на ПЕРВОМ решающем исходе {committed, failed, unknown}; accepted — итога ещё нет, квитанции нет (не-терминальное ожидание — текст «бизнес-результат не подтверждён»). Позднее evidence (3-7 reconciliation) допишет v2+ append — версионность заложена UNIQUE (tenant, operation_id, receipt_version_no), v1 неприкосновенна.
- Ссылка Work Item/Conversation на receipt = событие receipt.created собственного outbox модуля action (AD-2: прямой записи в чужие таблицы нет). Потребитель события — будущий контур (проекция таймлайна); записи честно копятся pending — зеркальный прецедент 3-5 «operation.queued копится pending до 3-6»: здесь receipt.created копится до будущего потребителя.
- Fixture-вертикаль: synthetic адаптер обслуживает capability fixture-определений (LIVE-чтение каталога — command.send-sms Idempotent=true); override гарантии закрывает строки «без гарантии» БЕЗ нового определения (прецедент ScriptGuarantee 3-3); /fixture/clock закрывает lease-истечение и valid_until; тумблеры 3-4/3-5 (preview-material, step-up) reused для фенций. Мир путей, не продуктовая персистентность — прецедент fixture-миров 3-3..3-5.
- Journey-мир 3-6: полный живой путь z33 (submit→confirm→authorize) reused до authorized/queued, затем drain машинным путём с scriptable исходами; второй ingress-кейс 3-5 (AC-9 эквивалентность) reused для decided-verify строк (проигравший reference — до dispatch не доходит, резервация одна).
- Drain — явная команда (operator scope manage, прецедент external-commitments/drain 3-3): НИКАКОГО фонового демона/ticker — планировщик будущая инфраструктура (честная граница; CI-контур прогонов не требует демона). Production: nil-адаптер = честный отказ словами — очередь копится pending (AG-4, прецедент DrainExternalCommitments).
- Шаги не трогают замороженные секции СПЕК 3-1..3-5 (код эволюционирует surgical-правками; тексты 3-5 OperationDispatchAbsentText/OperationExternalIDAbsentText заменяются словами живого контура — код, не спека); gofmt только touched-файлы слайса (урок 3-4/3-5: легаси-аномалии нетронутых файлов не чурнятся).
