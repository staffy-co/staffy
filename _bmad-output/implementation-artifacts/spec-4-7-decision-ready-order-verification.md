## Intent

**Problem:** квитанция 4-6 несёт слово-обещание `OrderManagerAssignmentWord` («заказ назначается проверяющему менеджеру согласно утверждённой политике (задача проверки — контур 4-7)») — механики НЕТ: delegated task не существует ни в одной таблице, назначения нет, deadline/backup-словарей проверки нет, «назначение ≠ принятие» нечему держать (прецедент 2-13 закрывал это для запроса человека — якорь turn_ref; задача заказа требует ДРУГОЙ якорь: операцию/квитанцию). Экрана проверки не существует: менеджер (в пилоте owner — единственный участник с Review+Commercial по живой грант-матрице identity: Operator = Operations+Claims, Review-скоупа нет) видит панель «Заказ клиента» с клиентскими словами, но НЕ decision-ready контекст проверки — нет одной собирающей поверхности с подтверждённым Vehicle+VIN, исходным Part Request, позициями с OEM/артикулами и якорями Fitment Evidence, условиями Supplier Offer, версиями Commitment/Confirmation, Operation ID/idempotency/correlation/квитанцией/внешним ID и словом 1С-unknown вместе (страница кейса несёт панели по отдельности, но без задачи-контейнера, пина точной версии и ЯВНЫХ различий). Human Verification Receipt не существует: решение проверки не записывается никуда, «решение нельзя применить к изменённой или более новой версии» (AC-10/AC-14) нечему держать — лестница 4.5 гейтит только dispatch. Уведомление/дедлайн честно не различаются: слов «назначен ≠ доставлено ≠ принял» для задачи проверки нет, overdue-деривации нет. Забор контура: интерфейс не говорит словами, ЧТО именно гарантирует Staffy (а что — только политика магазина: ABCP-обход руками возможен).

**Approach:** модуль action (задача живёт над операцией/квитанцией заказа — операция и квитанция суть сущности action-модуля; живой материал заказа уже деривируется там же). Восемь частей: (1) домен `internal/action/domain/order_verification.go` — типы, гварды поимённой матрицы, словари compile-time (состояния-слова 4 событий + read-time слова overdue/неприменимости; дедлайны {verify_4h, verify_1d} с честными текстами; причины blocked из 5 слов; честные слова уведомления/fence/ручного контура), DeriveOrderVerificationState + неприменимость решения; (2) миграция `migrations/action/00006_order_verifications.sql` — 2 append-only таблицы с RLS/CHECK-зеркалами словарей; (3) app-сервис 5 команд (assign/acknowledge/approve/block/reassign) с забором решения живой ре-деривацией и CAS assignment-эпохи; (4) экран «Проверка заказа» на странице кейса (сборка контекста чтением живых панелей + операции/квитанции + задачи; закупочная цена по Commercial-скоупу); (5) маршруты JSON+PRG; (6) OpenAPI-зеркала; (7) интеграционная eval-матрица AC-15 поимённо; (8) journeys z44.

**Ядро честности среза:** задача проверки — запись с жизненным циклом событий, НЕ передача владения кейсом (термы 2-4 не трогаются); решение — append-only событие с материальными пинами (order_digest hex + receipt identity + Work Items/evidence-якоря), применяемое ТОЛЬКО к той же материальной версии (живая ре-деривация тем же кодом лестницы 4.5 ДО записи; расхождение = отказ BY NAME + явные различия + повторная полная проверка); истечение дедлайна — read-time слово overdue, автоматического одобрения структурно НЕТ (approve — только явное событие принятого assignee); уведомление — честные слова поверхности (внешнего канала НЕТ — прецедент 2-13 Never); Staffy НЕ отправляет заказ поставщику (supplier-send не существует — зонд 0) и НЕ изображает гарантию fence за пределами своих слов: честное слово говорит, что обход проверки руками в ABCP возможен, формирование/отправка — ручное действие менеджера в фактическом контуре магазина, статус читается отдельно из Owning System (unknown).

## Boundaries & Constraints

**Always:** обе таблицы append-only — гранты INSERT/SELECT, RLS + FORCE ROW LEVEL SECURITY, UPDATE/DELETE/TRUNCATE нет; CHECK-словари событий/дедлайнов/причин = compile-time словари домена (миграция зеркалит); UNIQUE (tenant, case, verification_no) и UNIQUE (tenant, case, verification_no, event_no) — монотонность, история никогда не правится; DeriveOrderVerificationState/неприменимость решения — read-time, нигде не мутируются; якорь задачи — committed-операция create_abcp_customer_order с квитанцией (operation_id FK + receipt identity + внешний ABCP Order ID из receipt_references); assign/assignee-валидация по живой грант-матрице identity (assign actor — Review-скоуп; assignee — участник с Review-скоупом; backup — участник; Commercial-скоуп актёра решает видимость закупочной цены на экране); acknowledge/approve/block — actor=assignee (серверная истина), expected assignment-эпоха (event_no последнего assigned) — CAS под локами; забор решения — живая ре-деривация DeriveOrderCommitmentMaterial над свежим CaseView ДО записи события (код reused лестницы 4.5, НЕ новый шаг dispatch); событие approved несёт материальные пины: order_digest 64-hex, receipt identity, Work Items/evidence-якоря; событие blocked несёт затронутые позиции (проверяются против состава операции) + причину словом; экран — сборка ТОЛЬКО чтением живых панелей и портов (новых записывающих путей данных нет, кроме 5 команд задачи); все слова состояний/границ — словари домена; OpenAPI зеркалит словари; регресс — build/vet/unit + интеграция ×2 TZ + journeys + скан.

OQ-2 вне среза); НЕ строить автоматический backup-переключатель, воркеры и таймеры (AG-4/AD-14: runtime-workers вне среза; overdue — read-time деривация; fallback истечения = ЯВНОЕ переназначение человеком — reassign;
