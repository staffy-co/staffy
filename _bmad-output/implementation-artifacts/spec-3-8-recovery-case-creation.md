## Intent

**Problem:** Между honest-словами 3-6/3-7 («требуется человек» — исчерпана сверка, сверка не объявлена, конфликт терминальных итогов, повтора нет) и предметом работы человека отсутствует весь контур восстановления (FR-38, AC-блоки 1-12 эпика 3.8): оператор видит слово «требуется человек» на карточке операции, но в системе НЕТ объекта восстановления — отдельного Recovery Case со связями, доказательствами, владельцем и дедлайном. Доказательства разбросаны по таблицам action (операция, ledger, квитанции, lease, исходы), назначение никто не делает, повторный триггер не идемпотентен, панелей нет.

**Approach:** Модуль `internal/action` (таблица возможностей архитектуры: «Business mutation, receipt and recovery → action + connector»; AD-2 DAG без новых рёбер — те же прямые типовые чтения case/api (ownership исходного Case), employee/api (route facts — human coverage), identity/api, connector/api; recovery-контур пишет ТОЛЬКО собственные таблицы action, связь с Case/Work Item — пины UUID без FK и без записей в cases-таблицы). Явная команда оператора одной операцией (drain-прецедент, демона нет); eligibility по записанному состоянию; идемпотентность структурой (UNIQUE + keyed-HMAC ключ); link-bundle из SAFE-пинов; назначение живыми чтениями с fail-closed; append-only события + outbox; Recovery Panel с живой деривацией и a11y.

**Ядро честности среза:** создание Recovery Case — ЛОКАЛЬНЫЙ контур: НИ ОДНОГО сетевого вызова в пути (адаптеры структурно отсутствуют из команды — сеть остаётся в dispatch/reconcile); ни один газ лестницы НИЧЕГО не пишет (счётчики фейк-репо пинят); материал НИКОГДА не копируется (ссылки-пины вместо копий — AD-10/AC-9); неизвестное остаётся unknown (платежи, отсутствие внешнего объекта); исходный Case, операция и квитанции НИКОГДА не переписываются (append-only везде, «исходный Case не открывается повторно для перезаписи» — структурно).

## I/O & Edge-Case Matrix

- Given unknown-операция с исчерпанной сверкой (3 lease-попытки, окна истекли — /fixture/clock), when POST /v1/tenants/{t}/operations/{op}/recovery-case, then 201 создан: recovery_case_no монотонный, trigger reconciliation_exhausted, владелец/backup/deadline живыми чтениями, bundle SAFE-пинов, событие created, outbox recovery_case.created — AC-1.
- Given unknown-операция и сверка не объявлена (ReconciliationQuery пуст либо LIVE-слово пусто), when команда, then 201 создан с trigger reconciliation_unavailable — AC-1/AC-9-минимум 3-7 («ручная задача — 3-8» исполняется).
- Given production AG-4 (адаптер сверки nil — факт композиции) и unknown-операция, when команда, then 201 создан с trigger reconciliation_unavailable — автоматический контур недоступен, человек обязателен (честный production-путь среза).
- Given failed-операция с dispatch-попытками 3/3 либо retry-политикой без гарантии (нет provider_idempotent, нет no_effect-вердикта), when команда, then 201 создан с trigger operation_failed — AC-1 «доказанная ошибка, требующая человека».
- Given committed-операция, when команда, then 403 словами «восстановление не требуется: итог committed» ДО любой записи — честный отказ.
- Given unknown-операция с попытками сверки < 3 и доступной сверкой, when команда, then 403 «автоматическая сверка не исчерпана — сначала контур сверки (3-7)» — право автоматики не отбирается.
- Given failed-операция с retry-правом (no_effect записан, попытки < 3), when команда, then 403 «повтор доступен решением политики — восстановление преждевременно».
- Given операция в authorized/submitted/accepted/queued, when команда, then 403 «операция ещё в исполнении» — очереди/отправка/сверка живы.
- Given неизвестная операция либо чужой тенент, when команда, then 404 (membership-404 ДО материала — прецедент 3-6/3-7).
- Given повтор команды при существующем кейсе и НЕИЗМЕНЁННОМ bundle_digest, then 200 идемпотентно: существующий вид + слово «Recovery Case уже существует», второй строки НЕТ, события НЕТ — AC-5.

## Implementation Notes

- Решение модуля: Recovery Case — собственный агрегат action.recovery_cases в модуле action (таблица возможностей архитектуры: «Business mutation, receipt and recovery → action + connector»; AD-4 «linked Recovery Case» исполняется пинами UUID на Case/Work Item/Operation/Receipt — прецедент operations 3-5: case_id/work_item_id без FK и без записей в cases-таблицы). Домен cases не знает recovery (без новых рёбер DAG); событие recovery_case.created копится pending для будущих потребителей (claim-режим AC-2, контур 3-9) — прецедент receipt.created 3-6.
- AC-1 «назначает согласно Operating Profile»: срез материализует минимум честно — владелец = ТЕКУЩИЙ Response Owner исходного Case (терм максимального epoch, живое чтение — владелец разговора владеет восстановлением), backup и deadline = human coverage маршрута исходной conversation (RouteFactsSource — Operating Profile-материал 1-13, канон coverageWord cases/app: слово НИКОГДА из параметров команды). Полная recovery-политика профиля (очереди/роли/эскалации) — будущий срез; непрочитанное покрытие = fail-closed отказ (назначение обязательно — «назначает» не бывает без назначения).
- AC-2 вне среза: триггер среза — failed Operation (AC-1), не событие клиента; claim-классификация входящих и подъём Conversation Mode в claim — будущий срез (режим — домен cases, событие копится); «исходный Case не открывается повторно для перезаписи» — уже структурно (append-only везде).
- AC-3 соответствие словарю эпика: «Commitment» = Confirmation 3-5 (consent-обязательство цепочки над точной версией — дисциплина 2.9); отдельного 2.9-пина в action-цепочке структурно нет — срез не выдумывает связь (честная граница); payment/settlement = honest unknown-слово (AG-4: платёжных систем нет); «неизвестное состояние явно остаётся unknown» — NULLable внешние id + unknown-слова видов.
- AC-4: карточка читает последнюю квитанцию ЖИВОЙ деривацией (Owning System/внешние id/версия/время; отсутствует = unknown); «локальная копия не выдаётся за актуальное внешнее состояние» — фиксированные слова; read-only сверка = существующая команда 3-7 (нового пути запроса НЕТ — поверхность карточки операции ссылает).
- AC-5/AC-10-минимум: recovery key = keyed-HMAC пина операции → второй активный кейс невозможен (UNIQUE); повтор с дельтой = ОДНА append-only строка evidence_appended (новое evidence к существующему кейсу; контекст обновляется ссылкой, исходные записи не переписываются); конфликт «тот же ключ с другим материальным объектом» в срезе невозможен структурно (ключ выводится ИЗ пина операции) — компаратор пинится юнит-тестом для будущих claim-триггеров (дисциплина digest-компараторов 3-6/3-7).
