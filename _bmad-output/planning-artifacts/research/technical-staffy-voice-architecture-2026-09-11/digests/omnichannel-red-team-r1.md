# Omnichannel architecture red-team — round 1

**Decision challenged:** whether Staffy needs to own a canonical conversation/action core, separate action gateway and operation ledger, explicit versioning and write leases, plus one adapter per channel, before two pilots.

**Verdict: survives with simplification.** The conclusion that model + tools/RAG/MCP alone is insufficient survives: the official MCP project says tool annotations are untrusted hints rather than enforcement. However, the proposed Staffy-owned surface is too large for two pilots. Managed runtimes and communication/inbox platforms can own most turn state, channel normalization, routing, human handoff, and traces. Staffy should initially own only the business-action safety boundary and the small amount of cross-provider state that the selected platforms demonstrably do not provide.

## Strongest contrary evidence

### 1. A managed agent runtime can remove a custom conversation/run engine

OpenAI now exposes provider-managed agent sessions with retrievable session state, statuses, required actions and usage; its Agents SDK also includes persistent sessions, human-in-the-loop controls, MCP, guardrails and tracing. For a pilot, this is credible evidence that Staffy does not need its own general agent loop, run-state machine, or generic trace substrate.

- Evidence: [OpenAI Managed Agents session API](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/agents/subresources/sessions/methods/retrieve) — publisher: OpenAI; date: n.d. (live API reference, retrieved current on 2026-09-12); accessed: 2026-09-12; confidence: **high** for advertised API shape, **medium** for production durability because the API is under `beta`; class: **current compatibility / managed-runtime capability**.
- Evidence: [OpenAI Agents SDK overview](https://openai.github.io/openai-agents-python/) — publisher: OpenAI; date: n.d. (live SDK documentation, retrieved current on 2026-09-12); accessed: 2026-09-12; confidence: **high** for SDK capabilities, **medium** for replacing business audit; class: **current compatibility / AI landscape**.

The contrary evidence does **not** show that provider state is a durable business record. The cited materials describe working context, required actions, traces and usage; they do not promise an immutable record of the external side effect or a business-specific authorization decision. Therefore they can replace generic conversation/run infrastructure, not the minimum action/audit record.

- Evidence: [OpenAI Managed Agents session API](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/agents/subresources/sessions/methods/retrieve) — publisher: OpenAI; date: n.d. (live API reference); accessed: 2026-09-12; confidence: **medium** because this is an inference from the documented response fields and absence of an immutable-effect guarantee, not a documented product limitation; class: **managed-runtime gap / inference**.

### 2. Twilio can supply the conversation/channel core — but only inside its channel set

Twilio Agent Connect is the strongest simpler alternative found. Twilio says it handles channel webhooks and voice WebSockets, Conversations lifecycle coordination, memory/profile retrieval, session mapping, channel routing, tools, and human handoff. Its documented channel abstraction covers Voice, SMS, WhatsApp, RCS and Chat, so a Twilio-aligned pilot could delete Staffy's canonical channel model and most channel adapters.

- Evidence: [Twilio Agent Connect overview](https://www.twilio.com/docs/conversations/agent-connect/overview) — publisher: Twilio; date: n.d. (live documentation, retrieved current on 2026-09-12); accessed: 2026-09-12; confidence: **high** for advertised components and supported channel families; class: **current compatibility / managed omnichannel platform**.

This does not overturn the candidate architecture for the named first channels. Telegram, MAX and Jivo are absent from the documented TAC channel list, TAC explicitly says it is middleware rather than an agent runtime, and active conversations are instance-local unless deployment adds the recommended scaling controls. It is a real replacement option for a different channel mix, not a drop-in replacement for the proposed pilot mix.

- Evidence: [Twilio Agent Connect overview](https://www.twilio.com/docs/conversations/agent-connect/overview) — publisher: Twilio; date: n.d. (live documentation); accessed: 2026-09-12; confidence: **high** for documented omissions and instance-local state, **medium** for the conclusion that it is unsuitable because commercial/regional fit was not researched; class: **current compatibility / deployment constraint**.

### 3. An omnichannel inbox can replace Staffy's canonical conversation model for the pilots

Chatwoot already places every conversation in an inbox, supports a website widget and Telegram natively, offers assignment/routing options, and has an API Channel for unsupported messengers. That is enough to test a materially simpler spine: Chatwoot as the operator inbox and conversation system, one direct MAX bridge through API Channel, and no Staffy-owned canonical conversation aggregate.

- Evidence: [Chatwoot channel and inbox guide](https://www.chatwoot.com/hc/user-guide/articles/1677492191-adding-inboxes) — publisher: Chatwoot; date: 2026-04-29; accessed: 2026-09-12; confidence: **medium** for current compatibility because the page is older than the one-month compatibility window, **high** for the documented product model; class: **omnichannel inbox capability / compatibility unverified within freshness bar**.

This simplification carries operational risk rather than eliminating it. Chatwoot's latest release in the retrieved feed is v4.17.1 (2026-08-27) and includes fixes for duplicate Facebook messages, channel login, widget refreshes, and security hardening. The evidence shows an active project but also that channel-edge regressions occur, so a minimal dedupe/effect record at Staffy's boundary remains prudent.

- Evidence: [Chatwoot releases](https://github.com/chatwoot/chatwoot/releases?after=v1.11.0) — publisher: Chatwoot on GitHub; date: 2026-08-27 (v4.17.1); accessed: 2026-09-12; confidence: **high** for release contents, **medium** for extrapolating general channel risk from listed fixes; class: **ecosystem signal / production-maintenance evidence**.

### 4. MAX prevents a zero-state adapter strategy

MAX's current official docs state that `GET /chats` has been unsupported since June 2026 and put chat-ID collection, persistence, deletion and duplicate handling on the developer. Therefore even if Chatwoot owns the canonical conversation, the MAX bridge must keep a small provider-ID/dedupe table. This is strong evidence against both extremes: a large cross-channel canonical model is unnecessary, but a stateless webhook relay is unsafe.

- Evidence: [MAX `GET /chats` migration guidance](https://dev.max.ru/docs-api/methods/GET/chats) — publisher: MAX; date: June 2026 change, live docs current on access; accessed: 2026-09-12; confidence: **high**; class: **current compatibility / provider delivery-state requirement**.

### 5. Jivo is useful as an edge/handoff product, not a universal spine

Jivo's Bot API is a Jivo-initiated webhook flow with a three-second timeout, two retries and automatic transfer to an agent on failure; its events include Jivo chat, client, channel and agent-presence identifiers. This makes it a useful thin integration when a pilot already runs human support in Jivo, but not evidence for making Jivo the cross-channel system of record.

- Evidence: [JivoChat Bot API](https://www.jivochat.com/docs/bot/) — publisher: JivoChat; date: n.d. (live documentation, copyright 2026); accessed: 2026-09-12; confidence: **high** for protocol behavior, **medium** for architectural fit; class: **current compatibility / channel-adapter constraint**.

### 6. MCP-native execution cannot delete policy enforcement

The MCP project's own maintainers state that tool annotations are untrusted hints, do not resist prompt injection, and are not enforcement; hard guarantees require host-layer controls such as sandboxing or network policy. Therefore MCP can standardize discovery and invocation, and a managed host may supply approvals, but MCP itself cannot replace the application's authorization and effect-control boundary.

- Evidence: [Tool Annotations as Risk Vocabulary: What Hints Can and Can't Do](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/) — publisher: Model Context Protocol project; date: 2026-03-16; accessed: 2026-09-12; confidence: **high**; class: **architecture/security pattern**.

## Minimal pilot architecture that survives the red team

1. **System of engagement:** Chatwoot owns web/Telegram conversations, routing, assignment and human operations. This is a recommendation derived from its documented native channels and API Channel, not a verified deployment result. Evidence: [Chatwoot guide](https://www.chatwoot.com/hc/user-guide/articles/1677492191-adding-inboxes), publisher Chatwoot, 2026-04-29, accessed 2026-09-12, confidence medium, class architecture inference.
2. **MAX edge:** one thin bridge persists `{provider_event_id, chat_id, contact mapping, delivery state}` and forwards into Chatwoot API Channel; uniqueness handles duplicate updates. Evidence: [MAX guidance](https://dev.max.ru/docs-api/methods/GET/chats), publisher MAX, June 2026/live docs, accessed 2026-09-12, confidence high, class provider requirement.
3. **Agent runtime:** use OpenAI managed sessions or Agents SDK for turn state, tool dispatch, guardrails, HITL and traces; do not build a general orchestration engine in pilot one. Evidence: [Managed Agent session API](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/agents/subresources/sessions/methods/retrieve) and [Agents SDK](https://openai.github.io/openai-agents-python/), publisher OpenAI, n.d., accessed 2026-09-12, confidence medium-high, class current AI capability.
4. **Staffy-owned core:** one library/module containing action policy + executor and one append-only operations table. MCP is an adapter into this executor, not the authority. Evidence: [MCP risk vocabulary](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/), publisher MCP project, 2026-03-16, accessed 2026-09-12, confidence high, class security pattern.
5. **Jivo:** no universal dependency; integrate only if a pilot's humans are already on Jivo, respecting its short webhook budget and automatic handoff. Evidence: [Jivo Bot API](https://www.jivochat.com/docs/bot/), publisher JivoChat, n.d., accessed 2026-09-12, confidence high, class compatibility.

## Remaining gaps

- **Chatwoot freshness/fit:** native web/Telegram/API-channel capability was documented on 2026-04-29, outside the requested one-month compatibility window. A one-day spike against current v4.17.1 is required before treating it as selected. Evidence: [Chatwoot guide](https://www.chatwoot.com/hc/user-guide/articles/1677492191-adding-inboxes), publisher Chatwoot, 2026-04-29, accessed 2026-09-12, confidence high that freshness is insufficient, class verification gap; [Chatwoot releases](https://github.com/chatwoot/chatwoot/releases?after=v1.11.0), publisher Chatwoot on GitHub, 2026-08-27, accessed 2026-09-12, confidence high, class ecosystem/current version.
- **Managed Agents maturity and retention:** the current OpenAI session API is beta, and the retrieved source does not state a business-record retention/SLA contract. Verify retention, residency, export, failure recovery and pricing before relying on provider state. Evidence: [Managed Agent session API](https://developers.openai.com/api/reference/typescript/resources/beta/subresources/agents/subresources/sessions/methods/retrieve), publisher OpenAI, n.d., accessed 2026-09-12, confidence high for beta namespace and medium for the documented-gap inference, class managed-runtime gap.
- **Regional/commercial suitability:** this pass did not verify Twilio availability/economics for the target geography, nor MAX/Jivo/Telegram commercial restrictions. No selection claim should be made on that axis. Evidence: no qualifying primary evidence retrieved; confidence **low / unverified**; class: **commercial and regional gap**.
- **Failure semantics:** official docs establish retries, duplicate possibility, local state and handoff behavior, but do not establish end-to-end exactly-once business effects. Run a failure-injection pilot for duplicate inbound events, delayed model responses, action timeout after provider acceptance, and human/AI simultaneous reply. Evidence: [MAX guidance](https://dev.max.ru/docs-api/methods/GET/chats), publisher MAX, June 2026/live docs, accessed 2026-09-12, confidence high; [TAC overview](https://www.twilio.com/docs/conversations/agent-connect/overview), publisher Twilio, n.d., accessed 2026-09-12, confidence high; [Jivo Bot API](https://www.jivochat.com/docs/bot/), publisher JivoChat, n.d., accessed 2026-09-12, confidence high; class: **verification gap / reliability**.

## Source count and search notes

Eight distinct sources were used. The strongest simpler alternatives found were OpenAI Managed Agents/Agents SDK, Twilio Agent Connect, and Chatwoot. No primary evidence found in this pass showed a single platform that simultaneously provides the selected web + Telegram + MAX + Jivo channels, durable business-effect audit, and enforceable action policy. That absence is **not** proof none exists; confidence **low / unverified**; class: **landscape gap**.
