# Fresh-context red team: should Staffy build the complete Go voice core now?

**Conclusion attacked:** “Staffy should use a staged modular voice path for the first two pilots and postpone a complete own Go SIP/WebRTC/media core until measured triggers justify it.”  
**Mode:** adversarial search with no access to the supporting report or project context.  
**Access date for every source:** 2026-09-12.  
**Source budget:** 8 sources maximum; 8 used.

## Verdict

**The conclusion survives. Confidence: medium-high.** The search found strong evidence for putting an already-demonstrated latency-sensitive media/inference path in Go, but no evidence that two pilots inherently require Staffy to own a *complete* SIP + WebRTC + media core before observing a failure in the modular path.

The best evidence for Go-first is OpenAI's production experience: a Go/Pion service can own signaling and media for a 1:1 voice product [S1], and replacing a Python `asyncio` media frontend/inference path with Go improved frame-delivery smoothness so the new p95 matched the prior p50 [S2]. That evidence can overturn the recommendation **only if** Staffy's pilot has a non-negotiable tail-latency/full-duplex requirement and a representative test attributes misses to runtime scheduling, IPC, buffering, or the selected media abstraction. It does not establish that a complete proprietary SIP/WebRTC implementation is the smallest effective remedy.

The red-team case therefore changes the shape of the staged recommendation: **keep the media boundary replaceable from day one, and permit an early thin Go real-time path; do not equate that with building the whole telephony and WebRTC substrate.**

## What would actually overturn the conclusion before pilot 1?

Go-first is justified now only if at least one present-tense gate is satisfied—not because future scale is imagined:

1. **Measured real-time failure:** on representative hardware, network impairment, call duration, and expected pilot concurrency, the candidate modular path misses an agreed p95/p99 frame-gap, interruption, or end-to-end latency SLO; profiling attributes the miss to a framework/runtime/media boundary that a Go path removes.
2. **Hard protocol mismatch:** a pilot acceptance criterion needs RTP/RTCP access, codec control, media forking, outbound DTMF, custom jitter/loss behavior, or session ownership the candidate stack cannot expose without a fork.
3. **Eligibility failure:** legal/security review says all viable managed or externally hosted paths are ineligible and a self-hosted modular deployment still cannot meet the required data boundary or audit/control requirement.
4. **Irreversible coupling is unavoidable:** a short spike proves the staged provider forces business state, call identity, recording metadata, or application behavior into proprietary primitives that cannot be hidden behind Staffy-owned ports. Ordinary API wrappers or a self-hosted open-source media component do not satisfy this gate.

Even then, the evidence favors a **thin Go real-time kernel**—standard SIP/RTP/WebRTC at the edge, stable internal audio/event contracts, and provider adapters—before it favors a complete bespoke telephony platform. A complete core also inherits NAT traversal, codec negotiation, ICE/DTLS/SRTP state, public UDP exposure, carrier interoperability, recording, security patching, and failure recovery [S1][S7].

## Recommended red-team amendment to the decision

Retain the staged modular plan for two pilots, but add three non-negotiable safeguards:

- Define a vendor-neutral session/event contract and raw-audio boundary before integration; keep business state outside provider rooms/call objects.
- Run impairment and concurrency tests before each pilot, including p95/p99 frame gaps, barge-in success, one-way-audio recovery, call setup, and memory per active session; use the planned pilot load, not a forecast.
- Pre-authorize an early Go carve-out when one of the four gates above fires. Do not require a later executive re-argument merely because the original plan said “postpone Go.”

## Search limits and negative finding

The source set deliberately excludes marketing-only scale claims, anonymous anecdotes, and status-page incidents that merely prove a provider can have an outage. No primary or independent production evidence found within the source budget showed that a complete owned Go SIP/WebRTC/media core has higher pilot-stage reliability than a self-hosted modular stack. The missing evidence is a controlled, same-workload comparison at pilot-sized concurrency and Staffy's actual deployment/data-residency boundary.
