# Chatwoot as Staffy's system of engagement — round 2

**Decision:** Can current self-hosted Chatwoot v4.17.x be a replaceable system of engagement for Russia-first web + Telegram + MAX/Jivo pilots, rather than only a source of patterns?

**Verdict: one-day spike.** The evidence is strong enough to run a bounded deployment/integration spike, not strong enough to adopt immediately. Current Chatwoot removes substantial pilot work for web, Telegram, the shared inbox, conversation/contact storage, assignment, operator UI, and bot-to-human handoff. MAX has no documented native compatibility and would still require a Staffy-owned bridge through API Channel. Jivo can technically coexist through a webhook bridge, but the retrieved sources do not establish a safe dual-writer/source-of-truth design. Russian data-perimeter feasibility is plausible through self-hosting, but not verified: the official material does not enumerate all outbound telemetry, update, mail, object-storage, or AI egress.

## MAX through API Channel

**Assessment: protocol-shaped fit, undocumented compatibility.** Chatwoot's API Channel is expressly for unsupported/niche messaging platforms: Chatwoot sends outbound messages to a destination URL and the custom application relays them onward. That is the correct documented seam for a MAX bridge. No retrieved Chatwoot source names MAX, supplies a MAX adapter, defines MAX media/typing/edit/delete mappings, or guarantees behavior against MAX webhook retry semantics. Therefore “MAX can enter through API Channel” is a spike hypothesis, not an adoption fact.

- Evidence: [S2], publisher Chatwoot, 2026-07-22, accessed 2026-09-12, confidence **high** for API Channel's intended extension role, **low/unverified** for MAX compatibility; class: **integration compatibility**.

**Minimum spike proof:** inbound text creates exactly one Chatwoot contact/conversation; outbound human and bot replies reach MAX; duplicate inbound events are harmless; attachments degrade explicitly; handoff prevents double replies; provider IDs survive restart; and Chatwoot remains recoverable from an export. This is a proposed acceptance test, not a source claim; confidence: **n/a**; class: **verification plan**.

## Jivo coexistence

**Assessment: technically bridgeable, operationally ambiguous.** Jivo's Chat API and Chatwoot's API Channel are both bidirectional webhook surfaces, so an explicit Staffy bridge can translate between them. However, neither retrieved source documents Chatwoot↔Jivo compatibility, ownership of the authoritative conversation state, or loop/double-reply prevention. Running both as writable operator desks would therefore be an unverified dual-writer design.

- Evidence: [S2], publisher Chatwoot, 2026-07-22, accessed 2026-09-12, confidence high for generic API Channel; [S5], publisher JivoChat, n.d./live 2026 docs, accessed 2026-09-12, confidence high for Jivo's bidirectional API and retries; confidence **medium** for bridge feasibility and **low/unverified** for safe coexistence; class: **interoperability inference**.

**Recommendation:** for each pilot, choose one human system of engagement. If the customer requires Jivo, keep Jivo authoritative and attach Staffy's bot through Jivo's API; if not, keep Chatwoot authoritative and omit Jivo. A synchronized dual-inbox mode should not be in the first pilot. Evidence basis: [S2] and [S5] as above; confidence: **medium**; class: **architecture recommendation**.

## Vendor, upgrade and identity risks

- **Upgrade risk is material but bounded by self-hosting.** v4.17.1 is a recent patch with duplicate-message and security fixes; the v4.16.x notes also show public API/webhook, agent-bot token, and widget-identity fixes. Pin the exact image/version and run channel contract tests before each upgrade. Evidence: [S1], publisher Chatwoot/GitHub, 2026-08-27 and July 2026 release notes, accessed 2026-09-12, confidence **high**; class: **version/operational risk**.
- **API stability is not demonstrated by the retrieved docs.** The sources document behavior but no compatibility SLA, deprecation window, or stable webhook schema guarantee for Community Edition. Treat Chatwoot APIs as replaceable adapters and persist raw provider/Chatwoot IDs at Staffy's edge. Evidence: [S1] and [S3], publishers Chatwoot/GitHub and Chatwoot, 2026-08-27 and 2026-09-08, accessed 2026-09-12, confidence **low/unverified** because this is an absence-of-contract finding; class: **API-governance gap**.
- **License risk is low for a Community Edition spike, support risk is not.** Chatwoot says Community Edition is MIT-licensed and free but without premium support; hosting, maintenance and troubleshooting belong to the operator. Exact 4.17.1 repository file-by-file license boundaries were not verified in this five-source pass. Evidence: [S4], publisher Chatwoot, 2025-07-01, accessed 2026-09-12, confidence **medium**; class: **license/support**.
- **Identity remains the sharpest product risk.** Chatwoot exposes an account-wide contact with inbox-scoped conversations, but no retrieved source establishes automatic cross-channel identity proof. A person appearing through web, Telegram, MAX and Jivo may remain multiple identities unless Staffy or operators link them. Evidence: [S2], publisher Chatwoot, 2026-07-22, accessed 2026-09-12, confidence **medium**; class: **identity inference/gap**.

## Russian data-perimeter feasibility

**Feasible to test, not validated for production.** The official self-hosting guide claims data remains in the operator's environment and Chatwoot lacks access to the instance. That supports a Russia-hosted deployment hypothesis. It does not prove compliance, zero telemetry, or zero foreign egress, and the source is more than a year old. Before pilot data, capture DNS/HTTP egress for a clean 4.17.1 install; disable or redirect nonessential services; keep PostgreSQL, Redis, object storage, backups, email and logs inside the approved perimeter; and avoid Captain/external AI until its egress is separately approved.

- Evidence: [S4], publisher Chatwoot, 2025-07-01, accessed 2026-09-12, confidence **medium** for self-hosted data control, **low/unverified** for complete Russian data perimeter; class: **deployment/data-residency gap**.
- The proposed egress-capture procedure is a verification recommendation, not a documented Chatwoot feature; confidence: **n/a**; class: **verification plan**.

## One-day spike decision gate

Promote Chatwoot from “candidate” to “adopt for pilots” only if one pinned self-hosted v4.17.1 instance passes all of the following:

1. Website widget and Telegram round trips work with correct contact/conversation placement and AgentBot `pending ↔ open` handoff. Evidence basis: [S2] and [S3], publishers Chatwoot, 2026-07-22 and 2026-09-08, accessed 2026-09-12, confidence high, class compatibility test.
2. A minimal MAX bridge through API Channel passes duplicate, restart, media-degradation and outbound-delivery tests. Evidence basis: [S2], publisher Chatwoot, 2026-07-22, accessed 2026-09-12, confidence low/unverified until tested, class compatibility test.
3. Raw egress inventory shows an acceptable perimeter with Captain/optional external integrations disabled. Evidence basis: [S4], publisher Chatwoot, 2025-07-01, accessed 2026-09-12, confidence low/unverified until tested, class residency test.
4. Export/restore and pinned-version upgrade rehearsal preserve contacts, conversations and mappings. Evidence basis: [S1] and [S2], publishers Chatwoot/GitHub and Chatwoot, 2026-08-27 and 2026-07-22, accessed 2026-09-12, confidence medium, class operability test.
5. The pilot chooses Chatwoot **or** Jivo as the sole human-write authority. Evidence basis: [S2] and [S5], publishers Chatwoot and JivoChat, 2026-07-22 and n.d./live 2026, accessed 2026-09-12, confidence medium, class concurrency/source-of-truth test.

If any of gates 1–3 fails, downgrade to **patterns only**. Nothing in the retrieved evidence justifies **reject** before the spike, and nothing justifies **adopt now** without it.
